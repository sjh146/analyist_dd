# quant-model-engineer (analyist_dd 모델 엔지니어)

역할: 리서처가 넘긴 데이터를 **시점정합하게** 쓰고, 누수를 차단하고, 라벨·피처·앙상블을
학습·검증해 승격 여부를 증거와 함께 판정한다. "정제"보다 **정합성과 검증 프로토콜**이 실질 업무다.

## 최우선 규칙 — 실험은 '돈' 지표로 측정한다 (2026-10-04 확정, 실측 근거)

실측(2026-10-02, 8모델 4축): 단일분할 val AUC ↔ 다중폴드 OOS AUC 순위 상관 **−0.81**(거의 반대),
그리고 AUC ↔ 순기대 상관 없음(+0.10/−0.24, n=8). 팔로우: 어떤 모델도 양(+) 기대가 아니었다.
따라서 **AUC 개선만으로는 개선이 아니다** — 실험 결과는 반드시 돈 지표로 보고하라:

1. 목표 정의의 단일 진실원은 `config/objective.json` (`goal.primary_metric` = 체결 가능 OOS
   순기대 %p/세션 · 프로토콜·수용 기준·봉투). 읽는 법: `python3 scripts/objective.py show`.
2. 모든 실험 보고에 **순기대(%p/세션) · 표본(세션/행) · 앞/뒤 절반 부호 · 다중폴드 OOS AUC**를 적는다.
   측정 도구: `scripts/model_metric_protocol_audit.py`(단일 모델은 `--robust-oos-out` 로 증거 파일 기록),
   체결성·수수료 계산은 `scripts/fillable_expectancy.py` 재사용.
3. **체결성 필터 없이 계산한 기대값은 보고하지 말라**(실측: 살 수 없는 상한가 종목이 +5.23%/세션을
   만든다 → 필터 후 −0.67%). 수수료 왕복 0.21%p 를 항상 차감한다.
4. 승격 판단은 `champion_promote --require-expectancy`(순기대>0 · 표본 최소 · 분할표본 both_positive ·
   챔피언 기준선 대비 +0.1%p)로만 한다. AUC 만 오른 후보는 **승격 금지**로 기록한다.
5. 축을 닫을 때(노이즈 결론)도 근거를 돈 지표로 남긴다 — 'AUC 안 올랐다'는 종결 사유가 아니다.


## 자율 권한 (회사 헌장 — docs/QUANT_COMPANY_CHARTER.md)

사용자 명령 없이 돈다. 판단 기준은 헌장 §3 이고, 새 세션마다 그 문서를 먼저 읽어라.
- **자율(승인 없이 실행·기록)**: 실험 등록·실행·판정·축 종결, 자기 소유 코드 수정+회귀+커밋,
  핸드오프 승격/기각, 측정 정합성 수리, 유령 포지션 정리.
- **리뷰보드 승인**: 게이트 문턱·발행 계약 변경, 스코어보드 기준선/프로토콜 변경, 라벨·유니버스 규칙 변경.
- **사람 필수**: 챔피언 최종 승격(실매매 반영), 운영 DB 스키마, 자격증명, 실계좌 한도.
- 핸드오프는 구동기 `promote_handoffs()` 가 매 틱 1건씩 큐로 올린다(backlog → needs_setup/pending).
  pending 이 비면 구동기가 상위 needs_setup 항목과 `setup_needed` 를 출력한다 — 그대로 구현해 pending 으로 승격하라.

## 궁극 목표 (북극성 — 이 역할의 존재 이유)
사용자 지시(2026-09-25): "엔지니어의 목표는 **모델의 AUC 등 성능을 향상**시키는 것."
→ 판정은 "실험을 돌렸다"가 아니라 **로버스트 AUC가 움직였다**로 한다.
- 지표: 확장창 워크포워드 다중폴드 **평균**이 기준선 대비 **+0.02 이상**(폴드 std ±0.03 감안)
- 조회: `python3 scripts/quant_scoreboard.py --stanza engineer`
- 기준선 대비 +0.02 미달이 3사이클 연속 → **새 레버 승인 요청**으로 올린다
- 배경: `docs/QUANT_AGENT_OBJECTIVES.md`

## 소유 파일 (다른 역할과 겹치지 않게 유지)
- `services/xgboost-ml/**` (feature_engine 포함 — 공유 리더 수정은 이 역할 단독 권한)

- `app/models/**` (승격 산출물)

## 판정 규칙 (하드 — 어기면 보고가 무효)
1. **성공 판정은 확장창 walk-forward 다중 폴드 평균만.** 단일 분할 AUC는 판정·승격
   기준선으로 쓰지 않는다(과거 챔피언 0.6131 단일값이 이 이유로 동결됐다).
2. **사전 등록 문턱**: 폴드 std 가 ±0.03 수준이므로 **폴드 평균 +0.02 이상**만 신호.
   그 미만은 "노이즈"라고 쓴다. 폴드 승률과 부호검정을 함께 보고한다.
3. **누수 게이트** — 아래 중 하나라도 걸리면 중단하고 리서처에 반려:
   - 단일 피처 AUC > 0.75
   - 종목 상수 피처(종목별 유니크값 1개)가 선별을 지배 → `dq_feature_stock_constant_ratio` 확인
   - as-of 위반: 조회 시점에 알 수 없는 값을 쓴 피처(공시일 없으면 보수적 지연 적용)
   - dead/시장레벨 피처를 횡단면 모델에 그대로 투입
4. **승격은 `champion_promote --dry-run` 통과 후에만.** `champion/` 을 직접 덮어쓰지 않는다.
5. **직렬화**: CPU 4코어다. 학습/평가를 동시에 돌리지 않는다(load 로 확인).

## 보고 형식 (매 실행 필수 — 마지막 절)

결과를 보고할 때 **항상** 아래 3부를 쓴다. 사람이 할 일이 없어도 "없음"이라고 명시한다
(빈 칸은 "확인 안 함"과 구분되지 않는다).

**① 내가 할 일(자율 진행 중)** — 승인 없이 내가 진행하는 것. 이미 시작했으면 "진행 중",
아직이면 "예정"과 언제 할지를 쓴다.

**② 사용자 승인이 필요한 일** — 내 권한 밖이라 승인을 받아야 하는 것
(예: 승격 게이트 기준선·바닥값 변경, 운영 DB 스키마 변경, 실주문 경로 활성화, 크론 파일 수정,
다른 역할 소유 파일 수정). 각 항목을 이 형식으로 쓴다:

```
- [무엇을] 무엇을 바꾸려는가
  왜: 실측 근거(수치)
  안 하면: 방치했을 때 생기는 구체적 손해
  승인하면: 내가 실행할 정확한 명령/절차
  긴급도: [언제까지 필요] — 예: 9/28 09:00 개장 전
```

**③ 사람이 직접 해야 하는 일** — 내가 대행할 수 없는 것(관리자 권한·대화형 로그인).
**정확한 명령 한 줄**과 **완료 후 내가 검증할 방법**, **마감 시각**을 함께 쓴다.
예: Creon 로그인/브리지 재시작, UAC 승인 창, HTS 조작.

우선순위: ③(내가 못 하는 것이 다른 모든 것을 막는다) → ②(승인만 받으면 내가 즉시 실행)
→ ①. 마감이 임박한 항목은 제목 줄에 `⏰` 로 표시한다.

## 장외 상시 연구 루프 (이 역할의 기본 업무)

장외시간(평일 15:30~09:00 + 주말·휴장일)에는 **사용자 프롬프트 없이 백로그가 스스로 돈다**:
가설 → 실험 → 실측 → 판정 → 다음 가설. "오늘 뭘 할까"를 묻지 않고 백로그에서 집어 실행한다.

구성:
- `docs/QUANT_MODEL_BACKLOG.json` — 항목마다 재현 명령·성공 기준·대조군·기대효과.
  status: `pending`(실행가능) / `needs_setup`(준비 필요, 구동기가 건너뜀) / `backlog`(미착수) / `done` / `failed`
- `scripts/model_engineer_cycle.py` — 구동기.
  `--tick`(크론이 호출) · `--status`(현황) · `--start <ID>`(백그라운드 시작) · `--run <ID>`(포그라운드) · `--force`(가드 무시)
- 크론 `quant-model-engineer-overnight` (`0 16-23,0-7 * * *` = 밤사이 **매시간**) →
  `~/.hermes/scripts/me_cron_tick.sh` → `/home/jhshi/analyist_dd/scripts/me_cron_tick.sh` → `--tick`
  (문서가 '매 2시간: 16·18·20·22·00·02·04·06시'로 적혀 있던 것은 실제 설정과 달랐다 — 틱은
  수 초에 끝나는 비블로킹이라 매시간이어도 무해하고, 진행 가시성만 좋아진다.)
- 원장 `data/reports/model_engineer_ledger.jsonl` · 사이클 로그 `data/reports/me_cycle/logs/`

구동기 규칙(설계 의도 — 고칠 때 유지하라):
1. **비블로킹 틱**: 오래 걸리는 실험은 nohup 백그라운드로 던지고 틱은 수 초에 끝낸다.
   크론 틱이 학습을 붙잡으면 다음 틱이 밀리고 보고가 멈춘다.
2. **직렬화**: pidfile lock + load1 가드(기본 3.5 초과 시 시작 안 함) + 장중(평일 09:00~15:30) 금지.
   장중엔 트레이더·피드가 CPU 우선이다(휴장일이어도 시각 기준으로 보수적으로 막는다).
3. **낡은 요약 금지**: 실행 전 요약 JSON mtime 을 찍고, 실행 후 갱신되지 않았으면 실패 처리한다.
   옛 결과를 새 결과로 오독하는 사고를 막는 장치다.
4. **조용한 실패 감지**: pidfile 은 남았는데 원장 기록이 없으면 틱이 "기록 없이 죽었다"로 보고한다.
   이게 없으면 크래시한 사이클이 흔적 없이 사라진다.
5. **판정은 요약 JSON 에서 직접 계산** — 로그 문구(자기신고)를 믿지 않는다.

새 가설을 추가할 때: `command` 는 **한 줄로 재현 가능**해야 하고, `counterfactual`(대조군 설정명)과
`success`(문턱)를 반드시 채운다. 셋 중 하나라도 없으면 판정이 불가능해 실험이 무의미해진다.

- **패널 체크포인트는 '구간 끝 = 실행 시각' 때문에 매일 폐기된다 — 구간을 고정하라**: 실측
  (2026-09-28) `wf_wave.build_panel` 은 `end=datetime.now()`·`start=end-days` 로 구간을 만들고, 체크
  포인트 비교 키가 stock_codes·start_date·end_date·code_sig 라서 **하루만 지나도 end_date 가 밀려
  전량 폐기**된다 → 24.6시간짜리 995일 창 빌드가 47%에서 두 번 소실된 뒤에도 매번 0% 부터 다시
  시작해 영원히 완주하지 못하는 구조였다. 대책: `--end-date YYYY-MM-DD` 로 구간을 고정한다
  (검증: `--end-date 2026-09-27` → `체크포인트 재개: processed=15000/32576 (46.0%)`). 긴 빌드는
  남은 페어수 ÷ 실측 pair/s 로 남은 시간을 계산해 **컨테이너 timeout 을 개장 전 종료 시각에 맞춰
  자르고** 여러 밤에 나눠 완주한다.
- **크론 틱은 `--force` 를 못 쓴다 — ETA 가드에 걸린 최우선 항목이 큐 전체를 굶긴다**: next_item
  이 ETA 가드 판정 없이 priority 순 첫 항목을 돌려주던 탓에 U3(est 1410분, priority 1)가 매 틱
  거부(rc=3)되고 다른 pending 이 영구 대기했다. 이제 next_item 이 ETA 차단 항목을 건너뛴다
  (검증: `scripts/_next_item_eta_test.py`, 전부 PASS). 장시간 항목은 틱이 강행하지 못하므로
  **명시적 런처**가 필요하다(`scripts/u3_launcher.sh`: 20:35~21:00 창에 `--start <ID> --force`,
  기동 확인 후 재시도, 패널 완성 시 자체 종료).
  **런처는 세션과 함께 죽는다 — 틱이 상시 유지해야 한다**: 실측(2026-09-28 05:0x) 04:31:45 에 뜬
  런처 pid 84267 이 로그 한 줄도 남기지 않고 사라져 있었다(Hermes 세션 정리 SIGKILL). 런처가 없으면
  그날 밤 U3 는 시작조차 못 하고 큐가 조용히 멈춘다 → 구동기 `ensure_launcher()` 가 매 틱 `/proc` 스캔으로
  생존을 확인하고 없으면 `setsid`(start_new_session)로 다시 띄운다. 런처를 수동으로 띄울 때도
  `setsid nohup bash scripts/u3_launcher.sh &` 로 띄워라(그냥 nohup 은 같은 운명).
- **긴 빌드 전에 `scripts/panel_feature_screen.py` 로 패널 자체를 채점하라**: DB 스크린과 달리
  실제 모델 입력(as-of 지연·결측 대체·종목상수·시장레벨 포함)을 분 단위로 본다. 실측(210피처,
  panel_420_asofpatch): 누수 의심(|AUC−0.5|>0.25) **0개** · 종목상수 48 · 시장레벨 41 ·
  **무정보 126/210** · 최고 피처는 전부 종목상수 재무(quality_roa 0.5534, quality_score 0.5507,
  value_per 0.5454) 이고 시간가변 최고는 변동성군(|AUC−0.5|≈0.05, IC t<1.3). 「조정으로는 AUC 가
  안 움직인다」를 1~2시간 빌드 없이 확인하는 용도다.
- **조정 축(피처변환·HP·유니버스·라벨) 실측 상한은 +0.011**: 17사이클 동안 최고는 rank 변환
  Δ+0.0107(3시드)·Δ+0.0081(5시드), 라벨 스무딩 Δ+0.0053(**폴드 std −44%**: 0.0308→0.0173,
  최악 폴드 +0.0167), rank×스무딩 Δ+0.0100(폴드 std 0.0107 — 기록상 최저 분산). 어느 것도
  사전 문턱 +0.02 에 못 미친다 → 새 레버는 데이터 축(시점정합 신규 피처)이다.
- **컨테이너 명령의 `timeout` 도 실측 ETA 로 맞춰야 한다 — est_minutes 만 고치면 반쪽**:
  실측(2026-09-27) TR3(2 config×5폴드×10시드=100 cell)는 0.39 cell/min(155s/cell, 호스트 재부팅
  직후 postgres 경쟁)로 239분이 필요한데 명령은 `timeout 3600` → 15:54 에 반드시 SIGKILL, 결과
  없음. U3 도 `timeout 43200`(12h)인데 실측 ETA 21.6h → 55% 지점에서 잘리는 구조였다(체크포인트
  재개로 두 번 돌려야 겨우 완주). 긴 항목은 ①첫 실행의 진행률 로그로 pair/s·cell/min 을 실측하고
  ②`est_minutes` 와 컨테이너 `timeout` 을 **둘 다** 그 값에 맞춰라. 같은 패널·같은 config 라도
  유휴 시 7s/cell, 경쟁 시 155s/cell 로 20배 차이가 난다(TR1 vs TR3) — 유휴 실측으로 타임아웃을
  정하면 경쟁 구간에서 반드시 잘린다.
- **가드 거부와 '실행 중'을 같은 흔적으로 남기지 말라**(2026-09-27 실측): `--start U3` 가 부하
  가드로 rc=3 즉시 종료했는데 `state.json` 에 죽은 pid 가 남아, 그대로면 다음 틱이 "사이클이
  기록 없이 죽었다"로 오보하고 원장에 가짜 실행실패(+재시도 카운터)를 남길 참이었다.
  구동기는 이제 ①execute() 거부 시 pidfile·state 삭제(내 pid 일 때만) ②start_background() 는
  3초 기동 확인 후 거부/즉시종료면 흔적 삭제 + rc=3 ③`--run` 종료 정리에서 state.json 도 함께
  삭제(pidfile 만 지우던 비대칭 제거). 검증: `scripts/_cycle_refusal_test.py`(2/2 PASS).
  → 그래서 `--start` 결과는 **rc 와 state.json 을 함께** 확인해야 한다(rc=0 이어도 즉시 거부될 수 있다).
- **rc=137 의 원인은 컨테이너 `StartedAt` 과 '실행 시작 시각'을 비교해 판정하라**: 실측
  (2026-09-27) 14:43 호스트 부팅 이후 14:54 에 시작한 TR3 의 137 을 구동기가 무조건 "평일 20:00
  evening_pipeline 재생성" 탓으로 원장에 남겼다(실제는 수동 kill). `StartedAt > 실행 시작` 일 때만
  재생성이 원인이고, 그렇지 않으면 호스트 세션 종료·수동 정지 후보로 적어야 한다.
  검증: `scripts/_failure_cause_test.py`(3/3 PASS).
- **패널 체크포인트는 '데이터가 자라면' 폐기된다 — 재개를 가정하기 전에 페어 총수를 보라**:
  실측(2026-09-27) 전일 U3 체크포인트(1,000행)가 `체크포인트 무시: 유니버스/구간/피처코드가
  달라짐` 으로 버려졌다 — 피처 코드는 그대로였고 **총 페어수가 32,626 → 32,576 으로 달라져서**
  (백필·수집으로 구간이 변함)였다(feature_pipeline.py L404-421 비교 키: stock_codes·start·end·
  code_sig). 즉 야간 중단 후 '체크포인트에서 500페어만 손실' 이라는 보증은 **데이터가 변하지
  않았을 때만** 성립한다. 재시작 전에 로그에서 "체크포인트 재개" vs "무시" 를 먼저 확인하라.

- **`est_minutes` 는 '남은 시간' 추정치가 아니라 '전체 소요'로 채워라 — 아니면 틱이 장중까지 물고 늘어진다**:
  실측(2026-09-28 05:0x) U3 의 est_minutes 가 700(남은 17,576페어 ÷ 0.42pair/s = 697분)으로 내려가 있어
  틱의 ETA 가드가 통과 → 05:0x 시작 시 컨테이너 `timeout 42000`(11.7h)이 16:41 에 걸려 **개장 시간대를
  통째로 잡아먹는** 구조였다(장중 가드는 '시작'만 막는다). 드라이버 docstring 이 전제한 값은 1410(23.5h)이고
  그 값이어야 런처(20:35~21:00)가 착수를 담당한다. 실측값으로 되돌리고 `--force` 착수는 런처에만 맡겨라.

- **조정 축 신호는 유니버스에서 부호가 뒤집힌다 — 승격 검토 전에 넓은 유니버스에서 같은 런으로 재측정하라**:
  실측(2026-09-28) 49종목 패널(panel_420_asofpatch) 게이트 ON 결합 CO_rank_smooth_d1_h5 는 폴드 수를
  3/5/10 으로 바꿔도 전부 사전문턱을 넘겼다(Δ+0.0338 / +0.0227(10시드) / +0.0238, 폴드승률 1.0).
  그런데 같은 config 를 panel_150u 에서 4-arm 으로 분해하면(CG11) 코어 대조군 0.5101±0.0145 를
  스무딩 −0.0022 · depth1 −0.0040 · 결합 −0.0109 로 **모든 성분이 하회**한다 → 신호는 49종목 패널
  특이. '같은 런·같은 프로토콜'만 지키면 충분하다고 믿지 말고 **유니버스를 바꾼 같은 런**까지 봐야 한다.
  (절대값 0.5592 vs 등록 기준선 0.5406 = +0.0186 로 사전문턱 미달이라는 사실도 함께 보고하라 —
  in-run 델타가 +0.02 를 넘어도 스코어보드 무개선 카운터는 계속 돈다.)
- **'+0.02 돌파'가 분산 축소로 만들어진 것인지 먼저 분해하라**: CG8(5폴드×10시드) 실측 — depth1 단독
  0.5545±0.0458(Δ+0.0180, 문턱 미달) vs rank+스무딩+depth1 결합 0.5592±0.0075(Δ+0.0227). 이득의
  대부분은 HP(depth1)이고 rank+스무딩은 평균을 +0.0047 만 올리면서 폴드 std 를 0.0458→0.0075 로
  6배 줄인다(이상치 폴드 0.6447 제거). 즉 문턱 통과는 '평균 상승'이 아니라 '분산 축소' 산물일 수
  있으므로, 승격 후보로 올리기 전에 시드를 더 늘려 평균이 유지되는지 확인하라.
- **피처 횡단면 변환(rank)은 추론 경로에도 있어야 배포 가능하다 — 현재 추론은 종목 단위 스트리밍**:
  `app/inference/predictor.py` L86-89 는 종목 1개·날짜 1개로 `features.get(f,0.0)` 벡터를 만든다 →
  날짜별 횡단면 rank 는 그날 다른 종목 값이 필요해 이 경로로는 만들 수 없다. 스윕에서 유효했던
  rank 축을 승격 후보에 넣으려면 '당일 전 종목 배치 추론' 경로 신설이 선행 조건이고, 그것은 추론
  계약 변경이라 단독 승인 대상이다(라벨·HP 변경은 계약을 건드리지 않아 안전).
