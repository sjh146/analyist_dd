# 피처 패널 진단 · 재빌드

학습 패널(종목×날짜×피처)에서 "죽은 피처"를 만났을 때, ① 왜 죽었는지 분해하고 ② 다시 만들기 전에
비용을 계산하고 ③ 재빌드 후 같은 기준으로 재판정하는 절차. 판정은 항상 **개수가 아니라 원인 분류**로 한다.

## 1. 죽었는지부터 두 축으로 나눈다

### 1a. 먼저 코드가 0으로 덮고 있는지 본다 (가장 흔한 원인)

피처 코드가 조회 실패를 조용히 `0.0` 으로 대체하면, 원인 추적이 **불가능**해진다(0-채움과 실제 0이
같은 값). 패널을 의심하기 전에 파이프라인 소스를 grep 한다:

```bash
grep -n -A3 'except Exception' app/feature_engine/feature_pipeline.py | grep -c 'logger.debug'
grep -rn 'unavailable; using 0.0' app/feature_engine/
```

처방은 **0 을 NaN/결측으로 바꾸는 것이 아니라 먼저 '가시화'** 다: 조회 헬퍼마다
`_note_miss(feature, exc)` 로 (피처, 예외클래스) 카운트를 올리고 같은 사유는 WARNING **1회**만 찍고,
프로세스 종료 시(`atexit`) `feature_miss_report.json` 으로 덤프한다. 그 다음 3종목×1일만 빌드해
리포트를 읽으면 죽은 피처의 진짜 이유가 바로 나온다(실측: `UndefinedTable: relation "short_interest"
does not exist` → 테이블 자체가 없었다).

- **테이블 없음 / 컬럼 all-NULL / 기간 불일치를 구분**한다: `count(*)` 가 아니라 `count(column)` 으로 센다
  (실측: 188,264행인데 `count(balance_quantity)=0` → 계산 불가. 이건 쿼리 수리가 아니라 원천 수집 문제다).
- 원천이 비어 있는 피처는 0으로 내지 말고 **커버리지 게이트로 모델 입력에서 제외**하고, 결측으로 집계한다.
  없는 값을 0으로 두면 모델이 "정보 없음"과 "실제 0"을 구분하지 못한다.
- **진단용으로 파이프라인을 직접 호출할 때는 DB 연결을 넘겨라.** `FeaturePipeline()` 처럼 인자 없이 만들면
  `pg_conn=None` 이라 모든 DB 기반 피처가 기본값 `0.0` 으로 반환된다 — "원천이 죽었다"는 오진이 정확히 여기서 나온다
  (실측: SNS 행이 있는 종목조차 sentiment 0.0 → `pg_conn` 을 넘기면 0.0021·momentum -0.0525 로 정상).
  컨테이너 접속 env 로 커넥션을 만들어 넘기고, 같은 호출을 **연결 유무 두 번** 돌려 값이 달라지는지로 확인한다.

### 1b. 생존 리포트의 두 값을 **함께** 읽어라:

- `null_ratio 0.0` 인데 `std 0.0` → **결측을 0으로 덮은 것**이다. "측정된 0"이 아니다.
  모델은 "정보 없음"과 "실제 0"을 구분하지 못하고, 분산 0이라 트리 분기도 못 한다.
- `nnz < 5%` 정도로 희박 → 죽은 게 아니라 **드문 것**이다(이벤트류). 임계 설계 문제이지 데이터 결함이 아니다.
- `null_ratio` 높음 → 원천이 없거나 조인이 빗나간 것. 커버리지 축으로 넘어간다.

처방이 갈린다: 0-채움 → **결측은 NaN 유지 + 결측 지시자(missing indicator) 피처** 추가. 희박 → 누적 카운트·
EWMA·타깃 인코딩으로 재정의. 원천 결손 → 수집·조인 수리.

### 1c. 생존 점검은 매일·4단계로 자동화한다 (수동 grep 은 그날만 본다)

`feature_coverage` 스냅샷 두 값(`nonzero_ratio`, `cross_section_constant_ratio`)으로 매일 판정하고,
**전일 대비 새로 죽은 피처**를 따로 뽑아야 회귀가 잡힌다.

| 등급 | 판정 | 의미 |
|---|---|---|
| alive | nonzero ≥ 1% | 정상 |
| sparse | 0.05% ≤ nonzero < 1% | 희소 이벤트 — 정상값일 수 있다 |
| constant | 종목간 상수비율 > 99% | 시장공통 → 순위 기여 0 |
| dead | nonzero < 0.05% | 원천 결측/계산 실패 |

- **`nonzero < 1%` 를 곧바로 dead 로 쓰지 마라** — 이벤트류는 0.3% 가 정상값이라 대량 오탐이 난다
  (실측: 1% 기준 40개 → 0.05% 기준 22개). 임계는 등급별로 나누고, 보고에는 네 숫자를 함께 쓴다.
- 스냅샷이 2일 이상 낡았으면 판정을 `STALE` 로 라벨한다 — 그날 고친 원천 교체가 아직 반영되지 않은
  상태를 '새로 죽음'으로 읽으면 없는 회귀를 쫓게 된다.
- 주기는 수집 크론보다 **앞선 시각**(예 07:00)과 마감 후(16:10) 두 번. 수집·학습 뒤에 돌리면 그날은 이미 지나갔다.
- 산출물은 최신 1개 + 일자별 JSON + 로그 1줄로 남기고, 다음 실행이 그 최신 파일을 '전일'로 읽어
  `new_dead` 를 계산하게 한다(별도 DB 불필요).
- 원천이 **아예 없는** 피처(테이블 부재·컬럼 전부 NULL)는 죽음으로 세는 대신 ① 실데이터 프록시로 재정의하거나
  ② 커버리지 게이트로 모델 입력에서 빼고, 그 사실을 보고에 적는다 — 이름만 살린 0-채움이 가장 나쁘다.
- **원천부재는 별도 버킷(`unavailable`)으로 분리해 `dead` 집계에서 뺀다.** 코드가 조회조차 하지 않고 `0.0`
  으로 고정한 피처(예: 종목별 신용잔고·ETF 설정액 — 국내 공개 API 미제공, 비ETF 종목엔 정의상 값 없음)는
  "죽어서 고칠 수 있는 것"과 처방이 다르다. 예: `STRUCTURAL_UNAVAILABLE = {name: 사유}` 를 판정 함수
  최우선 분기로 두고 리포트에 `unavailable: {이름: 사유}` 로 남긴다(실측 dead 14 → 11 · unavailable 3).
- **그 피처들을 지금 지우지는 마라 — 챔피언 모델이 그 길이로 학습됐다.** 피처 목록에서 빼면 입력 벡터
  길이가 바뀌어 champion 추론이 깨지거나 조용히 어긋난다. 제거는 **다음 재학습 때** 하고, 그때까지는
  "설계상 상수"로 표기하고 모델 기여 0 임을 보고에 적는다(커버리지 게이트가 이미 drop_constant 로 처리).
- **리포트 쓰기는 원자적으로(tmp + `os.replace`)**: 크론이 root 로 돌면 산출물 소유자가 root 가 되어
  일반 사용자 재실행이 `PermissionError` 로 죽는다(실측 16:10 잡 → 사용자 실행 실패). 같은 디렉터리에
  tmp 를 쓰고 replace 하면 **디렉터리만 쓰기 가능하면 소유자와 무관하게** 교체된다 — 실패를 피하려
  파일을 지우거나 권한을 바꾸려 들지 말고 쓰기 방식을 고친다.
- **`feature_coverage` 는 여러 빌더가 조각내어 쓴다 — 판정 전에 `select computed_at, count(*) group by 1` 을 봐라.**
  이벤트·매크로·수급 빌더가 각자 자기 몫만 INSERT 하므로 어떤 피처는 며칠 전 실행 값으로 동결된다
  (실측: 209행 중 131행이 2일 전 값, 6피처가 그 값으로 'dead' 판정). 동결 행은 `STALE` 로 표기하고
  그 피처는 **패널에서 직접 다시 잰다**.
- **죽음의 최종 근거는 커버리지 테이블이 아니라 패널 행렬이다.** npz 의 `feature_names`+`X` 로 피처별
  nonzero%·std 를 재계산하면 ① 실제로 0 인지 ② 패널에 **컬럼 자체가 없는지**(계약 235 vs 패널 221 같은
  길이 차이)를 한 번에 가른다. 커버리지에 있는데 패널에 없는 피처는 계산 비용만 쓰고 버려진다.

### 1c-2. 피처 계약 ↔ DB 정합성은 기계적으로 감사한다 (LLM 에 맡기지 않는다)

"스크립트가 참조하는 테이블·컬럼이 실제로 있는가" 는 재현 가능한 검사다. LLM 에게 레포 전체를
읽히면 25분 넘게 돌다 타임아웃되고 결과가 남지 않는다(실측 rc=124). 결정적 스크립트로 돌려라:

- SQL 은 **삼중따옴표 블록 중 `select` 가 들어간 것만** 대상으로 한다. 파일 전체를 정규식으로 훑으면
  docstring 의 `from all data sources` 같은 문장이 '없는 테이블 all' 로 오탐된다(실측 오탐 8 → 0).
- `WITH x AS (` 로 선언된 **CTE 이름을 참조 목록에서 제외**한다 — `FROM d`, `FROM r` 같은 별칭이
  '없는 테이블' 로 잡힌다.
- 함께 볼 축: ① 크론이 부르는 스크립트 경로 존재(경로 하나만 틀려도 그 잡은 조용히 0회 실행)
  ② `.bak` 이 붙은 크론 파일 제외(백업을 세면 중복 스케줄이 수십 건으로 부푼다) ③ 같은 테이블을 쓰는
  스크립트 다중 writer 목록 ④ `.env` 에 없는 env 키(대부분 기본값이 있으니 '누락'이 아니라 '미등록'으로 표기).
- 결과는 `crash` 가 아니라 **JSON + 심각도 정렬**로 남기고, 매일 07:20 등 수집 전 시각에 크론으로 돌린다.

### 1c-3. 같은 이름의 피처가 '계약'과 '커버리지'에서 엇갈리는지 본다

파이프라인 `get_feature_names()` 와 `feature_coverage.feature_name` 을 **양방향 차집합**으로 비교한다.
실측: 계산·보유 중인데 계약에 없어 버려지던 피처 2개(`market_breadth`, `theme_momentum`), 계약에는
없는데 커버리지에만 남은 레거시 1개(`kalman_gain`). 계산은 되는데 계약에 없으면 그 비용은 순손실이다.



테이블 행수는 착시다. 반드시 패널의 `codes`·`dates` 로 다시 조회한다:

```sql
SELECT count(*), count(DISTINCT stock_code)
FROM <source> WHERE stock_code = ANY(%s) AND <date_col> BETWEEN %s AND %s;
```

실측 사례: 뉴스 테이블 12,817행이 살아 있는데 패널 200종목 중 27종목, 패널 기간 내로 좁히면 **4종목**.
SNS 29/200 · 수급 92/200 처럼 소스별 커버리지가 제각각이면, 피처가 0인 이유는 모델이 아니라 **조인 대상**이다.

- **소스 시계와 패널 시계를 대조하라.** 소스 시작일이 패널 시작일보다 늦으면 그 구간은 구조적으로 0이다
  (실측: 패널 2025-08~2026-09 인데 뉴스 2026-04~, SNS 피처 2026-09-23~, 감성 2026-11-15~).
  "이 피처는 무정보"라는 과거 결론이 **그 당시 소스가 없었기 때문**일 수 있다.
- **수집이 '기사/게시글 등장 종목' 기준인지 유니버스 기준인지 확인하라.** 전자면 조용한 종목은
  영원히 0이다 — 리더를 고쳐도 유니버스를 넓히기 전엔 안 살아난다.
- **수집기의 선정 기준과 패널 유니버스의 선정 기준이 같은지 대조하라 — 이름이 같아도 순위 축이 다르면 교집합이 붕괴한다.**
  실측: SNS 수집기는 "당일 거래대금 상위 250"으로 코드를 뽑고 패널은 "시총 상위 200"이라 교집합이 **36/200(18%)**,
  감성 피처 nonzero 0.01%였다. 처방은 수집기의 자동 유니버스를 그대로 쓰지 말고 **패널 npz 의 `codes`를
  `--codes`로 직접 넘기는 전용 크론**을 두는 것(200종목 수집 ≈ 13분, 교집합 36 → 130종목(65%), 패널 (종목,일) 0.01% → 4.9%).
  원천 행수가 아니라 **패널 코드 ∩ 원천 코드**를 항상 세어 보고한다.
- **부활 판정은 nonzero% 만으로 끝내지 말고 그 피처 하나의 상위-하위 분위 스프레드와 t 를 재라**(패널 행렬만으로 계산 가능,
  비용 왕복 0.21%를 빼서). 실측: 테마 모멘텀은 nonzero 10.5% · 5일 스프레드 +0.841% · **t=2.50(47폴드)** 로 부활 확정,
  같은 방식으로 늘린 SNS 3종은 유효값 4.2%(소스 시작이 늦음)에 |t|<1.4 로 **판정 불가**였다. 커버리지 상승과 엣지 확보는
  별개이므로 "살아났다"와 "돈이 된다"를 나눠 보고하고, 표본이 얇은 쪽은 기간을 더 쌓은 뒤 재판정한다.
- **죽은 컬럼과 살아 있는 원천 테이블을 구분하라.** 컬럼 기준 종결은 원천이 자라면 뒤집힌다 —
  닫힌 축은 분기마다 `pg_stat_user_tables` 행수·기간으로 재확인한다.

- **커버리지 게이트는 NaN 기준으로 만든다**: `nonzero_ratio` 로 결측을 판정하면 카운트형 피처
  (공시 건수 등)가 정당한 0 때문에 결측으로 오판된다(실측 98 vs 26 — 4배 과대). 패널 X 의 NaN 비율로
  `drop_missing`(NaN>50%) 과 `drop_constant`(날짜별 종목간 표준편차 0 비율>95% = 시장공통 → 크로스섹션
  순위에 기여 0)을 나누고, 남은 목록을 매일 갱신해 둔다(실측 235 → 사용 177 · 결측 26 · 시장공통 32).
- **로그 선별: 시장공통 피처는 '죽은' 것이 아니다** — 값은 있지만 종목 간 구분이 안 되므로 순위 모델 입력에서만
  무의미하다. 레짐/사이즈 조절 변수로 분리하는 것이 맞다.

## 2b. 생존(alive/dead)이 아니라 '비용 차감 후 기대값'으로 판정한다

생존 등급은 "값이 있냐" 만 답한다. 투자 판단은 그 피처로 상위 10%를 샀을 때 **비용 후 순수익**이
플러스냐로 한다. 신호 레지스트리(피처 × 거래일 전수)를 주 1회 돌려 한 표로 낸다:
IC(h1/h5/h20) · t값 · 커버리지 · 상위10% 비용차감 순수익. 실측: 표본이 충분한 155개 중 순수익이
플러스인 것은 **11개**였다 — alive 86개와 격차가 크고, 이 격차가 곧 "부활했지만 돈은 안 되는 피처"다.

판정 전에 걸러야 하는 함정 3개(전부 실측에서 나왔다):

- **하루치 데이터만 있는 피처가 1위로 올라온다.** 관측일이 적으면 IC·수익이 우연으로 폭발한다 →
  표본 하한(예: 60거래일) 미만은 순위에서 빼고 `판정보류`로 따로 센다(실측 80개).
- **액면분할·감자 미조정 가격이 초과수익을 수백%로 만든다**(실측 006740: 5일 287→3,870). 전방수익
  |x| > 50% 행을 이상치로 제외하고, **제외 행 수를 보고에 숫자로** 적는다. 안 걸러내면 순수익 1위
  피처가 전부 오염 피처가 된다.
- **초과수익(시장 대비)으로 재면 순위가 뒤집힌다** — 시장 공통 성분이 빠져 종목 선택 효과가 사라진다.
  돈 판정은 **절대 수익**으로, IC는 순위 기반이라 스케일 오염에 면역이므로 두 지표를 함께 쓴다.
  두 지표가 크게 어긋나면(IC는 높은데 순수익이 마이너스) 데이터 오염을 먼저 의심한다.

도구는 `scripts/signal_registry.py` 처럼 스스로 판정을 내리고 `data/reports/signal_registry.json/md`
를 남기는 형태로 만들고, 크론은 주 1회(장 마감 후)로 건다. 매번 판정이 바뀐 피처만 diff 로 보고하면
"죽은 피처 부활" 작업과 "돈 되는 피처" 판정을 같은 표에서 추적할 수 있다.

## 3. 재빌드는 비용을 먼저 계산하고 단계로 나눈다

피처 계산은 대개 (종목, 날짜) 페어 단위이고 처리량이 낮다. 실측 **0.368 페어/초** → 200종목×279일
= 54,800페어 ≈ **41시간**. "오늘 안에 재빌드해서 확인"은 불가능하다.

1. **스모크**: 8종목 × 60일 (수 분) — 배선·스키마만 검증.
   실험 목적이면 **기존 패널 npz 를 로드해 WF 만 돌린다**(수 분). `FeaturePipeline.build_features` 는
   (종목,날짜) 페어당 2.6~3.3개/초라 6만 페어면 ETA 5시간이 넘는다 — 빠른 AUC 비교에 쓰면 안 된다.
   컨테이너 마운트는 `services/xgboost-ml → /app` 이므로 코드는 `/app/app/...`, 패널은 `/app/app/models/wf/` 다.
2. **부분 빌드**: 50종목 × 소스가 실제로 존재하는 구간(≈6시간) — 밤새 완주 가능. 이 단계로도
   "죽은 피처가 소스 공백 때문인지"는 판정된다.
3. 전체 빌드는 2단계 결과를 보고 승인받아 주말 단위로.

- **패널을 읽거나 쓰는 패치 스크립트는 호스트에서 돌려라 — 컨테이너에는 `/app/data` 가 없다.**
  마운트는 `services/xgboost-ml → /app` 이라 `/app/scripts` 는 보이지만 `data/panels/*.npz` 는 없다(실측 `FileNotFoundError`).
  호스트 실행 시 접속 기본값이 컨테이너용(`postgres:5432`)이면 실패하므로 `POSTGRES_HOST=127.0.0.1 POSTGRES_PORT=5434` 를
  명시해 돌린다. 반대로 컨테이너 안에서만 가능한 것(앱 파이프라인 호출·writer)은 패널을 `docker cp` 로
  `/app/app/models/wf/` 에 넣고 그 경로를 `--panel` 로 넘긴다.
- **기준선 패널을 덮어쓰지 마라.** 항상 새 파일명 + sidecar(`days`·`end_date`·`universe`·`seed`·`rows`·
  `dates`·`codes_sha1`)로 빌드 조건을 남긴다. 대조군이 사라지면 재빌드 효과를 비교할 수 없다.
- 빌더 로직을 복제하지 말고 기존 빌드 함수를 **import** 한다(정의가 갈라지면 비교가 무의미해진다).
- 빌더에 `--end-date` 같은 구간 고정 인자가 있으면 반드시 준다 — 구간이 '실행 시각' 기준이면
  구간이 '실행 시각' 기준이면 체크포인트가 매일 무효화되어 영원히 완주하지 못한다.
- 피처 기반 A/B는 **컬럼 패치로 한다**: 기존 패널의 X 를 읽어 새 컬럼만 append 하고 `feature_names` 를 늘려
  새 파일로 저장한다(다른 컬럼은 비트 동일 assert). 전체 재빌드 없이 같은 행·같은 피처 위에서 델타가 나오고,
  41시간이 몇 초로 줄어든다. 라벨·타깃·행 집합이 바뀔 때만 전량 재빌드한다.
- **`prod` 처럼 “최근 데이터순 상위 N” 으로 유니버스를 뽑는 패널은 빌드마다 종목이 바뀐다**(실측 두 버전
  교집합 23/200). 그 상태의 두 패널 AUC 비교는 전략 비교가 아니라 유니버스 비교다 → A/B 전에 `codes_sha1`
  을 대조하고, 다르면 `--codes-file` 로 종목을 고정해 재빌드하거나 “종목 교체 포함”을 보고에 명시한다.
- **패치 직후 확인은 AUC 가 아니다**: ① 새 컬럼의 구간별 non-null 비율(6개월 버킷) ② 전체 생존 재판정(alive/dead)
  ③ 같은 WF 에서 대조군과 **fold-level 값이 동일한지** — 동일하면 그 피처가 선별/학습에 안 들어간 것이고,
  그건 “효과 0” 이 아니라 “측정 불가”다. 데이터가 있는 구간으로 슬라이스해 다시 재라(초기 폴드가
  커버 공백이면 선별에서 탈락해 세 패널이 비트 동일하게 나온다).
- **선별 문턱을 실행 전에 계산하라**: 부활 피처가 top-K 선별에 들 수 있는지, 경계값과 그 피처의 순위를
  같은 표로 낸다(실측 경계 |IC| 0.054 = 30위, 부활 3개는 54·71·122위). 경계 밖이면 WF 를 돌려도 결과는
  비트 동일하게 나온다 — 한 시간짜리 실행 전에 알 수 있는 사실이다.
- **선별 폭 확대는 피처 기여와 다른 레버다**: K 만 바꾼 A/B(top30→top60)로 “선별 폭” 효과를 재고,
  그 다음 **K 를 고정한 채 원본 vs 패치 패널**을 비교해야 피처 귀속이 된다. K 확대에서 오른 AUC 를
  부활 피처 덕으로 보고하면 오귀속이다(실측: K 확대 +0.0156 — 그런데 같은 K 에서 피처 귀속은 0.0000).
- **기여 0 이 측정으로 확정되면 그 축은 닫는다**: alive 개수 증가와 모델 기여는 별개다. 보고에
  “alive N개 증가 / AUC 기여 0(측정)”을 함께 쓰고, 다음 레버(선별 폭·비용·정의 변경)로 넘어간다.
  축을 닫지 않으면 같은 부활 작업을 다른 원천으로 반복하며 시간을 쓴다.
- 선별 폭 비교는 기존 WF 스크립트의 `CONFIGS` 를 monkeypatch 하는 **얇은 래퍼**로 만든다(패널·폴드·시드
  고정, `select` 만 교체). WF 본체가 `main()` 에서 argv 없이 `sys.argv` 를 직접 읽으면 래퍼에서 인자를
  넘기지 말고 그대로 호출해야 한다(`TypeError: main() takes 0 positional arguments`).
- 희박 이벤트 피처를 레벨·추세·묶음으로 재정의하는 검증된 레시피는
  `references/sparse-event-redefinition.md` 참고(실측: 신규 8개 중 7개 ALIVE).
- 이 단계에서 피처를 더 파기 전에 **문제 정의(라벨 지평·유니버스)가 보유시간과 맞는지** 먼저 확인한다 —
  지평 교체가 피처 부활보다 훨씬 큰 AUC 이동을 만든다(실측 h5→h1 +0.0312 vs 피처 +0.0000).
  절차는 `backtest-measurement-validity` §4d.

## 4. 피처 파이프라인 지연을 줄일 때 (측정 → 변경 → 동일성 확인)

실측 예: 스크리너 1회 8.17초 → 2.65초.

- **top-N-per-group 은 윈도우 함수가 아니라 LATERAL**: 전체 테이블(수백만 행)에
  `ROW_NUMBER() OVER (PARTITION BY code ORDER BY date DESC)` 를 걸면 3.68초,
  `CROSS JOIN LATERAL (… ORDER BY date DESC LIMIT n)` 는 (code, date) 인덱스만 타서 0.31초.
  조회 대상 코드 배열을 함께 넘겨 범위를 좁힌다.
- **비싼 계산 앞에 싼 필터를 둔다**: 칼만/모델 입력을 만들기 전에 유동성·가격·거래량을 **종목별 마지막 행**으로
  먼저 걸러 대상 수를 줄인다(실측 1,858→669, 2.4→0.9초). 사후 필터는 그대로 두어 계약을 보존한다.
- **모델 예측은 배치 1회**: 행마다 `predict(1×F)` 를 N번 부르지 말고 특징행렬을 만들어 1회 호출,
  shape 불일치·예외 시에만 행별 폴백.
- **최적화의 완료 조건은 '후보 목록·점수가 비트 동일'** 이다. 전후 산출물을 파일로 대조해 보고하라 —
  점수가 움직였으면 그건 최적화가 아니라 로직 변경이다.
- **병목을 추정하지 말고 구간별로 먼저 재라**: 함수 전체 시간만 보고 '정규식이 느리다' 고 단정하면
  캐시를 붙여도 이득이 0 이다(실측: 4,354종목×20패턴 매칭이 전부인 줄 알고 이름→테마 캐시 테이블을
  붙였으나 웜 1.75s vs 기준 1.72s, 병목은 DB 왕복이었다). 구간(`build_map`/`build_daily`)을 따로 재서
  큰 쪽부터 손대고, 이득이 측정되지 않으면 코드·새 테이블까지 되돌린다.
- **"컬럼 N개 × 집계 M종" 루프는 한 번의 집계 쿼리로 접어라 — 왕복 횟수가 병목인 경우가 대부분이다.**
  실측: 피처 빌더 88.6초 중 85초(96%)가 `feature_coverage` 재계산의 72회 왕복(24컬럼×nz·std/종목별/날짜별)이었고,
  격자 bisect 루프는 1초였다. `count(*) FILTER (WHERE c <> 0), stddev_pop(c)` 를 한 쿼리로,
  `count(DISTINCT c) … GROUP BY stock_code` / `GROUP BY trade_date` 를 각 1회로 합쳐 **102s → 15.7s (6.5배),
  변경 15줄**. 집계 함수를 바꿀 때(`percentile_cont(0.5)` → `statistics.median`)는 **행 수 + 컬럼별 합계**를
  체크섬으로 미리 박고 전후 대조한다(리팩터 위임 브리프에 숫자로 적어 준다).
- **DELETE+COPY 배치는 dead tuple 로 autovacuum 을 스스로 유발해 실행시간이 튄다**(실측: 회당 48,718 dead tuple
  이 임계 48,072 를 살짝 넘어 16초 ↔ 29~36초 변동). 최적화 後에도 변동이 남으면 "코드 문제가 아니라 vacuum"
  이라고 보고하고, 필요하면 TRUNCATE/파티션 교체로 바꾼다.
- **정규식 통합(alternation `(?P<t0>..)|(?P<t1>..)`)은 의미를 바꿀 수 있다**: 한 위치에서 첫 매칭이
  소비되면 겹치는 패턴이 같은 문자열에 못 걸린다(실측 매핑 1,645 → 1,629). 빠르지도 않았다 — 남은
  성능 문제를 정규식으로 풀기 전에 결과 동치(행 수·해시)를 먼저 확인한다.

## 5. 재빌드 · 백필 러너의 침묵 실패

- **ML 컨테이너에서 임시 파이썬을 돌릴 때 `docker exec ... python - <<EOF` 는 출력이 사라진다** — 테스트
  스크립트를 파일로 쓰고 `docker exec -w /app -e PYTHONPATH=/app -e PGPASSWORD=... stock_xgboost_ml python
  /app/tests/_check_x.py` 로 돌린다. `PYTHONPATH` 없으면 `ModuleNotFoundError: No module named 'app'` 이다.
  컨테이너에는 pytest 가 없는 경우가 많아, 검증은 단언을 담은 스크립트의 stdout 으로 한다.
  마운트는 `services/xgboost-ml → /app` 이므로 코드는 `/app/app/...`, 패널은 `/app/app/models/wf/` 이다
  (`/app/models` 는 다른 경로다 — 헛짚으면 No such file 이다).

- **백필 러너의 '기본 대상'이 신호 종목이면 신호 없는 날은 조용히 0행이다**: 실측 `codes=0, rows_written=0,
  rc=0` — 성공처럼 보이는 무동작. 당일 피드·저널 코드를 `--codes-file` 로 명시해야 한다.
- 그런 러너는 `--from < --to` 를 **엄격**히 요구하는 경우가 있다(동일 날짜 두 개는 거부) → `--to` 를 다음날로.
- 크론에 넣을 때는 날짜 `%` 를 `\%F` 로 이스케이프하고, 등록 후 **크론과 같은 셸 명령을 직접 한 번 실행**해
  인자 전개를 확인한다(인자 누락은 로그가 비어 있는 것으로만 드러난다).
- **진행(체크포인트) 파일 경로를 하드코딩하면 사본·다른 홈에서 절반이 조용히 실패한다**: 진행파일이
  다른 홈(`/home/<다른 사용자>/...`)을 가리키면 쓰기가 `PermissionError` 로 거부되고, 러너는 그 항목만
  건너뛴 뒤 마지막에 `완료: ok=N fail=N` 같은 요약을 찍어 성공처럼 보인다(실측 500호출 중 250 실패).
  경로는 `PROJ_DIR`/cwd 기준으로 해석하고, 크론 점검은 요약줄이 아니라 ① 진행파일 mtime 이 전진했는지
  ② 항목별 실패 줄의 **예외 클래스**가 무엇인지로 한다.

## 6. 이벤트·공시 피처가 0 일 때

- **정규식 앞에서 대괄호 접두어를 떼라**: `[기재정정]주주총회소집결의` 처럼 접두 태그가 붙으면 키워드
  매칭이 전부 빗나가 미매칭으로 빠진다(`re.sub(r"^\[[^\]]{1,20}\]\s*", "", name)` 후 매칭).
- 매칭률을 **분류기 밖에서** 재라: 상위 공시명을 뽑아 기존 패턴으로 걸러 보고 미매칭 상위 30개를 눈으로
  읽으면 사전에 없는 유형이 바로 보인다(실측 미매칭 5,757/24,270).
- 유형을 추가하면 **스키마도 늘어난다**: 적재가 `COPY event_features (stock_code, trade_date, <COLS>)`
  처럼 컬럼을 명시하면 새 유형은 INSERT 전에 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 가 필요하다.
- 접두어 제거 + 9유형 추가로 매칭률 89.8%까지 올랐고(생성 행 11,154 → 48,665), 새 유형은 커버리지
  게이트가 자동으로 집계한다. 단, **DB에 쌓였다고 모델이 쓰는 것은 아니다** — 피처 계약(이름 목록)에
  넣는 것은 별도 변경이고 WF 실험으로 기여도를 확인해야 한다.
- **키워드가 '희박'인지 '원천에 없음'인지 원문에서 먼저 세라**: 파이프라인을 고치기 전에
  `select count(*) from disclosures where report_nm ~ '<패턴>' and rcept_dt >= current_date - 60` 으로
  최근 원문 적중 수를 확인한다. 실측 제휴/MOU 1건 · 리콜 0건 · 특허 8건(전체 227,590건) → 0.05% 미만은
  수집 결함이 아니라 **국내 공시 용어 자체가 다르다**(경영사항·투자판단관련주요경영사항으로 나간다).
- **이벤트가 두 계통으로 수집되면 한쪽만 피처로 배선되어 있을 수 있다**: DART 기반 `event_features` 와
  뉴스 클러스터(`news_events.event_type`)가 별도로 존재하고, 뉴스 쪽에 파트너십 588 · 규제 1,096 ·
  신제품 1,049 · 유동성 502건이 있어도 피처로 안 들어가면 그 축은 죽은 것이 아니라 **미배선**이다.
  죽은 이벤트 피처를 만나면 두 테이블의 최근 건수를 나란히 세고, 새 수집기를 붙이기 전에 원천이 있는
  쪽을 배선하는 것을 먼저 검토한다.
- **그래프(Neo4j) 의존 피처는 적재 상태를 먼저 본다**: `graph_features` 가 만드는 `sector_count`·`theme_*`
  는 관계가 없으면 0 이고, 컨테이너 로그에 `UnknownRelationshipType FOLLOWS_CYCLE` 같은 경고가 찍힌다.
  이 경고는 피처 코드 버그가 아니라 그래프 적재 누락 신호다.
- **파생 집계 테이블의 최신 날짜를 함께 본다**: `theme_daily` 처럼 손으로 한 번 만든 집계는 크론이 없으면
  조용히 며칠씩 낡는다(실측 760행·최신 2일 전). 피처가 0 인 이유가 '당일 행이 없다'일 수 있다.
- **그 집계가 '크론이 도는데도 낡은' 경우는 스크립트의 접속 설정을 의심하라.** 실측: 테마 빌더가 ① `.env` 를 읽지 않아
  크론에서 `no password supplied` ② 셸에서 `.env` 를 source 해 돌리면 통과해 원인이 가려짐 ③ `.env` 의 컨테이너용
  `POSTGRES_PORT=5432` 를 그대로 써서 호스트에서 접속 타임아웃 — 세 조건이 겹쳐 매일 18:50 실패했다.
  수리는 `_load_env()`(파일 파싱 + `setdefault`) + 호스트 보정(`postgres→127.0.0.1`, `5432→5434`)이고,
  검증은 **아무 env 도 export 하지 않은 새 셸에서 인자 없이 실행**해 행수가 늘어나는지로 한다.
  집계 최신일이 밀릴 때 '피처 코드'를 고치기 전에 빌더 로그의 마지막 줄을 먼저 확인하라.

## 7. 보고

- 죽은 피처 수는 **결과**다. 원인 분해표(0-채움 / 희박 / 원천부재 / 커버리지부족 / 수집기없음)를
  개수와 함께 내고, 각 분류에 처방과 예상 난이도를 붙인다.
- "재빌드하면 살아난다"고 말하려면 2단계 부분 빌드의 실측을 근거로 대라. 근거 없는 약속은 하지 않는다.
- 부분 빌드는 **같은 유니버스 규칙**으로 만들어야 비교된다(종목 수·선정 규칙을 명시).
