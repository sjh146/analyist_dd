# 피처 패널 진단 · 재빌드

학습 패널(종목×날짜×피처)에서 "죽은 피처"를 만났을 때, ① 왜 죽었는지 분해하고 ② 다시 만들기 전에
비용을 계산하고 ③ 재빌드 후 같은 기준으로 재판정하는 절차. 판정은 항상 **개수가 아니라 원인 분류**로 한다.

## 1. 죽었는지부터 두 축으로 나눈다

생존 리포트의 두 값을 **함께** 읽어라:

- `null_ratio 0.0` 인데 `std 0.0` → **결측을 0으로 덮은 것**이다. "측정된 0"이 아니다.
  모델은 "정보 없음"과 "실제 0"을 구분하지 못하고, 분산 0이라 트리 분기도 못 한다.
- `nnz < 5%` 정도로 희박 → 죽은 게 아니라 **드문 것**이다(이벤트류). 임계 설계 문제이지 데이터 결함이 아니다.
- `null_ratio` 높음 → 원천이 없거나 조인이 빗나간 것. 커버리지 축으로 넘어간다.

처방이 갈린다: 0-채움 → **결측은 NaN 유지 + 결측 지시자(missing indicator) 피처** 추가. 희박 → 누적 카운트·
EWMA·타깃 인코딩으로 재정의. 원천 결손 → 수집·조인 수리.

## 2. 커버리지는 '테이블 전체'가 아니라 '패널 코드 집합 × 패널 기간'으로 센다

테이블 행수는 착시다. 반드시 패널의 `codes`·`dates` 로 다시 조회한다:

```sql
SELECT count(*), count(DISTINCT stock_code)
FROM <source> WHERE stock_code = ANY(%s) AND <date_col> BETWEEN %s AND %s;
```

실측 사례: 뉴스 테이블 12,817행이 살아 있는데 패널 200종목 중 27종목, 패널 기간 내로 좁히면 **4종목**.
SNS 29/200 · 수급 92/200 처럼 소스별 커버리지가 제각각이면, 피처가 0인 이유는 모델이 아니라 **조인 대상**이다.

- **소스 시계와 패널 시계를 대조하라.** 소스 시작일이 패널 시작일보다 늦으면 그 구간은 구조적으로 0이다
  (실측: 패널 2025-08~2026-09 인데 뉴스 2026-04~, SNS 피처 2026-09-23~, 감성 2026-11-15~).
  "이 피처는 무정보"라는 과거 결론이 **그 당시 소스가 없었기 때문**일 수 있다.
- **수집이 '기사/게시글 등장 종목' 기준인지 유니버스 기준인지 확인하라.** 전자면 조용한 종목은
  영원히 0이다 — 리더를 고쳐도 유니버스를 넓히기 전엔 안 살아난다.
- **죽은 컬럼과 살아 있는 원천 테이블을 구분하라.** 컬럼 기준 종결은 원천이 자라면 뒤집힌다 —
  닫힌 축은 분기마다 `pg_stat_user_tables` 행수·기간으로 재확인한다.

## 3. 재빌드는 비용을 먼저 계산하고 단계로 나눈다

피처 계산은 대개 (종목, 날짜) 페어 단위이고 처리량이 낮다. 실측 **0.368 페어/초** → 200종목×279일
= 54,800페어 ≈ **41시간**. "오늘 안에 재빌드해서 확인"은 불가능하다.

1. **스모크**: 8종목 × 60일 (수 분) — 배선·스키마만 검증.
2. **부분 빌드**: 50종목 × 소스가 실제로 존재하는 구간(≈6시간) — 밤새 완주 가능. 이 단계로도
   "죽은 피처가 소스 공백 때문인지"는 판정된다.
3. 전체 빌드는 2단계 결과를 보고 승인받아 주말 단위로.

- **기준선 패널을 덮어쓰지 마라.** 항상 새 파일명 + sidecar(`days`·`end_date`·`universe`·`seed`·`rows`·
  `dates`·`codes_sha1`)로 빌드 조건을 남긴다. 대조군이 사라지면 재빌드 효과를 비교할 수 없다.
- 빌더 로직을 복제하지 말고 기존 빌드 함수를 **import** 한다(정의가 갈라지면 비교가 무의미해진다).
- 빌더에 `--end-date` 같은 구간 고정 인자가 있으면 반드시 준다 — 구간이 '실행 시각' 기준이면
  구간이 '실행 시각' 기준이면 체크포인트가 매일 무효화되어 영원히 완주하지 못한다.
- 피처 기반 A/B는 **컬럼 패치로 한다**: 기존 패널의 X 를 읽어 새 컬럼만 append 하고 `feature_names` 를 늘려
  새 파일로 저장한다(다른 컬럼은 비트 동일 assert). 전체 재빌드 없이 같은 행·같은 피처 위에서 델타가 나오고,
  41시간이 몇 초로 줄어든다. 라벨·타깃·행 집합이 바뀔 때만 전량 재빌드한다.
- **`prod` 처럼 “최근 데이터순 상위 N” 으로 유니버스를 뽑는 패널은 빌드마다 종목이 바뀐다**(실측 두 버전
  교집합 23/200). 그 상태의 두 패널 AUC 비교는 전략 비교가 아니라 유니버스 비교다 → A/B 전에 `codes_sha1`
  을 대조하고, 다르면 `--codes-file` 로 종목을 고정해 재빌드하거나 “종목 교체 포함”을 보고에 명시한다.
- **패치 직후 확인은 AUC 가 아니다**: ① 새 컬럼의 구간별 non-null 비율(6개월 버킷) ② 전체 생존 재판정(alive/dead)
  ③ 같은 WF 에서 대조군과 **fold-level 값이 동일한지** — 동일하면 그 피처가 선별/학습에 안 들어간 것이고,
  그건 “효과 0” 이 아니라 “측정 불가”다. 데이터가 있는 구간으로 슬라이스해 다시 재라(초기 폴드가
  커버 공백이면 선별에서 탈락해 세 패널이 비트 동일하게 나온다).
- **선별 문턱을 실행 전에 계산하라**: 부활 피처가 top-K 선별에 들 수 있는지, 경계값과 그 피처의 순위를
  같은 표로 낸다(실측 경계 |IC| 0.054 = 30위, 부활 3개는 54·71·122위). 경계 밖이면 WF 를 돌려도 결과는
  비트 동일하게 나온다 — 한 시간짜리 실행 전에 알 수 있는 사실이다.
- **선별 폭 확대는 피처 기여와 다른 레버다**: K 만 바꾼 A/B(top30→top60)로 “선별 폭” 효과를 재고,
  그 다음 **K 를 고정한 채 원본 vs 패치 패널**을 비교해야 피처 귀속이 된다. K 확대에서 오른 AUC 를
  부활 피처 덕으로 보고하면 오귀속이다(실측: K 확대 +0.0156 — 그런데 같은 K 에서 피처 귀속은 0.0000).
- **기여 0 이 측정으로 확정되면 그 축은 닫는다**: alive 개수 증가와 모델 기여는 별개다. 보고에
  “alive N개 증가 / AUC 기여 0(측정)”을 함께 쓰고, 다음 레버(선별 폭·비용·정의 변경)로 넘어간다.
  축을 닫지 않으면 같은 부활 작업을 다른 원천으로 반복하며 시간을 쓴다.
- 선별 폭 비교는 기존 WF 스크립트의 `CONFIGS` 를 monkeypatch 하는 **얇은 래퍼**로 만든다(패널·폴드·시드
  고정, `select` 만 교체). WF 본체가 `main()` 에서 argv 없이 `sys.argv` 를 직접 읽으면 래퍼에서 인자를
  넘기지 말고 그대로 호출해야 한다(`TypeError: main() takes 0 positional arguments`).
- 희박 이벤트 피처를 레벨·추세·묶음으로 재정의하는 검증된 레시피는
  `references/sparse-event-redefinition.md` 참고(실측: 신규 8개 중 7개 ALIVE).
- 이 단계에서 피처를 더 파기 전에 **문제 정의(라벨 지평·유니버스)가 보유시간과 맞는지** 먼저 확인한다 —
  지평 교체가 피처 부활보다 훨씬 큰 AUC 이동을 만든다(실측 h5→h1 +0.0312 vs 피처 +0.0000).
  절차는 `backtest-measurement-validity` §4d.

## 4. 피처 파이프라인 지연을 줄일 때 (측정 → 변경 → 동일성 확인)

실측 예: 스크리너 1회 8.17초 → 2.65초.

- **top-N-per-group 은 윈도우 함수가 아니라 LATERAL**: 전체 테이블(수백만 행)에
  `ROW_NUMBER() OVER (PARTITION BY code ORDER BY date DESC)` 를 걸면 3.68초,
  `CROSS JOIN LATERAL (… ORDER BY date DESC LIMIT n)` 는 (code, date) 인덱스만 타서 0.31초.
  조회 대상 코드 배열을 함께 넘겨 범위를 좁힌다.
- **비싼 계산 앞에 싼 필터를 둔다**: 칼만/모델 입력을 만들기 전에 유동성·가격·거래량을 **종목별 마지막 행**으로
  먼저 걸러 대상 수를 줄인다(실측 1,858→669, 2.4→0.9초). 사후 필터는 그대로 두어 계약을 보존한다.
- **모델 예측은 배치 1회**: 행마다 `predict(1×F)` 를 N번 부르지 말고 특징행렬을 만들어 1회 호출,
  shape 불일치·예외 시에만 행별 폴백.
- **최적화의 완료 조건은 '후보 목록·점수가 비트 동일'** 이다. 전후 산출물을 파일로 대조해 보고하라 —
  점수가 움직였으면 그건 최적화가 아니라 로직 변경이다.

## 5. 재빌드 · 백필 러너의 침묵 실패

- **백필 러너의 '기본 대상'이 신호 종목이면 신호 없는 날은 조용히 0행이다**: 실측 `codes=0, rows_written=0,
  rc=0` — 성공처럼 보이는 무동작. 당일 피드·저널 코드를 `--codes-file` 로 명시해야 한다.
- 그런 러너는 `--from < --to` 를 **엄격**히 요구하는 경우가 있다(동일 날짜 두 개는 거부) → `--to` 를 다음날로.
- 크론에 넣을 때는 날짜 `%` 를 `\%F` 로 이스케이프하고, 등록 후 **크론과 같은 셸 명령을 직접 한 번 실행**해
  인자 전개를 확인한다(인자 누락은 로그가 비어 있는 것으로만 드러난다).
- **진행(체크포인트) 파일 경로를 하드코딩하면 사본·다른 홈에서 절반이 조용히 실패한다**: 진행파일이
  다른 홈(`/home/<다른 사용자>/...`)을 가리키면 쓰기가 `PermissionError` 로 거부되고, 러너는 그 항목만
  건너뛴 뒤 마지막에 `완료: ok=N fail=N` 같은 요약을 찍어 성공처럼 보인다(실측 500호출 중 250 실패).
  경로는 `PROJ_DIR`/cwd 기준으로 해석하고, 크론 점검은 요약줄이 아니라 ① 진행파일 mtime 이 전진했는지
  ② 항목별 실패 줄의 **예외 클래스**가 무엇인지로 한다.

## 6. 보고

- 죽은 피처 수는 **결과**다. 원인 분해표(0-채움 / 희박 / 원천부재 / 커버리지부족 / 수집기없음)를
  개수와 함께 내고, 각 분류에 처방과 예상 난이도를 붙인다.
- "재빌드하면 살아난다"고 말하려면 2단계 부분 빌드의 실측을 근거로 대라. 근거 없는 약속은 하지 않는다.
- 부분 빌드는 **같은 유니버스 규칙**으로 만들어야 비교된다(종목 수·선정 규칙을 명시).
