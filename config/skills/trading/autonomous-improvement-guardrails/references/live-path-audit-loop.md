# 라이브 경로 감사 루프 (읽기) + 일일 개선 큐 (쓰기 입구)

trading/주문 경로처럼 **실돈이 흘러가는 경로의 개선을 무한 반복**할 때의 구조.
핵심 분리: 감사는 **읽기 전용**으로 5분마다 자동, 수정은 **큐를 거쳐** 사람(또는 다음 세션)이 판단.
감사 경로에 격리(worktree) 비용을 쓰지 않고, 쓰기 경로는 `SKILL.md`의 절차(격리·검증·되돌리기)를
그대로 따른다.

## 1. 감사 스크립트가 갖춰야 할 것 (읽기 전용)

- **소비자와 같은 출처를 본다**: 브로커 API(`/positions`, `/orders`, `/quotes`), 소비자가 폴링하는
  HTTP 피드, 그리고 로컬 저널. "설정 파일을 읽었다"는 증거가 아니다.
- **저널은 복사본으로 읽는다**: WAL 모드 sqlite 를 다른 OS/프로세스에서 직접 열면 `disk I/O error` 가
  나고, 이는 손상으로 오독된다. `<db>`, `<db>-wal`, `<db>-shm` 세 개를 임시 디렉터리로 복사한 뒤 쿼리한다.
- **결과는 두 파일로**: 최신 스냅샷 1개(`*_latest.json` — 덮어쓰기, 사람이 바로 읽음) + 발견 누적
  `*_findings.jsonl`(append). 누적본은 **지문(kind+detail 의 sha256 앞자리)** 으로 중복 제거해, 같은
  위반이 5분마다 100줄 쌓이지 않게 한다.
- **종료코드로 판정을 말한다**: 0 정상 / 1 위반 있음 / 2 판정 불가(브로커·피드 읽기 실패). 크론 로그에서
  "조용한 0"(아무 것도 못 읽었는데 정상처럼 보임)을 구분하기 위한 장치다.

## 2. 실주문 경로에서 실제로 잡히는 불변식

각 항목은 "전략이 나쁜 것처럼 보이지만 실제로는 실행 경로 결함"인 것들이다.

| 종류 | 판정 | 왜 이게 돈을 잃는가 |
|---|---|---|
| `broker_without_journal` | 브로커 보유 ∖ 저널 미청산 | 손절·익절 관리자가 없는 포지션 |
| `journal_without_broker` | 저널 미청산 ∖ 브로커 보유 | 유령 포지션이 슬롯을 먹고 매도 주문을 낸다 |
| `stop_not_fired` | 현재가 ≤ 진입가×(1−stop_pct) 인데 미청산 | 손절이 안 걸린 채 손실이 커진다 |
| `unfilled_order_open` | `/orders` 에 `filled_qty=0` 이 N초 이상 | 나중에 유리하지 않은 가격에 체결된다 |
| `thin_liquidity_candidate` | 피드 후보의 거래대금 < 하한 | 체결이 밀려 슬리피지가 전략 손익을 지배한다 |
| `feed_missing_trading_value` | 후보에 유동성 필드 자체가 없음 | 유동성 게이트가 **조용히 무력** |

**필드 부재와 값 미달은 다른 사건이다.** 유동성 필드가 피드에 없는데 `0` 으로 채워 읽으면 20건 전부가
"유동성 미달"로 오탐되고, 진짜 문제(피드 계약 누락)가 가려진다. 필드가 없으면 `*_missing_*`(medium)로,
값이 하한 미만이면 `*_candidate`(high)로 분리해 기록하고, 피드 발행 단계에서 그 필드를 싣도록 고친다.

## 3. 크론 형태 (시장 시간만)

    */5 9-15 * * 1-5  cd <repo> && python3 scripts/<x>_audit.py >> reports/cron_<x>_audit.log 2>&1
    30 16 * * 1-5     <repo>/cron/<x>_improve.sh >> reports/cron_<x>_improve.log 2>&1

개선 스크립트는 코드를 고치지 않는다. 당일 발견을 모아 큐(`reports/<x>_improve_queue_YYYYMMDD.md`)로
쓰고, 규칙 세 줄을 함께 박는다: ① 위반은 재현 수치·스크립트와 함께 고친다 ② 실주문 경로 변경은 테스트 +
**장중 실측 검증**까지 통과해야 종료 ③ 커밋 1건당 수정 1개 + 되돌리기 sha 기록.

## 4. 루프를 닫는 방법

- 감사가 낸 위반은 **그 자체로 실험 설계가 아니다**. 수정 전에 재현 실행(스크립트 1회 실행 + 해당 로그
  라인)으로 확인하고, 수정 후에는 같은 감사를 다시 돌려 그 kind 가 사라졌는지 수치로 확인한다.
- 감사 결과가 계속 "OK" 인데 손익이 나빠지면 **감사가 측정하지 않는 축**이 있다는 뜻이다(예: 진입가 대비
  슬리피지, 체결 지연). 그때는 지표를 손익 쪽으로 넓히지 말고, 누락된 지표를 감사에 **새 불변식으로 추가**한 뒤
  그 지표로 다시 판정한다.
- 큐가 비어도 끝난 것이 아니다: 다음 개선 후보는 레지스트리/실측(어느 신호가 비용을 넘는가)에서 나온다.
