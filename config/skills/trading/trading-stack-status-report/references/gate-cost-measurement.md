# 게이트 비용 측정 — 막힌 경로가 방어인가 손실인가

쓰임: 사용자가 "장이 이렇게 좋았는데 왜 한 건도 안 샀나" 류로 물을 때, 또는 게이트/문턱을
완화하는 변경을 검토하기 전. **문턱을 만지기 전에 차단된 집단의 실측 기대값을 낸다.**

## 0. 체결 가능성(fillability) 필터를 먼저 적용한다 — 빼면 부호가 뒤집힌다

막힌 집단의 평균이 플러스라고 해서 "게이트가 돈을 막고 있다"로 넘어가면 틀린다. close 후보의 상위권은
**그날 이미 +25~30% 오른(상한가 부근) 종목**이고 그 종목들은 매도 물량이 없어 종가에 **살 수 없다**. 실측(87세션·1,736후보,
수수료 왕복 0.21%p 반영, 세션 단위 집계): 원시(gross) +5.23%/세션(t=+8.8) → 상한가 근처(당일등락 ≥+25%, 396건)
제외 시 **−0.67%/세션(t=−2.8)**. 같은 필터에서 HEAT 해제도 −0.52%, 각 버킷의 부호가 전부 뒤집혔다.

- 선택 룰 자체를 먼저 본다: 세션별 score 상위 3픽(n=261)의 당일등락 **중앙 +29.91%**(≥+25%가 82.4%),
  살 수 있는 46픽만 보면 gross −1.19% / net −1.40% — 스코어가 '오늘 많이 오른 종목'의 대리변수다.
- 따라서 **거래 가능 유니버스 안에서 재선별**하는 것이 먼저이고, 게이트 완화는 그 뒤에도 양(+)일 때만 검토한다.
- 필터는 한 값이 아니라 **사다리**로 보고한다(당일등락 <+25/<+20/<+15%, 거래대금 하한): 효과가 단조면 필터를
  고른 게 아니라 구조를 찾은 것이다. 도구: `scripts/close_gate_expectancy.py --max-day-chg 25 --topk 3`.
- 행(row) 단위 평균으로 결론내지 않는다 — 한 세션이 수십 행을 넣어 n 을 ~20배 부풀린다. **세션 평균 → 세션들에 대해
  평균·중앙·양(+)세션 비율·t** 순서로 계산하고, 창을 반으로 쪼개 양쪽이 모두 양(+)인지까지 본다.

## 절차

1. **후보를 그날 데이터로 재생성한다** — 발행본은 보관되지 않는다(`data/feed/screener_latest.json`
   최신본만 남는다). 종가스크리너는 기준일 인자가 있다:

   ```bash
   cd /home/jhshi/analyist_dd
   python3 scripts/close_screener.py --date YYYY-MM-DD --top-n 20 \
       --output <dir>/close_candidates_YYYYMMDD_000000.csv
   ```

   여러 날을 한 번에(재생성 루프 + 집계 + 게이트별 분해) 돌리는 프로브가 레포에 있다:

   ```bash
   set -a; . ./.env; set +a; export POSTGRES_HOST=127.0.0.1 POSTGRES_PORT=5434
   /usr/bin/python3 scripts/_close_gate_backtest.py --days 120 --out-dir data/reports/close_gate_probe
   #  → summary.json(집단별 통계) · days.csv(일자별 게이트 통과·평균) · trades.csv(건별 수익률)
   ```
   거래일당 수십 초(스크리너 전 종목 재계산)라 3개월 창은 30~45분 — 백그라운드로 돌린다.

2. **게이트 판정과 같은 집계로 부분집합을 가른다.** close 는 상위 10개 평균 기준
   (`analyist_dd/runner/config.py`): R1 `r1_min_avg_score["close"]`=88.0 · HEAT `r1_max_avg_pct`=15.0,
   상위 N 은 `r1_top_n`=10. 후보별 값이 아니라 **상위 N 평균**으로 판정해야 트레이더와 같은 계산이다.

3. **수익률 정의를 트레이더 프로파일과 맞춘다** (`trader_core/profiles.py`): close = 발굴일 종가 매수 →
   **다음 거래일 시가** 매도(`exit_mode=next_open`). 스크리너 문서의 "종가 매수 → 익일 매도" 를 그대로 쓰면
   다른 전략을 재는 것이 된다.

4. **사유별로 나눠 보고한다**: `r1_fail_heat_ok` · `r1_ok_heat_fail` · `both_fail` + 게이트가 열린 날/닫힌 날.

## 어느 숫자가 기회비용인가 (혼동하면 보고가 틀린다)

- 차단 **당일**의 등락은 우리 몫이 아니다 — close 프로파일은 그날 **종가 동시호가 직전**에 사므로, 이미 일어난
  상승은 진입가에 반영돼 있다(그 열이 HEAT 를 걸리게 한 값이다). 당일 등락을 기회비용으로 인용하면 아쉬움을 과장한다.
  보고에는 두 숫자를 **나눠** 쓰고 각각이 무엇인지 라벨을 붙인다: "차단 당일 등락(우리 몫 아님)" vs "다음 세션 시가 갭(실제 손익 형태)".
- 판정 지표는 **다음 세션 시가 갭**(종가 매수 → 다음 거래일 09:00-09:10 시가 매도, `exit_mode=next_open`) 하나다.
  1세션으로 결론 내지 않고 세션당 1줄 누적해 **5세션 이상** 쌓인 뒤 판단한다(회의록의 되돌림 조건도 이 지표로 적는다).
- 매일 싸게 재는 도구가 레포에 있다: `python3 scripts/close_path_gap_probe.py` — 피드의 close 후보(직전 거래일
  `signal_date`)마다 다음 거래일 **시가**를 일봉 API 로 받아 갭을 계산하고 `data/reports/close_path_gap_history.jsonl`
  에 세션당 1줄(평균·중앙·상승/하락·건별)을 append 한다. 휴장일에는 새 거래일 행이 없어 스스로 침묵한다(크론 09:20).
- 일봉 창구: `https://api.finance.naver.com/siseJson.naver?symbol=<code>&requestType=1&startTime=YYYYMMDD&endTime=YYYYMMDD&timeframe=day`
  → 행은 `[날짜, 시가, 고가, 저가, 종가, 거래량]`. **장중에 부르면 마지막 행의 '종가'는 직전 체결가**이므로 갭 계산에는
  **시가(두 번째 필드)** 를 쓴다(종가를 쓰면 그날 등락을 다시 재는 셈이 된다). 이 창구는 종목 전용이니 지수에는 쓰지 않는다.
- 이 회선은 프록시 전용이라 WSL 쪽 요청이 502/타임아웃이면 같은 URL 을 Windows 프로세스로 부른다:
  `/mnt/c/Windows/System32/curl.exe -s --noproxy '*' -m 25 "<url>"`(그 자체가 Windows 프로세스라 egress 경로가 다르다).
  보고에는 이 값이 **몇 세션 누적치**인지 항상 붙인다.

## 실측 결론 (최근 11거래일, close 경로)

> 위 §0 의 체결 가능성 필터를 적용한 87세션 재측정이 우선한다: **현행 게이트 진입 0세션 · HEAT 해제 −0.52%/세션 ·
> 게이트 없음 −0.67%/세션(t=−2.8)** — 즉 이 경로는 **게이트 때문에 안 버는 것이 아니라, 살 수 있는 후보에
> 순기대가 없어서** 안 번다. 게이트 완화는 근거가 아니라 손실 확대가 된다. 아래 11거래일 수치는 필터 없는
> 원시 평균이므로 '왜 안 샀나'를 설명하는 데는 쓰되, 완화 근거로 인용하지 않는다.

- R1 통과 **11/11일**(상위10 평균 88.82) · HEAT 통과 **0/11일**(상위10 평균 등락 +20.0%)
  → 이중 상한에서 **실제로 경로를 닫는 것은 HEAT 이고, R1 은 close 에서 사실상 죽은 문턱**이다
  (`r1_ok_heat_fail` = 220건, 나머지 두 갈래는 0건).
- 차단 집단 220건 수익률: 평균 **+1.36%** · 승률 50.5% · 중앙 **+0.07%** · p10 −3.02% · p90 +6.55%
  → 평균은 오른쪽 꼬리가 만들고 중앙값은 0 근처다. "차단된 집단이 플러스"와 "그 게이트가 옳았다"는 양립한다
  (HEAT 는 추격 손실 때문에 도입됐다). 단일 구간으로 완화를 정하지 말고 월별·레짐별로 쪼개 본다.
- 가능한 결론은 세 갈래뿐이다: ① 방어 유지(근거: 레짐별 분해에서 음수 구간 존재) ② **조건부 완화**
  (강세 레짐에서만 상한을 늘리는 안 — 반드시 shadow 가상 체결로 며칠 검증 후) ③ 배관 문제로 규정
  (게이트가 항상 닫혀 신호가 죽은 경로 = 문턱이 아니라 파이프라인 수정 대상).

## 한계 (빠뜨리면 기대값을 과대평가한다)

- **진입가를 그날 종가로 근사**한다 — 실제 체결은 14:50~15:29 이고 그 시각 체결가는 어디에도 저장되지 않는다.
- 재생성 후보는 **당시 발행본이 아니다**(그날 데이터로 다시 계산). `signal_date` 는 전일인 경우가 많다.
- 측정 구간이 강세장이면 평균이 위로 치우치고, 시가 매도는 **갭 리스크**를 포함한다(전일 종가 대비 시가).

## 시장 지수·당일 성과를 싸게 얻는 법

- 지수: `https://m.stock.naver.com/api/index/KOSDAQ/basic` (`KOSPI` 도 같은 형태) →
  `closePrice` · `compareToPreviousClosePrice` 로 등락률 계산. **일부 값이 콤마 포함 문자열('6,971.35')이라
  float 변환 전에 콤마를 제거**해야 한다(안 하면 ValueError). 지수에 `api.finance.naver.com/siseJson.naver`
  창구는 쓰지 말라 — 헤더만 돌아온다(그 창구는 종목용).
- 차단/보유 후보의 당일 실제 성과는 브리지 1~2콜이면 끝난다:
  `/mnt/c/Windows/System32/curl.exe -s --noproxy '*' -m 25 "http://127.0.0.1:8100/quotes?codes=코드,코드,..."`
  (20개씩 청크) → 종목별 `base`(전일 종가) · `open` · `high` · `low` · `current` · `volume`.
  마감 후에는 `current` = 그날 종가다. Daishin 예산을 태우지 않으므로 사후 측정에 부담이 없다.
- 보고에는 계좌 한도로 환산한 금액을 붙인다: 노출 상한 = 계좌 equity × (종목 % × 동시 슬롯 수)
  (실계좌 설정: 종목 1/3 · 동시 3종목 · 총 100% — 정본 `trader_core/config.py`, `scripts/risk_limits.py` 로 읽기)
  → 그 노출 × 측정 수익률 = 기회비용. 절대 금액까지 써야
  아쉬움의 크기가 과장되지 않는다.
