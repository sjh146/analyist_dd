# 임베딩 디바이스·CPU 처리량·GPU 대비

## CPU 처리량 실측 (4코어 · GPU 없음 · MiniLM 384차원)

- 스레드 1: 약 20~30 문장/초 (경합에 가장 둔감한 하한값)
- 스레드 2: 약 16~20, 스레드 4: 6~8 — **다른 학습 작업이 도는 중이면 스레드 증가가 역효과**(경합).
- 첫 모델 로드 30~70초(다운로드 포함), 이후 캐시.
- 측정 시 load average 를 함께 기록하고 코어 수 대비 load 가 높으면 `[CONTENDED]` 라벨을 붙인다. 경합 중 숫자를 정상치로 보고하지 않는다.
- 결론: 하루 수만 건(뉴스·종토방)은 CPU 로 충분. GPU 가 실질적으로 필요한 곳은 대량 백필(100만 건급)과 로컬 LLM 추론이다.

## 디바이스 스위치 (GPU 가 생기면 코드 수정 없이 사용)

- `EMBEDDING_DEVICE=auto`(cuda 있으면 cuda, 없으면 cpu) · `EMBEDDING_BATCH_SIZE` · `EMBEDDING_TORCH_THREADS`(미설정 = torch 기본, 즉 기본 동작 불변).
- 디바이스 해석은 torch 비의존 순수 함수로 분리한다 → GPU 없는 환경에서도 단위테스트가 돈다.
- `cuda` 를 명시했는데 사용 불가면 조용히 CPU 로 떨어지지 말고 경고 로그 + CPU 폴백.
- 컨테이너 GPU 연결은 별도 오버레이(`docker-compose.gpu.yml`, `deploy.resources.reservations.devices: driver nvidia`)로 하고
  본체 compose 는 건드리지 않는다. 되돌리기는 오버레이 없이 기동.
- 진단 도구는 한 번에 "호스트 노드 존재 여부 + `nvidia-smi`/`nvcc` 유무 + 컨테이너별 `torch.cuda.is_available()` +
  각 서비스가 실제 선택할 디바이스"를 출력하고, `--require-gpu` 로 검증 실패를 비영 종료하게 만든다.

## 무료 오픈소스 임베딩으로 교체할 때 선행조건

1) **torch ≥2.6** — 취약점 대응으로 `torch.load` 경로가 막혀, safetensors 가 없는(bin 만 있는) 모델은 로드가 거부된다.
2) **차원 정합 = 스키마 마이그레이션** — 설정의 `VECTOR_DIMENSION`(1024)과 실제 모델 차원(384)이 이미 불일치한다.
   차원을 바꾸면 pgvector 컬럼 타입·HNSW 인덱스·임베딩 테이블(종목 벡터, 뉴스 분석, 뉴스 임베딩)을 함께 마이그레이션해야 한다.
   "모델만 교체"가 아니라 스키마 변경 작업으로 계획한다.
3) 교체 후 유사종목 조회 등 소비 경로 동작을 확인한다.

## 로컬 LLM 전환 경로

- 뉴스/SNS 분석은 클라우드 LLM API 를 쓰되 `LLM_BASE_URL`(+`LLM_MODEL`)로 엔드포인트를 로컬 서버로 바꿀 수 있게 되어 있다
  (기본값은 클라우드 유지 — 스위치를 넣을 때 반드시 기본 동작을 보존한다).
- SNS 정제는 **규칙 우선 트라이지**로 80~90% 를 LLM 없이 판정하고 애매/중요 건만 LLM 을 호출한다.
  로컬 소형 모델로 전부 대체하면 품질·속도 모두 손해이므로 기본 권고는 하이브리드 유지 + 임베딩만 오픈소스로 강화다.
