# 패널 재빌드 운영 (wf_wave 기반 스택)

죽은 피처의 "소스 공백" 가설을 검증할 때 쓰는 절차. **기준선 패널을 덮지 않고** 같은 유니버스로
새 기간·새 소스 기준의 패널을 만들어 두 패널의 생존 판정을 비교한다.

## 0. 재빌드가 필요한지 먼저 판정

- 패널 빌드 시각과 소스 시작일을 비교한다(예: 패널 2026-10-02 빌드 / 조회 구간 2025-08~2026-09,
  뉴스는 2026-04 시작, SNS 피처는 2026-09-23 시작) → 구간 대부분이 "원천 부재"면 재빌드가 의미 있다.
- 커버리지는 패널 유니버스 × 기간으로 센다. 전역 행수는 근거가 아니다(200종목 중 4종목일 수 있다).
- 반대로 `null_ratio 0 + std 0`(상수 0)은 재빌드로 안 고쳐진다 — `fillna(0)` 문제이므로 NaN 유지 +
  결측 지시자를 먼저 고친다.

## 1. 빌드 실행

```bash
docker exec -w /app -e OMP_NUM_THREADS=4 <ml-container> python -u scripts/rebuild_panel.py \
  --panel-out /app/app/models/wf/<새이름>.npz --days 470 --limit 200 \
  --end-date <YYYY-MM-DD> --universe prod --universe-seed 0 --json-out /app/reports/panel_rebuild.json
```

- 러너는 하네스의 `build_panel` 을 **import 해서** 쓴다(빌드 로직 복제 금지 — 정의가 갈라지면 비교가 무의미).
- `--panel-out` 은 새 경로여야 한다. 기준선 패널(`panel_prod200.npz` 등)과 basename 이 같으면 거부하는
  가드를 둔다. 대조군을 잃으면 재빌드 자체가 무의미해진다.
- 결과 옆에 **sidecar**(days·end_date·universe·seed·rows·dates·codes_sha1)를 남긴다. 비교 시 `codes_sha1`
  이 같은지부터 확인 — 다르면 유니버스가 달라 비교가 성립하지 않는다.

## 2. 비용·진행 관리

- 처리량 **2~3 pair/s**(pair = 종목×날짜 1건의 피처 계산). 200종목×470일 = 61,640 pair ≈ **6~8시간**.
  전체 재빌드는 "한나절~하룻밤" 단위로 계획하고 백그라운드로 띄운다.
- 500행마다 체크포인트가 남아 같은 `--panel-out` 재실행으로 이어받는다. 단 `end_date` 를 매번 바꾸면
  체크포인트 키가 달라져 재개되지 않는다 → 구간을 고정하라.
- 그래프 DB 관계 미정의 경고(Neo4j `FOLLOWS_CYCLE` 류)가 로그를 폭주시킨다 — 무해하니 실패로 오판하지 말고
  `grep -v Neo.ClientNotification` 으로 진행 라인만 본다.
- 컨테이너가 root 로 돌면 산출물·sidecar 가 root 0600 이 되어 호스트에서 못 읽는다 → 빌드 후 `chmod 644`.

## 3. 같은 파이프라인을 빠르게 만드는 3가지 (출력 동일성 검증 필수)

빌드 체인이 시간을 잡아먹을 때, **결과가 바뀌지 않음을 비트 비교로 먼저 증명**한 뒤에만 적용한다
(후보 코드·점수 배열이 같으면 통과). 실측 효과: 전체 스크리너 8.17s → 2.65s.

1. **종목별 최근 N행 = `ROW_NUMBER()` 윈도우 대신 `CROSS JOIN LATERAL ... LIMIT n`.**
   윈도우 버전은 전체 테이블(수백만 행)을 정렬한다(3.68s). LATERAL + `(stock_code, trade_date)` 인덱스는
   종목별 20행만 읽어 0.37s. 조회 대상을 유니버스 코드로 한정(`stock_code = ANY(%s)`)하면 더 줄어든다.
2. **비싼 피처 계산 앞에 싼 사전 필터를 둔다.** 유동성·가격·거래량 같은 조건은 종목별 마지막 행만으로
   판정되므로 칼만/모델 계산 전에 걸러 대상을 1/3로 줄인다(1,858 → 669). 사후 필터는 그대로 남겨
   계약을 보존한다.
3. **모델 예측은 종목별 단건 호출을 한 번의 배치로.** 특징행렬(행=종목, 열=feature_names)을 만들어
   `predict(X)` 한 번 호출하고, shape 불일치·예외 시에만 기존 행별 경로로 폴백한다.

적용 전후 산출물을 같은 경로에 따로 저장해 **코드·점수 배열을 비교**하고, 보고에 그 비교를 붙인다
("빨라졌다"만으로는 계약이 바뀌었는지 알 수 없다).

## 4. 재판정·비교

```bash
python3 scripts/feature_survival_report.py --panel <새패널.npz> \
  --json-out data/reports/feature_survival_v2.json --md-out data/reports/feature_survival_v2.md
```

- 비교표로 보고한다: alive / dead / 조건부, `DEAD_CONST_ZERO`(결측 0채움) / `DEAD_SPARSE`(희박) 증감,
  새로 살아난 피처 이름, 여전히 0 인 피처와 사유(writer 부재/커버리지/희박 임계).
- 작은 스모크 패널(예: 8종목×39일)의 alive/dead 를 기준선과 비교하지 말 것 — 창이 다르면 등급이 뒤집힌다.
- 재빌드 패널은 **실험 산출물**이다. 운영 피처 계약(순서·목록)과 다를 수 있으므로 승격·라이브 경로에 그대로 쓰지 않는다.
- **"같은 유니버스로 재빌드"는 자동으로 성립하지 않는다 — 유니버스가 회전한다.** prod 유니버스가 "최근 데이터순
  200종목" 같은 규칙이면 몇 달 뒤 재빌드는 **다른 200종목**을 준다(실측: 두 패널 교집합 23/200). 그래서 sidecar 의
  `codes_sha1` · 교집합을 **비교 전에** 세고, 교집합이 작으면 ① 생존 판정 비교를 "현재 유니버스의 상태"로만 해석하거나
  ② 기준선 패널의 코드 목록을 파일로 넘기는 **명시 유니버스 경로**(`--codes-file`)로 다시 빌드한다. 교집합을 확인하지
  않은 채 "재빌드로 개선됐다"를 말하면 서로 다른 표본을 비교한 것이다.
- **산출물 경로는 사용자 쓰기 가능한 곳으로 잡아라.** 모델 디렉터리(`models/wf` 등)가 컨테이너 root 소유면
  `tempfile.mkstemp` 단계에서 `PermissionError` 로 죽는다 → 쓰기 가능한 경로(예: `data/panels/`)에 저장하고,
  라이브 경로로 옮기는 것은 권한 있는 쪽의 별도 단계로 둔다.
