# analyist_dd 운영 워크플로

이 스킬은 스택을 매일 어떻게 돌리는가를 답한다. 수집 함정은 `analyist-dd-stack-ops`,
코드 변경은 `analyist-dd-code-change-safety`, 보고 형식 원본은 `trading-stack-status-report` 를 본다.
여기서는 **순서·판정·완료 기준**만 다룬다.

## 1. 계기와 빈도

- 계기: 스택이 조용히 멈추거나 조용히 틀린 데이터를 쓰는 사고가 반복됐다. 그래서 돌고 있다가 아니라
  실제 행·실제 수치가 남았다를 매일 확인하는 리듬이 생겼다.
- 장기 목표(사용자 지시): 죽은 피처 부활 + 모델 AUC 0.6 돌파. 판정은 확장창 walk-forward 다중폴드 평균.
- 빈도(평일, KST):

| 시각 | 무엇 |
|---|---|
| 08:20~08:50 | 개장 전 점검(브리지·루프·세션·피드·후보 수) |
| 09:10 / 12:10 / 14:10 | 단타 후보 생성·발행 |
| 09:05~14:05 매시 | 인트라데이 후보 갱신 |
| 14:40 | close 후보(상한가 제외 메타 포함) |
| 15:10~15:55 | 마감 틱(트레이더·감사·프로토콜 락) |
| 18:55 | 일봉 적재 |
| 19:10 | 수급(KIS) |
| 20:00 | 저녁 파이프라인(수집·예측) |
| 20:30 | 피드 발행 |
| 22:35 | 당일 일봉 재시도 |
| 23:05 | 발행 관문 G1~G5 |
| 23:20~23:25 | 장마감 후 점검 일괄 + 실패 분석 |
| 02:50 / 03:05 / 03:10 | 테스트 스위트 / 스킬 미러 / 스킬 린트 |

장중 매매 루프: 30초 주기(집중창 10~15초), 사이클 1~1.5초.

## 3. 실제 순서 (운영 1사이클)

1. 관문부터: `scripts/verify_daily_pipeline_gates.py` 로 G1~G5 를 먼저 본다.
2. 매매 상태: 브리지 `/positions`·`/balance`·`/daily_pnl` + 저널 오늘 행으로 보유·실현손익·진입 수를 센다.
3. 루프 상태: `runner.log` 최근 사이클, `loop_state.json`(daily/guard), 프로세스 pid.
4. 피드 신선도: `screener_latest.json` 의 `generated_at`·전략별 items·`regime` (구 피드면 국면 규칙이 무력화된다).
5. 백로그 우선순위: needs_approval 0 인지 확인하고 지금 실행 가능한 1~2개를 고른다.
6. 수정 → 검증 → 커밋: 관련 테스트 → lint → 커밋 → 푸시(`git ls-remote` 로 원격 해시 확인).
7. 보고: 했음 / 검증(수치) / 남음 3부.
8. 자동화 배선: 같은 점검을 두 번 손으로 했다면 스크립트+크론으로 옮기고 로그·JSON 산출물을 남긴다.

## 4. 결정 규칙 (수치 포함)

- 추정 금지: 로그·DB·응답에서 직접 읽은 수치만 쓴다. 못 재면 측정 불가로 적는다.
- 배선 ≠ 실제 행: 스크립트에 넣었다로 끝내지 않고 DB 행·파일·발행본에서 확인한다.
- 실주문 경로·한도·피드 계약 변경은 사람 승인. 승인 전에 .env·설정 실물부터 확인한다.
- 국면별 공격성: risk_on + ATR ≥ 4% → 일일 진입 +2·엣지 −1, risk_off → 사이즈 ×0.5·엣지 +2(문턱 6).
- 비용 게이트: 진입 스프레드 > 0.30% 차단, 당일 등락 ≥ +15% 차단(뉴스 단발).
- 일일 상한 10건. 청산 후 30분 쿨다운, 종목당 1일 1회 재진입 금지.
- 청산: 단타 +1% 무장 트레일링 −0.8%, 90분 시한(수익 중이고 진입 시점 지수보다 지금 지수가 높으면 240분까지 연장).
- 레짐: risk_off 라도 후보 생성은 유지하고 트레이더가 조인다(전면 중단은 사용자 결정으로 폐기).
- 커밋 경계: 실거래 코드는 라이브 사본(Windows 중첩 리포)에서만 수정한다. WSL 사본은 낡은 스냅샷.

## 5. 완료 판정 체크리스트

- [ ] 관련 테스트 수를 숫자로 말할 수 있다(예: 5스위트 1,651 passed / 실패 0).
- [ ] 관문 결과가 숫자다(G1~G5 중 n/5, 실패 항목과 사유).
- [ ] 발행본·DB·저널 중 최소 1곳에서 실제 행/파일을 확인했다.
- [ ] 커밋이 원격에 있다(`git rev-parse` == `git ls-remote`).
- [ ] 자동화로 옮겼다면 로그/JSON 산출물 경로가 있다.
- [ ] 실패·블로커·한계를 숨기지 않고 적었다.

## 6. 예외 사례 (실제 사고)

상세 카탈로그: `references/incidents.md`. 대표 유형:
- 입력 가시성 불일치: 같은 스크립트가 호스트는 차단, 컨테이너는 통과 → `data/state` 마운트 누락.
- 설정 타입 붕괴: tuple 필드가 문자열로 왕복 → 보수화·확장·게이트가 조용히 무력화.
- 테스트 거짓 통과: 러너가 `skipped`(테스트 수)를 스위트 건너뜀으로 오독.
- 환경 의존 테스트: `.env` 미로딩·주말 날짜·하드코딩 날짜 → 같은 코드가 4/5건으로 다르게 실패.
- 시한부 청산이 이긴 포지션을 끊음: 90분 규칙, 고점 대비 반납.

## 7. 결과물 톤·기준

- 한국어. 수치 먼저, 해석은 다음. 결론 → 근거(수치) → 남은 것.
- 3부 구성: 했음 / 검증(실측) / 남음(블로커·한계 포함).
- 금지: 추정치를 사실처럼, 아마/대략으로 수치 대체, 자기신고 로그를 실측처럼 인용.
- 사용자에게 올리는 시점: 되돌리기 어려운 변경(실주문 경로·한도·설정·삭제), 승인 항목, 목표 미달.

## 8. 나쁜 버전의 모습

- 로그에 완료만 있고 DB 행·발행본·실측 수치가 없다.
- 원인을 분리하지 않고 환경 문제로 뭉갠다(브리지/컨테이너/호스트/자격증명 중 어디인지 미확인).
- 한 번의 관찰로 조건 없이 일반화한다.
- 테스트를 통과시키려 기대값을 약화한다(원인 판정 없이 assert 삭제).
- 커밋만 하고 푸시·원격 해시 확인을 건너뛴다.
- 자동화로 옮겼다고 말하지만 크론 등록·실행 로그·산출물이 없다(배선만 한 상태).
- 실패를 다음 틱으로 미루고 사용자에게 알리지 않는다(조용한 공전).

## 운영자 판단 (관제 기반 추정 — 사용자 확인 대기)

이 4개는 사용자가 직접 답한 것이 아니라, 이 세션에서 관제된 행동·지시에서 추출한 가설이다.
다르면 수정한다.

1. 계기·재발 트리거: 장기 목표를 "죽은 피처 부활 + AUC 0.6"으로 직접 지정하고 야간 자율 루프를
   돌려 아침에 실측을 확인하는 패턴. 다시 하게 되는 트리거는 "보고가 0건·변동 없음" 또는
   서브시스템이 조용히 멈춘 증거를 보았을 때(예: swing signal_date 가 비거래일).
2. 손으로 남기는 부분: Creon 로그인·UAC 같은 사람 단계, 실주문 경로·한도·자본 관련 승인,
   그리고 "오늘 매매 여부" 같은 자본 판단. 나머지 점검·배선·검증은 자동화로 넘긴다.
3. 개인 문턱: 단일 분할 수치를 신뢰하지 않고 다중폴드·실측을 요구. 작은 표본을 성과로 계상하지 않는다
   (예: daytrading 11건 +2,285원을 판단 근거로 쓰지 않음). 비용은 왕복 기준으로 상시 확인(0.21%+스프레드).
4. 보고에서 가장 중요하게 보는 한 줄: **실현 순손익(원)** — 보유·진입·게이트는 그 뒤 설명이다.
   그 다음이 "왜 오늘 돈을 못 벗겼나(게이트·국면·비용)"이다.
