# 보안 감사 — 도구 운용과 결과 검증

## 스캔 범위 정하기

두 가지를 따로 본다:
1. **저장소 스캔(비밀값)** — `.env` 실제 값 기반 검색이 가장 확실하다: `.env` 를 파싱해 값마다
   `git log --all -S "<값>"` 과 `git grep -F "<값>"` 을 돌린다. 키 내임 기반 정규식만으로는 `PATH`/`URL` 같은
   비밀 아닌 값이 대량 오탐된다(키 내임이 `SECRET|PASSWORD|TOKEN|API_KEY|APP_KEY` 인 것만, `.env.example`
   기본값과 같은 값은 제외).
2. **자동 펜테스트** — 코드 품질·설정 결함(권한·주입·노출)에는 유용하지만, 실행 비용·시간이 들고 환각이 쉽다.
   로컬 코드만 볼 때는 저장소 사본을 따로 만들어(`.git`·`data`·모델 가중치 제외) 스캐너가 원본을 수정하지 않게 한다.

## 자동 펜테스트 도구(strix 류) 운용

- 설치: `uv tool install strix-agent` — 백그라운드 셀로 돌릴 때 `uv` 가 PATH 에 없을 수 있으니 절대경로를 쓴다.
- 모델: `STRIX_LLM=<provider>/<model>` + `LLM_API_KEY`. OpenAI 호환 프로바이더면 기본 모델명으로 동작한다.
- 첫 실행은 샌드박스 이미지(수 GB)를 받는다. 로그에 `Docker image ready` 가 뜨기 전에 프로세스를 죽이면
  이미지 풀은 끝났는데 스캔만 날린다 — 이미지 존재(`docker images | grep strix`)를 확인하고 기다린다.
- 대상은 디렉터리·URL·API 스펙 모두 가능. `--instruction-file` 로 스코프·금지사항(로컬만, 파괴 금지, 한국어 보고)을
  명시하고 `--scan-mode quick --max-budget N` 으로 비용을 상한한다. 비용은 실행 후 보고된다(수십 건 감사에 $1 미만).
- 실행 중 `vulnerabilities.json` 은 **미완성**이다. 완료 벤너(`Penetration test completed` + 심각도 합계)를
  확인한 뒤 파일을 읽는다.

## 결과 검증 (필수)

AI 스캐너는 그럴듯한 수정안에 **존재하지 않는 파일·함수**를 섞는다. 지적마다 저장소에서 증거를 찾는다:

| 주장 유형 | 검증 명령 |
|---|---|
| 포트·볼륨 노출 | `grep -n 'docker.sock\|0\.0\.0\.0' docker-compose.yml`, `docker ps --format '{{.Names}} {{.Ports}}'` |
| 하드코딩 비밀번호 | `grep -n 'PASSWORD.*=.*"' <파일>` |
| 미정의 변수(NameError) | 해당 함수 본문을 읽고 이름 정의 여부 확인 |
| 파일 존재 | `git ls-files | grep <파일>` (없으면 그 지적은 환각) |
| 추적 여부 | `git ls-files`, `git check-ignore -v <파일>` |

검증 결과는 세 갈래로 보고한다: **실재·수정함 / 실재·보류(이유) / 재현 불가(환각)**.
재현 불가로 판정한 항목도 문서에 근거와 함께 남긴다(다음 스캔에서 같은 지적이 반복되므로).

## 수정 우선순위

1. 남의 권한으로 다른 사용자에게 피해를 줄 수 있는 것(공유 서명키·토큰·소켓 노출·공개 저장소의 비밀번호)
2. 조용히 기능이 죽은 것(500 오류, 마스킹 우회)
3. 하드닝(포트 바인딩, 의존성 CVE)

회귀 테스트는 "취약점이 다시 들어오면 실패"하게 쓴다: `.env` 값 재유입, 기본값 하드코딩, 교차 고객 서명 위조,
마스킹 우회 입력. 스캐너 실행 자체를 테스트로 만들지는 않는다(비결정적·고비용).
