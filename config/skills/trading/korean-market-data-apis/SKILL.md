# 한국 시장 데이터 API (KIS · KRX · Naver)

한국 주식 데이터를 수집하는 모든 작업(유니버스 시딩, 일봉/분봉 백필, 감정분석용 LLM)의
자격증명 위치·호출 모양·호출 경제성·오류 진단. 프로젝트별 절차는 각 레포 문서가 갖고,
여기에는 재사용되는 API 지식만 둔다.

## 0. 자격증명 반영·검증 (모든 소스 공통)

1. `.env`(또는 동등한 런타임 env)에 기록한다. 값은 파일에만 — 임시 python 스크립트로 쓰고 즉시 삭제해 transcript에 값이 남지 않게 한다. `chmod 600`.
2. **컨테이너는 `docker compose up -d`로 재생성해야 `env_file`이 반영된다**(설정이 바뀐 서비스만 Recreate). 호스트에서 도는 크론·스크립트는 `.env`를 `source`하므로 재기동 불필요.
3. 검증은 **컨테이너 안에서 실제 호출**로 한다 — 호스트 curl이 200이라도 컨테이너에 env가 들어갔다는 증거는 아니다.
4. 새 키를 받으면 "그 키로 실제 **되는 경로가 무엇인지**"를 먼저 확인한다: 레포에서 그 키를 쓰는 코드를 `grep` → 없으면 실호출로 엔드포인트를 확인. 안 되는 키를 "설정했습니다"로 끝내면 사용자는 수집이 도는 줄 안다 — 되는 것과 안 되는 것을 나눠서 보고한다.
5. 러너는 키 미설정 시 **fail-fast**(메시지 + `exit 2`)하게 만든다. 조용히 0건 수집하면 크론 로그가 성공처럼 보인다.
6. **키의 "존재"와 "유효"는 다르다 — 실호출 프로브로 성공을 확인한 뒤에만 .env에 반영한다.**
   디스패처가 `[ -n "$APP_KEY" ]` 같은 **존재 검사**로 수집 소스를 고르게 되어 있으면, 인증 실패하는 키를 넣는
   순간 잘 돌던 폴백 경로(KRX 등)가 선택 해제되어 야간 수집이 통째로 죽는다. 순서를 지킨다:
   (a) 키 전용 1콜 프로브(예: KIS 토큰 발급, KRX 하루치 1마켓) → (b) 성공하면 .env 반영, (c) 실패하면
   .env에서 **빼고** 보류 파일(예: `~/<source>_keys.pending.env`, 0600)로 옮긴 뒤 "보류 중, 폴백 경로 유지"를 보고.
   구조적 해법은 디스패처에 "프로브 성공 시에만 A, 실패 시 B" 분기를 넣는 것 — 만료·오타 키가 수집을 멈추지 못하게 한다.
7. **붙여넣은 자격증명은 쓰기 전에 자체 검증한다.**
   - base64 시크릿(앱시크릿·인증키) 길이는 **4의 배수**여야 한다. 179처럼 나머지가 3이면 잘림이 확정이므로 재복사를 요청한다.
   - 파일에 쓴 값이 사용자가 준 문자열과 **정확히 같은지** 대조한다(앞뒤 공백·비표준 문자·개행 포함 여부). 값 비교는 hash 접두어로만 출력해 transcript에 원문을 남기지 않는다.
   - 검증 커맨드에 시크릿 리터럴을 쓰지 않는다 — `.env`를 `source`한 뒤 `"$APP_SECRET"`을 curl 인자로 넘긴다.

## 1. 잘못된 응답 코드를 상태로 읽기 (핵심 규칙)

| 응답 | 진단 | 행동 |
|---|---|---|
| `401` + JSON `{"respMsg":"Unauthorized API Call"}` | 엔드포인트는 맞고 **키가 그 서비스에 승인되지 않음** | 콘솔에서 서비스 신청/승인 확인. 경로 변형을 더 시도해도 결과 동일 |
| `404` | 호스트/경로가 다름 | 호스트를 바꾼다 (예: 운영 호스트엔 `/svc/apis` 경로 자체가 없을 수 있음) |
| `403` + HTML | WAF/IP 차단 | 재시도 무의미. 다른 소스(KIS 등)로 피벗 |
| `200` + 기대한 필드 없음 / **0건** | 파서는 돌았지만 내용이 없음 — **성공으로 취급하지 않는다** | 스크래핑 대상 사이트가 개편(SPA 전환)된 경우가 대표적 |

- **리다이렉트된 HTML을 파싱하면 0건이 조용히 나온다.** DOM 선택자가 사라진 게 아니라 응답이 다른 페이지다 — `follow_redirects=True`면 상태코드는 200으로 보인다. "수집 0건"을 반드시 실패로 보고 원인을 찾는다.
- OpenAI 호환 LLM 엔드포인트의 `/v1/models` 목록은 **호출 가능한 모델의 전체 목록이 아니다**(목록에 `deepseek-flash`/`deepseek-v4-pro`만 있어도 `deepseek-chat`이 completion에서 200으로 답한다). 목록을 보고 모델명을 "고치지" 말고 실제 completion으로 검증한다.

## 2. KIS OpenAPI (한국투자증권 — 일봉/분봉 수집의 주 소스)

- env: `KIS_APP_KEY`, `KIS_APP_SECRET`, `KIS_ACCOUNT_NO`(시세엔 불필요), `KIS_BASE_URL`, `KIS_DAILY_TR_ID`, `KIS_MINUTE_TR_ID`, `KIS_REQUEST_DELAY`(기본 3.0s+jitter), `KIS_RETRY_MAX`, `KIS_TOKEN_PATH`(JWT 24h 캐시 — 발급은 분당 1회 제한), `KIS_DRY_RUN`.
- **1콜 = 최대 100일 범위 조회(기간별시세)** → 구간 백필은 종목당 1콜이면 충분하다. 일자별 반복은 호출을 N배 낭비한다.
- **일일 호출 한도는 코드에 없다 — 스코프를 넓히기 전에 계정 한도를 먼저 확정하라.** 이 레포들이 강제하는 것은
  호출 간 지연(`KIS_REQUEST_DELAY` 3.0s+지터)뿐이고 일일 상한은 `.env`·설정 어디에도 없다. 그래서 대상을 늘리는 변경
  (회전 주기 단축·유니버스 확대·같은 스크립트 이중 실행)은 **초과를 감지할 장치 없이** 핵심 회전과 같은 앱키 쿼터를 나눠 쓴다.
  확대 요청을 받으면 ① 후보 스코프의 호출 예산을 먼저 계산해 수치로 제시한다(예: 4,340종목 × 1콜 ≈ 2,700콜 ≈ 3s 지연에서 2.3시간)
  ② 한도가 확인되기 전에는 **현행 스코프 유지**가 기본값이고, 그 결정을 기록한다 ③ 확대하기로 했으면 env 상한을
  명시적으로 올린다 — 러너의 안전 상한 기본값은 넓은 스캔을 **조용히 토막내고** 로그에는 `완료 0건` 처럼 보인다.
- **분봉은 1회 응답 30행 고정**이다 — `FID_CNT`를 100으로 올려도 30행만 온다(실측). 정규장 391분이면 14페이지가 필요하고, 시간 내림차순 응답을 과거로 페이지네이션한다. `MAX_PAGES` 같은 안전장치의 기본값을 10으로 두면 개장 후 약 91분이 조용히 누락된다 — 페이지 수 상한은 14 이상으로 두거나 env로 조정 가능하게 한다.
- **분봉 페이지네이션 종료 조건을 `len(page) < fid_cnt` 로 쓰지 마라 — 30행 고정이라 항상 참이다.**
  KIS는 `FID_CNT=100` 을 줘도 페이지당 30행만 주므로 그 조건을 종료식에 넣으면 **1페이지만 받고 끝나**
  마감 직전 30분(15:01~15:30)만 쌓인다. 실측: 40여 세션 동안 하루 9,000행(=300종목×30행)으로 고정돼 있었고,
  그 데이터로는 장중 손절/익절 순서를 전혀 알 수 없다. 종료는 ① 빈 페이지 ② `oldest == MARKET_OPEN_TIME`
  ③ 기준시각이 진행하지 않음 으로만 판정하고, 적재 감사에 **종목당 행수가 380~391인지**를 넣는다
  (30행 근처면 페이지네이션이 죽은 것).
- **KIS로 못 채우는 과거 분봉은 Naver `siseJson` 으로 되살린다 — 단 종가만 온다.**
  `https://api.finance.naver.com/siseJson.naver?symbol=005930&requestType=1&startTime=YYYYMMDD&endTime=YYYYMMDD&timeframe=minute`
  → 실측 6거래일 × 정규장 381분/일(행 `["YYYYMMDDHHMM", 시가, 고가, 저가, 종가, 누적거래량, …]`).
  **시/고/저는 null 이고 종가·누적거래량만** 채워져 있으므로, ① 손절/익절 순서 판정은 분 종가 경로로만 하고
  ② 없는 OHLC 를 현재가로 메꿔 저장하지 말며(별도 테이블 + `source` 컬럼으로 분리) ③ 창을 좁혀 과거로 더
  파고들 수 있는지 실호출로 확인한다(KIS는 당일만 주므로 이 경로가 과거 분봉의 유일한 대안이다).
- **분봉은 당일만 제공된다** — 지난 날짜를 요청하면 `no_data`가 온다. 과거 분봉 백필은 불가능하므로 수집 크론이 그날 안에 돌지 않으면 그날 분봉은 영구 결손이다.
- **전 종목 분봉 수집 비용을 먼저 계산한다**: 종목당 ~14콜(30행×14페이지) × 2,700종목 ≈ 3.8만 콜 ≈ 30시간 이상. 야간 크론에 들어가지 않는다 → 우선순위 유니버스(스크리너 후보·보유·관심 종목 100~300종목 = 1~2.7시간)로 제한한다.
- **일봉을 KIS로 전 종목 받으면 1일 2,770콜 ≈ 2.5시간**(3s+지터)이다. 일봉 야간 수집의 기본 경로는 날짜당 2콜인 KRX로 두고 KIS는 폴백·프로브용으로 쓴다. 긴 수집을 다음 단계 시작 시각과 겹치게 돌리면 그 단계(예: 20:00 ML 파이프라인)가 부분 적재분을 학습 입력으로 읽는다.
- HTTP는 `subprocess curl` — 파이썬 `requests`/`urllib`는 WAF 403.
- **유니버스를 `market_data`에서 읽는 구현은 빈 DB에서 아무것도 수집하지 않는다.** 종목 마스터(`stocks`)를 먼저 시딩하고, 백필 러너는 `stocks`(KOSPI/KOSDAQ) 기준으로 돌린다. 이 함정은 KIS에만 있지 않다 — 시세 테이블을 유니버스/스코프 소스로 삼는 러너(재무 백필, 채점기)는 **신규 배포에서 전부 0건**이 되므로 `market_data`가 비면 다른 유니버스로 폴백하는 분기를 넣는다.
- 토큰 발급(`POST {BASE}/oauth2/tokenP`, json `appkey`/`appsecret`)이 **키 유효성을 반증할 수 있는 유일한 1콜 프로브**다. 시세 호출 로그만 보면 원인이 안 갈린다.
  - `403` + `{"error_code":"EGW00103","error_description":"유효하지 않은 AppKey입니다."}` = 앱키 자체를 인식 못 함(오타·폐기·만료). 복사 오류라면 눈에 안 보이는 문자 혼동이 흔하다 — `I`↔`l`, `0`↔`O`, `1`↔`l`, `S`↔`5`. 케이스만 다른 후보 2개를 각각 1콜로 프로브하면 즉시 갈린다.
  - `EGW00102` = AppSecret 불일치. 어느 쪽이든 **두 도메인(실전 `openapi.koreainvestment.com:9443`, 모의 `openapivts.koreainvestment.com:29443`)에서 같은 코드면 도메인 문제가 아니다** — 도메인을 더 바꿔보지 말고 키 재발급을 요청한다.
  - **토큰 발급은 앱키당 분당 1회 — 수동 프로브가 바로 뒤 실행을 깨뜨린다.** 방금 1콜로 토큰을 받아왔는데 이어서 돌린 수집기가 `http=403 EGW-UNKNOWN(rt_cd=1)`으로 죽으면 오타·차단이 아니라 **방금 소진한 발급 쿼터**다. 60초 뒤 같은 명령을 다시 돌려 성공을 확인한다(성공하면 `KIS_TOKEN_PATH` 캐시가 생성된다).
  - **tokenP 실패 본문은 `error_code`/`error_description`으로 온다**(시세 API의 `msg_cd`/`msg1`이 아니다). `msg_cd`만 읽는 클라이언트는 원인을 `EGW-UNKNOWN`으로 뭉개고 레이트리밋 재시도(60s)도 걸지 않아 오타와 쿼터가 로그에서 구분되지 않는다 — 두 키를 모두 읽게 고친다.
- **키를 교체하면 `KIS_TOKEN_PATH` 캐시를 반드시 지운다.** 다른 앱키로 발급된 캐시 JWT를 그대로 쓰면 시세 호출이 `403 EGW-UNKNOWN(rt_cd=1)`으로 즉시 죽어 IP 차단으로 오독된다. 캐시 JWT payload의 `aud`(36자)가 발급 앱키이므로 새 키와 hash를 비교하면 "예전 키와 다른 키"인지 판별할 수 있다(레포에 커밋된 옛 캐시가 남아 있는 경우가 있다).
- **자격증명 점검은 토큰 발급만으로 불충분하다**: 캐시 토큰(`KIS_TOKEN_PATH`)이 남아 있으면 앱키가 틀려도 프로브가 "정상"을 출력한다(실측). 점검 모드는 **대표종목 시세 1콜**까지 해야 하고, 그래야 앱키 불일치가 401 → 재발급 실패 → `EGW00103`으로 드러난다.
- **`EGW00102`/`EGW00103`(자격증명 거부)은 재시도 금지.** KIS가 HTTP 500으로 돌려주기 때문에 일반 일시오류 분기에 걸려 백오프 6회(60초+)를 태우고 실패한다 — 자격증명 오류를 별도 분기로 빼서 즉시 종료하고 EGW코드를 로그에 남긴다.
- **"키가 설정되어 있다"와 "그 키로 된다"는 다르다**: 야간 수집 러너는 경로 선택 전에 프로브를 돌리고, 실패하면 2,700건을 실패로 쓸어버리지 말고 EGW코드와 함께 `exit 3`으로 끝낸다(크론 로그가 수천 건 실패로 채워지지 않게).
- 휴장/공실 판별을 다른 소스로 대체할 때는 러너의 **진행파일을 무시하는 플래그**(`--ignore-progress`)가 필요하다 — 이미 처리한 날짜는 스킵되어 응답 자체를 못 보기 때문이다(실측: 프로브가 계속 판별불가를 반환).
- 상세(tr_id 값·필드 매핑·오류 코드): 레포의 `docs/KIS_컬렉터_PLAN.md`.
- **호스트에서 도는 수집 러너는 `.env` 를 source 한 뒤 DB host/port 를 덮어써야 한다.** `.env` 는
  컨테이너 기준(`POSTGRES_HOST=postgres`, `PORT=5432`)으로 적혀 있어서, 호스트 셸에서는 ① `postgres`
  이름이 해석되지 않고(`could not translate host name` → 후보 0건) ② 노출 포트는 5434 다(컨테이너 5432→호스트 5434).
  `set -a; . .env; set +a` 직후 `export POSTGRES_HOST=127.0.0.1 POSTGRES_PORT=5434` 로 **명시적으로 덮어쓰고**,
  `docker port <pg컨테이너>` 로 실제 노출 포트를 확인한다.

### 2a. 투자자 수급(외국인/기관/개인 순매수) · 지분율 — TR 두 개를 구분하라 (2026-09-24 실측)

수급 데이터는 **TR 에 따라 날짜 파라미터 지원이 정반대**다. 하나만 알면 "최근 30일까지만 된다"고 잘못 결론낸다.

| TR / 경로 | 날짜 파라미터 | 행 수 |
|---|---|---|
| `FHKST01010900` `/uapi/domestic-stock/v1/quotations/inquire-investor` | **완전 무시** — 20250101~20250201 을 요청해도 **최신 30영업일**이 온다 | 1콜 30행 고정 → 페이지네이션 불성립(구간을 바꿔도 같은 행) |
| `FHPTJ04160001` `/uapi/domestic-stock/v1/quotations/investor-trade-by-stock-daily` | `FID_INPUT_DATE_1` = **창의 끝(포함)**, `FID_INPUT_DATE_2 > FID_INPUT_DATE_1` 필수(같으면 **빈 응답**) | d1=20260811 → 20260630~20260811 / d1=20260630 → 20260518~20260630 |

- **과거 백필(60~90영업일)은 두 번째 TR 로만 가능하다**: `d1 = DB 최소일 − 1일`, `d2 = d1 + 1일` 로 한 페이지씩
  과거로 밀면 30영업일씩 파고들 수 있다(진행파일로 재개, 종목당 60영업일 = 2콜).
- 응답 배열 키가 **TR 마다 다르다** — `FHKST01010900` 은 `output`(리스트), `FHPTJ04160001` 은 `output2`
  (리스트; 같은 응답의 `output1` 은 현재가 요약 dict). **한 키만 읽는 파서는 두 번째 TR 에서 조용히 0행**이 되어
  "날짜 앵커가 틀렸다"고 오진하게 된다 → 파서는 두 키를 모두 시도한다. 필드명은 동일:
  `{prsn,frgn,orgn}_ntby_qty`(순매수 수량), `{prsn,frgn,orgn}_ntby_tr_pbmn`(순매수 대금),
  `{prsn,frgn,orgn}_{shnu,seln}_{vol,tr_pbmn}`(매수/매도). 두 TR 의 같은 날짜 값은 서로 일치한다.
  한 응답 안에서도 단위가 섞인다 — `acml_tr_pbmn` 은 **원**, `*_ntby_tr_pbmn` 은 **백만원**.
- 호스트에서 러너를 돌릴 때 `python3` 가 **Hermes 자신의 venv python**(psycopg2 없음)을 가리키는 경우가 있다
  (`ModuleNotFoundError: No module named 'psycopg2'`). 레포 호스트 스크립트는 `/usr/bin/python3` 로 실행한다.
- 레이트리밋: 토큰 발급은 앱키당 분당 1회(`EGW00133`), 시세 호출은 실전 계좌 초당 20건 수준이라
  1.5s+지터면 30종목×~4콜(≈120콜)이 3분 내에 끝난다. 프로브를 먼저 돌려 토큰 쿼터를 소진하면
  직후 본 실행이 `EGW00133` 으로 시작하니, 프로브와 본 실행을 붙여 돌리지 않는다.
- **`*_tr_pbmn` 단위는 백만원이다** — 교차검증: 005930 2026-09-23 `frgn_ntby_qty` 4,513,767 × 종가 286,500
  = 1.293e12원 ≈ API값 1,283,306 × 1e6. 저장 시 단위를 계약으로 못박아라(원으로 환산 권장).
- **지분율은 현재가 TR(`FHKST01010100` `/inquire-price`)에서 온다**: `hts_frgn_ehrt`(외국인 지분율 %)이고
  `frgn_hldn_qty / lstn_stcn × 100` 과 일치한다(005930: 2,726,977,583/5,846,278,608 = 46.64).
  **스냅샷만 제공 — 과거 시점 조회 불가**(종목당 1행). **기관 지분율 필드는 없다**(output 전수 확인) →
  0 을 지어내지 말고 NULL 로 두고 소비 측에 비외국인(개인+기관) 잔여로 해석된다고 보고한다.
  - **스냅샷을 '오늘' 날짜 한 행만 적재하면 과거 패널에서는 전부 0 이 된다** — as-of 리더가
    `trade_date <= 조회일 ORDER BY trade_date DESC LIMIT 1` 로 읽으므로 조회일이 적재일 미만인 행은 못 잡는다.
    과거 날짜에 현재값을 복사해 넣는 것은 룩어헤드다(하지 마라) → **"현재값을 채웠다"와 "과거 시계열 피처가 살아났다"를
    구분해서 보고**하고, 과거 이력은 일별 지분율을 주는 다른 소스를 확인한다.
- **이력 조회 TR 은 상장(거래개시) 전 구간을 all-zero 행으로 패딩해 준다.** 시세 테이블에 시세가 없는 날짜인데
  수급 행만 날짜를 채워 오면 그것이 패딩이다 → 적재 전에 **시세 테이블에 그 `(종목, 날짜)` 가 있는 행만** 남긴다.
  걸러내지 않으면 커버리지(행수·거래일 수)가 부풀고, 상장 직후 5일 평균이 0 으로 희석된다.
- **수급 리더는 `date` 를 안 받으면 테이블 최신 행을 집어간다**(`ORDER BY trade_date DESC LIMIT n`) → 조회일을
  바꿔도 값이 같고 과거 조회일에 미래 수급이 섞인다. as-of 필터(`trade_date <= date`)를 리더에 넣어야
  "날짜별로 값이 달라지는" 피처가 된다. 파이프라인이 `date` 를 안 넘겨도 시세 프레임(이미 `<= date` 로 잘림)의
  최대 거래일을 as-of 로 쓰면 **호출부 수정 없이** 리더 안에서 정합을 맞출 수 있다.

- **공매도 '잔고'(short interest)는 이 스택에서 구할 수 없다 — 그 피처는 폐기하라.** KIS 공매도 TR(`FHPST04830000`)은
  **체결**(일별 거래량·거래대금·거래비중)만 주고, 잔고 계열 후보 6경로(`daily-short-sale-balance`,
  `inquire-short-sale-balance`, `short-sale-balance-trend`, `short-sale`, `ranking/short-sale-balance`,
  `daily-loan-balance`)는 **전부 404** 였다. KRX OpenAPI 주식 카탈로그에도 공매도 서비스가 없다.
  따라서 `short_interest_ratio`(잔고/발행주식)·`days_to_cover`(잔고/평균거래량)는 **데이터 자체가 없고**,
  `krx_short_selling.balance_quantity` 는 전량 0/NULL 이다 — 빌더를 고쳐도 살아나지 않는다.
  살릴 수 있는 것은 체결 기반 `short_selling_ratio`(공매도 거래비중)뿐이고, 그것도 커버리지(패널 26/200)를
  백필로 넓혀야 임계(5%)를 넘는다.

### 2b. 프로그램매매 — 시장 전체 값은 종합조회(일별) TR 하나로 끝난다 (2026-09-24 실측)

"프로그램매매 비중" 피처는 종목별 집계로 풀려 하면 수천 콜이 된다(3콜/초라도 수십 분). 시장 전체 값을
한 구간씩 주는 TR 이 따로 있다 — **먼저 이걸 찾고, 없을 때만 종목별로 내려간다**.

| TR / 경로 | 범위 | 특징 |
|---|---|---|
| `FHPPG04600001` `/uapi/domestic-stock/v1/quotations/comp-program-trade-daily` | **시장 전체·일별(1행/일)** | `FID_COND_MRKT_DIV_CODE=J`, `FID_MRKT_CLS_CODE=K`(KOSPI)/`Q`(KOSDAQ), `FID_INPUT_DATE_1`~`_2` 구간(20일 안전) → `whol_smtn_{seln,shnu,ntby}_tr_pbmn`(전체 프로그램 매도/매수/순매수, **백만원**) + 차익/비차익·위탁/자기 분해. 백필의 기본 경로 |
| `FHPPG04650101` `/quotations/program-trade-by-stock` | 종목별(1콜=최신 30행 고정) | 필드는 `whol_*` 뿐 — **투자자(외국인/기관) 분해 없음**. 시장 전체를 만들려면 전체 종목 집계가 필요해 비경제적 |
| `FHPPG04650201` `/quotations/program-trade-by-stock-daily` | 종목별(위와 동일 응답) | 위 TR 과 경로만 다르고 결과가 같다 — TR_ID 와 경로를 짝지어 확인할 것 |
| `HHPPG046600C1` `/quotations/comp-program-trade-today` | 시장 전체·**장중(당일)** | 외국인 분해가 있는 유일한 프로그램 API 지만 과거 백필 불가 |

- **수급 시장 전체(외국인 매수/매도)는 KIS 에 없다**: `FHPTJ04040000` `/quotations/inquire-investor-daily-by-market`
  은 KOSPI/KOSDAQ 일별을 구간으로 주지만 `{prsn,frgn,orgn}_ntby_tr_pbmn`(**순매수** 백만원)만 있다 — 매수/매도 분해는 종목별 TR 에만 있다.
  그래서 `(foreign_buy + foreign_sell) / total_value` 모양의 리더를 채울 때는 **시장 전체 프로그램 매수/매도 + 시장 전체 거래대금**을 쓰고,
  컬럼명이 `foreign_*` 여도 실제로는 프로그램 전체 값이라는 사실을 마이그레이션 COMMENT 에 남긴다(거짓 라벨링 금지).
- **필수 파라미터는 오류 메시지가 하나씩 가르쳐 준다**: `OPSQ2001 ERROR INPUT FIELD NOT FOUND [FIELD]` 가
  **없는 필드 이름을 그대로** 알려준다 → 한 콜씩 추가하면 3~6콜 안에 요구 파라미터 전부를 확정한다.
  실측: `comp-program-trade-daily` 는 `FID_INPUT_DATE_2`→`FID_INPUT_DATE_1` 순으로, `inquire-investor-daily-by-market`
  은 `FID_INPUT_ISCD`→`_1`→`_2`→`FID_INPUT_DATE_2` 순으로 요구했다(문서 없이도 확정 가능). **`OPSQ2001` 은 권한 문제가 아니다** — 스키마 교정 대상이다.
- **시장 코드로 종목별 엔드포인트를 때리지 마라**: `program-trade-by-stock`·`inquire-investor` 에 `0001`/`1001`/`2001`
  을 넣으면 `rt_cd=0` + **빈 output** 이 온다(성공처럼 보이지만 0행). 시장 집계는 위 표의 시장 전용 TR 로만 된다.
- 경로·TR_ID 카탈로그(문서가 막힐 때): `https://m72x2.com/X2/_PAGE/help/kis_api_list.php` 가
  수백 개 엔드포인트의 `경로 + TR_ID` 쌍을 한 페이지에 준다(예: `comp-program-trade-daily FHPPG04600001`).
  추측 대신 여기서 이름을 확인한 뒤 1콜 프로브한다.

## 3. Naver 금융 (유니버스 시딩 — 키 불필요)

- `finance.naver.com/sise/sise_market_sum` 은 SPA로 전환되어 `page=` 링크가 없다 → 기존 HTML 파서가 **0종목**을 반환한다(위 §1).
- 대체(실측 동작): `https://m.stock.naver.com/api/stocks/marketValue/{KOSPI|KOSDAQ}?page=N&pageSize=100`
  - JSON `stocks[]`에 `itemCode`, `stockName`, `stockEndType`, `marketValue`; `totalCount`로 종료 판단; 페이지는 100건씩(마지막 다음 페이지는 빈 배열)
  - **ETF/ETN 제외는 `stockEndType != 'stock'`** — KOSPI는 이 필터로 2,484행 → 945종목 (시총 상위에 ETF가 섞여 있다). KOSDAQ은 1,820 모두 주식. 합계 약 2,678종목이 실제 주식 유니버스.
- 6자리(`\d{6}`) 코드만 저장 — 우선주/신형 코드가 섞이면 유니버스가 오염된다.

### 3a. 지수 일봉(KOSPI/KOSDAQ) — 키 없이 `siseJson`, 레짐 판정의 전제

레짐 분리(`risk_off` 게이트, 하락장 조건부 측정)를 하려면 **지수 일봉**이 필요한데 종목 시세 테이블에는
지수가 없다. 이때 종목 일별 수익률 중앙값(breadth)을 프록시로 쓰면 **하락일을 과다 분류**해 표본 구성이
달라진다(실측: 같은 기간 하락 표본 655 vs 303) → 프록시는 임시방편이고, 지수를 한 번 받아 두면 된다.

- `https://api.finance.naver.com/siseJson.naver?symbol=KOSPI&requestType=1&startTime=YYYYMMDD&endTime=YYYYMMDD&timeframe=day`
  (`symbol=KOSDAQ` 도 동일). **키·토큰 불필요**, 1콜로 수년치가 온다(실측: 459거래일 × 2지수 = 2콜).
- 응답은 **JSON 이 아니라 작은따옴표 파이썬 리스트 리터럴**이다 — `json.loads` 는 죽는다. `ast.literal_eval`
  로 파싱하고 **첫 행은 헤더**(`['날짜','시가','고가','저가','종가','거래량','외국인소진율']`)이므로 버린다.
  날짜는 `YYYYMMDD` 문자열, 값은 문자열/None 혼재 → 숫자 변환 시 None 스킵.
- 저장은 신규 테이블 `index_daily(index_code, trade_date, open, high, low, close, volume)` + PK 멱등 upsert.
  재실행 시 행수 불변을 확인한다(실측 918행 불변).
- 이것으로 **레짐을 실측 지수로 판정**한다: `close < MA20` 또는 `5일 수익률 <= -3%` → `risk_off`.
  지수 결측은 0/추정으로 메우지 말고 `unknown + 사유`로 남긴다(그 상태의 게이트는 fail-open + 경고 1줄).
- 주의: 지수 일봉은 **종가 기준**이라 장중 레짐 판정에는 쓰지 않는다. 장중 판정이 필요하면 같은 심볼의
  분봉/현재가 경로를 따로 확인하고, 일봉 기준 게이트는 "전일 종가 기준"임을 리포트에 명시한다.

### 3b. 업종(sector) 채우기 — Naver 업종분류가 '종목당 1콜'을 대체한다

`sector` 가 비어 있는 종목이 65%(실측 2,809/4,353)일 때 KIS 로 채우면 `FHKST01010100` output 의
`bstp_kor_isnm`(업종명, 실측 `전기·전자`)을 쓰는 종목당 1콜 = 2,809콜 ≈ 2.7시간이다. Naver 는 **~103콜/1분**으로 끝난다:

- 업종 목록: `GET https://m.stock.naver.com/api/stocks/industry?page=N&pageSize=100` → `groups[{no,name,totalCount}]`(totalCount 로 종료)
- 업종별 종목: `GET .../api/stocks/industry/<no>?page=N&pageSize=100` → `groupInfo.name`(**업종명**) + `stocks[].itemCode`(페이지당 100)
- 6자리 코드만 채택하고 **빈 `sector` 만 UPDATE** 한다 — 일부 스택은 `sector` 컬럼에 상품구분(`ETF`/`ETN`)을 넣어 두므로
  덮어쓰기는 별도 플래그로 분리한다. 실측 결과 결측 2,809 → 135(KONEX·신규·업종 미분류).
- 호출은 기존 `net_guard('naver')` 키를 경유시키고, 주 1회 크론으로 신규상장분만 채운다(멱등).

**업종명을 안 주는 경로(추측 금지)**: KRX `sto/stk_isu_base_info` 의 `SECT_TP_NM` 은 KOSDAQ **소속부**
(`우량기업부`)이고 KOSPI 는 빈 값이다 — 종목기본정보로 업종을 채우려 하지 마라. Naver
`.../stock/<code>/basic`·`/integration` 은 `industryCode`(숫자)만 주고, `/api/industry/<no>` 는 404 다.
이름은 업종 목록/업종별 응답의 `groupInfo.name` 으로만 얻는다.

### 3c. 상권·자영업 매출(대안 데이터) — 어디가 열려 있고, 모델에 쓸 수 있나

  자치구·행정동·상권×업종 추정매출(신한카드 결제 + 보정비율), 무료 키 ② 공공데이터포털
  「서울시 상권분석서비스(추정매출_자치구)」·「경기도 발달/골목상권 추정매출」(JSON+XML, KSIC 10차, 자동승인)
  ③ 신한카드 DataBada(업종별 매출·신규/해지 매장)는 **B2B 심사·계약 대상**이라 무료 오픈API 로 가정하지 마라.
- 소상공인 상권정보(상가업소 200만건)에는 **매출이 없다**(업소·업종 정보만) — 매출 원천으로 쓰지 않는다.
- **모델 적합성 판정을 수집보다 먼저 한다**: 지역×업종×분기 매출은 시장/섹터 레벨이라 종목에 붙이면 같은
  업종 종목이 동일값이 되어 횡단면 변별력이 0 이다(§11 의 시장레벨 판정과 같은 이유, 계약상 횡단면 피처 부적격).
  종목 차별화는 사업보고서 세그먼트 매출·점포수와 결합해야 성립하고 그건 별도 프로젝트다 → 기본 용도는
  **소비재 레짐/섹터 게이트·대시보드**이고, 갱신이 분기라 일 단위 매매 신호에는 못 쓴다.
- 키가 없으면 그건 사람 단계다(data.go.kr·서울 열린데이터광장 키는 무료·자동승인). 키를 받으면 크론을 걸기 전에
  **1콜 프로브**로 응답 필드(업종코드·매출금액·기준분기)를 확인하고, 종목 피처가 아니라 게이트/리포트 소비처를
  먼저 정한다 — 쓸 곳이 없는 수집은 커버리지만 늘린다.

### 3d. 장중 실시간 시세·지수 — "오늘 X 테마 왜 올랐나" 확인용 (키 불필요)

테마·섹터 급등 원인을 물으면 기억·뉴스 요약만으로 답하지 말고 **① 실제 등락 ② 지수 동시 등락 ③ 기사 원문**을 붙인다.

- 종목: `GET https://polling.finance.naver.com/api/realtime/domestic/stock/<code>,<code>,...`(콤마로 다종목 한 콜)
  → `{time, datas:[...]}` 이고 항목은 `itemCode`·`stockName`·`closePrice`·`compareToPreviousClosePrice`·
  `fluctuationsRatio`(**문자열 % — 정렬·비교 전 `float()` 필수**)·`accumulatedTradingValue`·`marketStatus`(`OPEN`)·`localTradedAt`.
- 지수: 같은 호스트 `/api/realtime/domestic/index/KOSPI,KOSDAQ` → `datas[]` 의 현재값·등락률.
- **`m.stock.naver.com/api/stock/<code>/integration` 은 현재가·등락률 필드를 주지 않는다**(키 구조가 다름) — 현재가 용도로는 위 폴링 경로를 쓴다.
  `/basic` 도 필드를 확인한 뒤에만 쓴다.
- **테마 판정은 대형주와 초소형 테마주를 나눠 본다.** 실측: 지수 −5.5% 인 날 한 테마에서 상한가(+30%)·+24%·+20% 소형주가 나온 반면
  대표 대형주 2개는 −3% 였다 — breadth 없이 "테마가 올랐다"고 쓰면 오보다. 오전 10시 +4~5% 가 11시 반 +0.2/−0.5% 로 밀리는 일도 흔하므로
  **조회 시각을 반드시 적는다**.
- 원인은 ① 개별 재료(수주·공급계약·목표주가 상향) ② 수급 순환(다른 업종 투매 → 규제 리스크 낮은 테마로 이동)
  ③ 이벤트 기대(전시회·신제품) 로 나누고, 각각에 매체·핵심 문장 인용을 붙인다. 마지막에 "우리 후보/규칙에 걸렸는지"(피드 종목 대조,
  상한가·급등 필터 여부)를 한 줄로 붙이면 보고가 행동으로 이어진다.

## 4. KRX OpenAPI (진단 — 레포에 따라 미사용일 수 있음)

- 호출 형태: `https://data-dbg.krx.co.kr/svc/apis/<서비스>/<api>?basDd=YYYYMMDD`, 헤더 `AUTH_KEY: <key>` → JSON `OutBlock_1`. 토큰 교환/서명 없음.
- 서비스별 경로 예: `sto/stk_bydd_trd`(유가증권 일별매매), `sto/ksq_bydd_trd`(코스닥), `idx/kospi_dd_trd`(지수).
- 키가 승인되지 않은 상태의 전형적 응답이 바로 §1의 표 첫 줄(401 JSON)이다 — **경로가 맞다는 증거이므로 경로를 바꿔가며 헤매지 말고 콘솔 승인을 확인**한다.
  - 남은 단계는 4단계 중 3단계다: openapi.krx.co.kr 로그인 → 마이페이지 API 인증키 신청/발급내역(`/contents/OPP/MYPG/mypage/OPPMYPG001.cmd`)에서 키·유효기간(1년) 확인 → 서비스 목록(`/contents/OPP/INFO/service/OPPINFO004.cmd`, 주식 카테고리 `/contents/OPP/USES/service/OPPUSES002_S1.cmd`)에서 **API 활용신청** → 관리자 승인(보통 1일). 인증키 발급만으로는 호출되지 않는다 — 인증키는 “신원”, 활용신청은 “서비스별 권한”이다.
  - 신청할 서비스: 유가증권 일별매매정보(`sto/stk_bydd_trd`), 코스닥 일별매매정보(`sto/ksq_bydd_trd`), 선택적으로 종목기본정보(유니버스/상장주식수 보강)·지수 일별시세(시장 레짐 피처).
  - 승인 확인은 1콜 프로브로 한다(하루치 1마켓만 호출) — `respCode 200`과 종목 행이 오면 승인 완료, `Unauthorized API Call` 그대로면 대기 중이다. 헤더/호스트 변형을 손으로 시도하지 말고 이 스킬의 `scripts/krx_probe.py`를 쓴다(JSON 응답이 오는 순간 멈춤).
- **차단 이력이 있는 소스는 보수적 호출 정책을 러너의 기본값으로 박는다**: 호출 간 지연+지터, 실행 간 최소 간격(공유 상태파일에 기록해 크론·수동 실행이 겹쳐도 몰아치지 않게), 실행당 호출 상한, 차단 신호에서 재시도 없이 즉시 종료, 날짜/구간별 진행파일로 재개. 파라미터는 전부 env로 빼서 상향 조정에 코드 수정이 필요 없게 한다.
- **"가격이 빈 행 = 휴장" 판정을 최근 날짜에 적용하면 데이터를 영구히 잃는다.** 일별매매정보는 D-1(실제로는 D-2)까지 반영되므로, 아직 공표 전인 날짜를 조회하면 전 종목 가격이 빈값으로 온다. 이걸 휴장으로 파일에 기록하면 그 날짜는 이후 모든 러너가 건너뛴다(휴장 캐시가 스킵 근거가 된다). 러너는 ① 종료일 기본값을 `today`(−1)가 아니라 "DB 최신일 다음날" 기준으로 잡고, ② 최근 2일 이내 날짜는 휴장 확정을 보류해 다음 실행에서 재확인한다. 휴장일은 파일에 기록하기 전에 그 날짜가 이미 시세를 가진 적이 없는지도 확인한다.
- **무거래·거래정지 종목도 행으로 온다** — 시가·고가·저가가 0, 거래량 0, 종가만 기준가로 채워진 행이 섞인다(1년 패널에서 579종목·28,282행, 최근 일평균 약 113종목). 종가만 보고 넘기면 수익률·MA 위치·변동성 피처가 0 기준으로 계산되므로 소비 측(피처 빌더)에서 `open=high=low=0` 행을 제거하거나 플래그를 세운다.
- pykrx는 이 OpenAPI가 아니라 `data.krx.co.kr/comm/bldAttendant/getJsonData.cmd`(레거시 JSON)를 쓴다. 그 경로는 WAF로 IP 차단된 이력이 있고 "KRX 수집이 죽었다"의 원인이 보통 이것이지만, **차단 여부는 IP대역·시점에 따라 다르다** — 같은 호스트의 보조 수집기가 pykrx로 정상 수집 중인 경우도 있다(실측). "차단됐다"를 전제로 설계하지 말고 1콜 프로브로 현재 상태를 확인한 뒤 경로를 고정한다. 같은 데이터를 주는 경로가 둘 이상이면 **호출 수가 적은 쪽을 기본으로, 실패 시 다른 쪽으로 폴백**한다.
- 경제성: 일별매매정보는 **시장 1콜로 그날 전 종목**이 온다(KOSPI `sto/stk_bydd_trd` + KOSDAQ `sto/ksq_bydd_trd`) → **날짜당 2콜, 1년 약 500콜**(실측 247거래일 = 494콜, 3.0s+지터로 57분). 같은 기간을 KIS 종목당 1콜로 받으면 2,700콜 이상이므로, 승인돼 있다면 과거 일봉 백필은 이 경로를 우선한다.
- **승인 카탈로그로 "이 계정에 무엇이 열려 있나"를 먼저 확정하라.** 실제로는 몇 묶음이다: 지수(시리즈·파생상품지수·ESG) ·
  일별매매정보(유가/코스닥/코넥스/신주인수권 2종) · 종목기본정보 · ETF/ETN/ELW · 채권 3시장 ·
  **파생(선물·주식선물 유가/코스닥·옵션·주식옵션)** · 원자재(석유/금/배출권) · ESG 증권상품.
  **투자자별 거래실적(수급)·공매도·프로그램매매는 이 카탈로그에 없다** → 그 피처군을 KRX 로 풀려고 서비스 신청을 기다리거나
  경로를 뒤지지 말고, 즉시 KIS·다른 소스로 피벗한다(§1 표의 401 진단과 함께 판단).
- **없는 엔드포인트는 404 JSON 으로 바로 드러난다**: `{"respMsg":"[svc/apis/...] API referenced by the path does not exist.","respCode":"404"}`.
  경로 이름을 추측해 여러 개를 던져보지 말고, 살아있는 경로 1콜(`sto/stk_bydd_trd?basDd=YYYYMMDD`)로 키·승인을 먼저
  확인한 뒤 카탈로그에 있는 이름만 시도한다(프로브는 1~2콜로 제한).

## 13. 호출 정책은 프로세스 밖에서 강제하라 (IP 차단 회피의 핵심)

러너마다 지연을 넣는 것만으로는 차단을 못 막는다 — **지연은 프로세스 안에서만 유효하다**.

- 같은 호스트/앱키에 두 프로세스가 겹치면(크론+수동, 크론 두 개) 실제 호출률은 **2배**가 되고,
  두 로그 모두 정상으로 보인다. 차단은 그 다음에 온다.
- 해법: **호스트(또는 자격증명) 키별 상태파일 + `flock`** 으로 ①프로세스 간 최소 간격
  ②일일 예산 ③차단 신호 쿨다운(다른 프로세스에 즉시 전파) ④이벤트 로그를 강제한다.
  구현 예: analyist_dd `scripts/net_guard.py`. 락을 잡고 대기하므로 겹친 실행이 직렬화된다.
- **예산은 '일일' 상한으로 분리하라** — 러너별 실행 상한(예: `KIS_MAX_CALLS`)을 그대로 예산으로
  쓰면 분봉처럼 콜이 많은 러너가 조용히 토막난다(로그엔 `완료 0건`처럼 보인다). 기본은 0(무제한),
  하루 상한을 실제로 강제할 때만 켠다.
- **러너가 자체 sleep 을 가질 때 가드가 켜져 있으면 그 sleep 을 생략**하라. 둘 다 돌면 같은 간격을
  두 번 기다려 수집이 2배 느려진다(정확도는 그대로, 속도만 손해).
- **가드는 fail-open** 이어야 한다: 상태파일을 못 쓰면 예외 없이 기존 동작으로 폴백한다(수집을 막지 않는다).
  **단 '폴백'은 '무력화'와 같지 않다 — 폴백 사실을 반드시 이벤트로 남기고 중복을 억제하라.** 실측(2026-10-03):
  크론(=`root`)이 만든 `0644` 상태파일을 사용자 프로세스가 못 열어 `PermissionError` → 가드가 조용히
  **아무 간격도 강제하지 않은 채** 수집을 통과시켰고(가드가 없는 것과 동일) 같은 오류를 9회 기록했다.
  처방: ① 상태파일을 `0666` 으로 생성(+생성 후 `chmod` 시도) ② 그래도 막히면 uid 별 파일(`<키>.json.u<uid>`)로
  내려가되 `guard_fallback` 이벤트를 남긴다(다른 uid 와의 직렬화가 약해졌음을 숨기지 않는다)
  ③ 같은 오류는 프로세스당 1회만 기록. 운영 조치로 상태 디렉터리 `0777`·파일 `0666` 로 맞춘다.
- **차단 판정은 구조화된 신호로만 하라 — 페이로드 문자열 검색은 숫자에 걸려 오탐한다**: 실측(2026-10-03)
  `_blocked_looking` 이 응답 dict 를 `str(data)` 로 만들어 `"403"` 을 찾았는데, 응답에는 종목코드·접수번호
  같은 긴 숫자열이 있어 `403` 이 우연히 포함된다(예: `corp_code` `0040304`) → 정상 응답을 차단으로 오판해
  900초 쿨다운 + 그날 적재 0행. 규칙: ① 응답이 dict 면 **상태 필드**로만 판정한다(예: DART `status`
  `000` 정상 · `013` 데이터 없음 · `020` 요청 제한 · `100/101/102` 키 오류 · `800/900` 시스템)
  ② 예외면 `HTTP 403` · `403 Client Error` · `<html` 처럼 **HTTP 맥락이 있는** 패턴만 본다
  ③ 상태코드가 '요청 제한'이면 그때만 쿨다운을 걸어 전 프로세스에 전파한다. 회귀 테스트로 '정상 payload 안에
  403 숫자가 있어도 차단 아님'을 고정하라(오탐은 수집을 조용히 멈추므로 1회로 충분히 비싸다).
- **테스트에서는 env 로 끈다**(`NET_GUARD_DISABLE=1`, conftest 에서 설정). 안 그러면 테스트가 운영
  상태파일을 오염시키고 운영 지연(3s/콜)을 물려받으며, `sleep_fn` 주입을 검증하는 테스트가 깨진다.
  이벤트 로그 경로도 env 로 오버라이드 가능하게 만들어야 스모크 테스트가 실 감사로그를 더럽히지 않는다.
- **검증은 '프로세스 간'을 실측하라**: N개 프로세스 × M콜을 동시에 돌려 합친 타임스탬프의 최소 간격이
  지연 이상인지 본다. 가드 OFF 대조군도 함께 재야 테스트가 비어있지 않음이 증명된다(실측: ON 0.25s / OFF 0.000s).
- 배선 후 **"차단 응답 뒤 다음 호출이 HTTP 를 보내지 않았는지"를 호출수로 확인**한다 — 그게 쿨다운 전파의 증거다.
- 자체 `curl` 을 쓰는 러너도 **같은 앱키 키를 공유**하게 묶어라(안 묶으면 그 러너만 규칙 밖에서 때린다).
- **JSON API 가 HTML(WAF 차단 페이지)을 주면 성공으로 읽지 마라** — `body.startswith("<")` 검사를
  파서 앞에 두고 차단으로 분류한다. 0건/빈 목록으로 흘리면 "데이터 없음"으로 오독된다.
- **403 을 재시도 루프 안에 넣지 마라**: `if status in (403, 429) or status >= 500: sleep; continue` 같은
  코드는 마지막 시도에서 루프를 빠져나가 **빈 목록을 반환**한다(실측: naver_daily_backfill). 403 은 즉시 raise.
- **중단은 '쿼터 초과'와 같은 급으로 올려라**: 수집 루프가 이미 `quota_hit` 분기로 멈추게 되어 있으면
  정책 중단도 같은 코드 집합(`RATE_LIMIT_CODES`)에 넣어 그 분기가 멈추도록 한다. 루프별로 그 분기가
  있는지 확인하라(분봉 수집기에는 없어서 정책 중단을 무시하고 계속 돌았다).
- **"오늘 봉 1건"이 만드는 영구 결손**: 증분 시작일을 `MAX(trade_date)+1` 로 잡는 러너는 다른 작성자가
  **당일 봉을 1행만** 넣는 순간 구간이 공집합이 되어(`수집 구간 없음`) 그 전날 봉이 영원히 안 채워진다.
  처방은 **행수 기준 '덜 찬 날'부터** 시작하는 것(예: 최근 7일 창에서 `count < 2000` 인 가장 이른 평일,
  휴장 파일·주말 제외) + 같은 로직을 단위 테스트로 고정. 재수집은 멱등 upsert 라 비용이 낮고,
  KRX 응답의 빈 시세일은 휴장 파일에 기록되므로 루프가 자기종료한다.
- **차단은 감지로 끝나지 않는다 — 보이게 만들어야 한다.** 가드가 중단해도 수집기는 조용히 멈추고
  크론 로그엔 '완료'처럼 남는다 → 상태·이벤트를 읽어 ①쿨다운 중인 호스트 ②예산 소진/임박
  ③최근 N시간 차단·전송오류 ④가드 자체 오류를 한 줄씩 보고하는 경보 틱을 둔다(문제 없으면 침묵,
  같은 경보는 상태파일로 중복 전송 차단). 도구 예: analyist_dd `scripts/net_guard_alert.py`.
- **쿨다운 해제는 명령으로 하고 사유를 남긴다.** 해제는 "다시 때려도 된다"는 선언이므로, 원인을
  확인한 뒤 `net_guard.py clear --key <키> --note <사유>` 로 풀고 이벤트 로그에 흔적을 남긴다.
  상태 파일을 지우거나 손으로 편집해 숨기지 않는다(다음 차단의 원인 추적이 불가능해진다).

## 12. ECOS (한국은행 경제통계) — 금리·물가·스프레드

매크로 피처의 원천. 키는 `ECOS_API_KEY` 하나이고, **키가 유효한데도 전부 0 이 나오는 실패 모드가 4가지** 있다(전부 URL·코드 문제이지 키 문제가 아니다).

- URL 고정 형태: `https://ecos.bok.or.kr/api/StatisticSearch/{KEY}/json/kr/{start}/{end}/{STAT_CODE}/{CYCLE}/{시작}/{끝}/{ITEM}`.
  **`StatisticSearch` 세그먼트를 빠뜨리면 게이트웨이가 HTTP 404(빈 본문)를 돌려주고, 코드는 그것을 "키 무효"로 오인한다** —
  키 재발급을 요청하기 전에 URL 조립부터 본다.
- **검증된 통계코드**(실응답 기준, 추측 금지): 기준금리 `722Y001`/D/`0101000` · 국고채3년 `817Y002`/D/`010200000` ·
  회사채3년 `817Y002`/D/`010300000` · CPI `901Y009`/M/`0` · PPI `404Y014`/M/`*AA`.
  국고채·회사채는 **같은 표(시장금리 일별)의 다른 ITEM** 이다. 없는 조합은 HTTP **200** + `INFO-200 해당하는 데이터가 없습니다` 로
  조용히 실패한다(§1 표의 "200 + 0건" 줄) — 상태코드만 보면 성공으로 오독한다.
- **요청 1회 = 최대 1,000행**이고 초과분은 잘린다 → 일별 시리즈는 **연 단위로 나눠 호출·병합**한다.
  그러지 않으면 응답이 과거에서 끊겨 가장 중요한 최신 값이 사라진다(3년 일별 ≈ 1,000영업일).
- **YoY 피처에 지수 레벨을 넣지 마라.** `cpi_yoy`/`ppi_yoy` 같은 이름의 피처에 지수(예: `120.05`)를 넣으면
  값이 비정상(non-stationary) 시계열이라 모델에는 시간 추세로만 작동한다 → `(현재/12개월 전 − 1)×100`.
  스프레드도 하드코딩 상수(3.5 등)를 기준선으로 쓰지 말고 실제 정책금리 기준으로 계산한다.
- 적재는 `(지표명, 날짜)` 유니크에 멱등 upsert 로 하고, **반드시 두 날짜 이상에서 피처값이 달라지는지** 확인한다
  (상수면 as-of 배선이 끊긴 것이지 데이터가 없는 게 아니다). FRED 계열(USD/KRW·JPY/KRW·CNY/KRW·WTI)은 키 없이 같은 러너로 채워진다.

## 8. KIS 엔드포인트 전수 프로브 ("무엇을 수집할 수 있나" 질문)

"이번에 KIS에 상품을 추가했다는데 수집 가능한가" 류의 요청은 **엔드포인트 카탈로그를 1콜씩 돌려** 확인한다(추측·문서 인용 금지).
프로브 스크립트: `scripts/kis_probe_all.py`(레포 `services/kis-collector` 의 클라이언트를 재사용, 호출 간 1.2s), 결과 카탈로그: `references/kis-endpoint-catalog.md`.

- **국내주식 엔드포인트는 ETF/ETN에도 그대로 통한다** — 별도 상품이 아니다. ETF가 안 돌고 있으면 대개 유니버스(`stocks`)에 없기 때문이다.
- **원유(유가) 노출은 해외선물이 아니라 해외주식 경로로 먼저 확인한다.** 해외선물 시세 TR 변형은 실측에서 전부 `EGW-UNKNOWN` 이었다(별도 신청 필요 가능성) — 반면 해외주식 현재가/일봉은 USO 같은 원유 ETF 심볼로 정상 응답한다. 어느 쪽인지 1콜로 가린 뒤 보고한다(미신청으로 단정하지 말고 "이 경로는 되고 저 경로는 안 된다"로 보고 + 신청 필요 여부 확인).
- 오류를 **세 갈래로 구분해 보고**한다: `OPSQ2001` = 필드명 오류(권한 문제 아님, 파라미터 교정 대상) / `EGW-UNKNOWN`(응답에 코드 필드가 없어 클라이언트가 붙인 값) = 경로·TR_ID 불일치 또는 미신청 / 권한 거부 메시지 = 콘솔 신청 필요.
- **경로 하나만 보고 "지원 안 함"으로 결론내지 말 것.** 거래량 순위는 `/uapi/domestic-stock/v1/quotations/volume-rank` 가 맞고 `/ranking/volume` 은 실패한다 — 같은 API의 구·신 경로 차이다. 문서·기억의 경로가 실패하면 변형 2~3개를 1콜씩 돌려 확정한다.

## 9. 종목 마스터 파일 (ETF 유니버스 시딩용)

> ETF **시장가/NAV 괴리율** 수집(레버리지·인버스 계측)은 `references/etf-nav-and-premium.md` —
> 네이버 ETF 목록 **1콜(EUC-KR)** 로 전 종목 `nowVal`·`nav` 를 받는 경로, 장외 스냅샷 오독 주의, 손익분기 계산.

`https://new.real.download.dws.co.kr/common/master/{kospi_code.mst.zip,kosdaq_code.mst.zip}` 를 받아 **그룹코드로 종류를 가른다**:
ETF = `EF`, ETN = `EN`, 외국주권 = `FS`, 수익증권 = `BC`. `idxcode.mst.zip` 는 지수코드라 ETF 목록이 아니다.
- 마스터는 `cp949` 인코딩이고 레코드 폭이 고정이 아니다 → 정규식(코드 6자리 + 이름 + 그룹코드 2자)으로 파싱한다. **고정 오프셋 슬라이싱은 일부 라인에서 어긋나 그룹코드를 오독한다.**
- 이 파일로 ETF/ETN을 `stocks`에 시딩하면 기존 시세 수집 경로가 그대로 ETF를 수집한다(스키마 변경 없음).
- **시딩 순서를 지킨다 — 유니버스가 코드순 정렬이면 신규 종목 삽입이 기존 창을 밀어낸다.** `ORDER BY stock_code LIMIT 50` 류 유니버스(학습·백테스트·스크리너)는 종목이 추가되는 순간 다른 집합이 된다 → ① 종류 컬럼(예: `instrument_type`, 기본 'STOCK') 추가 ② 종목 전용 조회에 `instrument_type='STOCK'` 필터 추가 ③ **삽입 전후 유니버스 쿼리 결과를 diff로 완전 동일 확인** ④ 그 다음 삽입. 순서를 뒤집으면 진행 중인 학습 실험이 조용히 다른 표본으로 돌아간다.
- 시딩 검증은 종류·시장별 건수(`GROUP BY instrument_type, market`) + 컬럼 존재 + 대표 종목 1~2개의 시세 1콜 수집으로 한다. 전량 백필은 별도 작업으로 분리한다(시딩 검증과 섞으면 다른 실험과 자원을 다툰다).
- 대량 DDL이 멈추면 장기 `idle in transaction` 커넥션을 의심한다 — 다른 컨테이너의 트랜잭션이 락을 쥐고 있으면 `pg_stat_activity`에서 찾아 그 백엔드만 종료한다(컨테이너 재기동은 그 안의 작업을 죽인다).

## 10. DART OpenAPI (공시·재무)

- env: `DART_API_KEY`(쿼리 파라미터 `crtfc_key`). 엔드포인트: `https://opendart.fss.or.kr/api/list.json`(공시 목록), 재무제표 API. 소비처는 공시 수집기(news-analyzer)·재무 수집기(yfinance-collector)·재무 백필 러너.
- **성패는 HTTP 코드가 아니라 바디의 `status`로 판정한다**: `"000"` = 정상(`total_count`·`list[]`), 그 외 코드는 실패로 집계한다. 오류도 HTTP 200으로 오기 때문에 상태코드만 보면 성공으로 오독한다.
- `status=013`(해당 연도 보고서 없음)은 정상 스킵이다 — 백필 로그에서 이 값과 “연속 실패” 카운트를 오류로 읽지 않는다.
- 계정과목명은 `매출액/영업이익/당기순이익`이 IS·CIS 양쪽에 나타나고 `(손실)` 접미사·공백 변형이 있으므로 **정규화(괄호 내용·공백 제거) 후 매칭**한다. 손익은 IS/CIS 모두, 재무상태는 BS만 허용.
- 재무 백필 러너 설계: 연간 사업보고서 1콜로 당기/전기/전전기 3개년을 뽑아 **종목당 1콜**로 끝낸다. 최소 1.5s+지터, 일일 예산(기본 2,500콜) 초과 시 중단 후 체크포인트 재개, 429/5xx 지수 백오프, 연속 실패 서킷 브레이커.
- **스코프 함정**(§2와 같은 원인): 대상이 `corp_mapping ∩ market_data`로 짜여 있으면 시세가 비어 있는 신규 배포에서 대상이 **0종목**이 된다 → 시세 테이블이 비면 `stocks` 유니버스로 폴백하고, dry-run으로 대상 수를 먼저 확인한 뒤 실행한다.
- **공시 목록 수집과 재무 파싱은 별개 러너이고, 파서가 스케줄에 없는 경우가 실제로 있다.** `disclosures.rcept_dt` 는
  매일 갱신되는데 `financial_statements.report_date` 가 반기에서 멈춰 있으면(3분기 보고서가 목록에 1,181건 있어도)
  원인은 파서 미배선이다 — `scripts/dart_financial_backfill.py` 는 `--reprt-code 11014`(3분기)·`--year` 를 사람이 줘야
  도는 수동 도구이고, 크론 grep 0건이면 아무도 안 돌린다. 복구는 1회 백필(종목당 1콜, `--max-calls` 예산 필수) 후
  해당 `report_date` 행수로 판정하고, 재발 방지는 분기 1회 크론이다. 재무비율 피처는 이 테이블을 읽으므로
  파싱이 멈춘 동안에도 '정상 갱신'으로 보인다(6월 재무 기준으로 매일 재계산).
- **분기 크론 래퍼는 '이번 달에 지금 제출되는 보고서'를 스스로 골라야 한다**: 3·4월→`11011`(사업보고서,
  year-1) · 5·6월→`11013` · 8·9월→`11012` · 11·12월→`11014`, 그 외 달은 침묵. 월 2회(예: 15·28일) 돌려
  제출 지연·재제출을 흡수하고, 상태파일은 `backfill_state_<reprt_code>_<year>.json` 으로 **래퍼가
  `--state-file` 을 명시해** 넘긴다(§11 커서 항목의 공유-상태파일 사고와 같은 이유). 러너는 진행파일로
  이미 끝낸 종목을 건너뛰므로 재실행이 싸다.
- **A유형(정기공시) 주간 백필은 200콜 예산으로 최근 창에 못 미친다 — 그 결과가 재무 피처에 나타난다**(실측
  2026-11-21~22): 수동 정기 백필이 18:20 WSL 종료로 중단되자 최근 2개월 A 공시가 비어 `disclosures` 에
  분기보고서가 없는 종목이 생겼고, 재무비율 빌더는 as-of 접수일을 못 붙여 **직전 반기(semi)로 남겼다**
  (quarter 반영 1,044 vs 공시 보유 2,742). 처방은 `--since <최근 2개월> --types A` catch-up 1회(실측
  35콜·1,633행) → 재무비율 빌더 재계산(quarter 6,726 → 13,504행, 반영 종목 1,044 → 2,402).
  판정 지표는 `disclosures` 의 `분기보고서 (YYYY.MM)` distinct 종목 수와 `financial_ratio_features` 의
  `period_type='quarter'` 종목 수를 나란히 보는 것이다(둘의 차이는 격자 밖 ETF·비상장).
- **재무비율 빌더는 `DELETE FROM <table>` 전량 후 재삽입이다** — 실행 전에 `pg_dump -t financial_ratio_features`
  로 백업하라(실측 868K행 ≈ 34MB gzip). 중간에 죽으면 테이블이 비므로 재실행이 곧 복구이고(멱등),
  `불변식 위반: rcept>D / report>D` 줄이 0 인지까지 확인해야 누수 없는 as-of 가 증명된다.

### 10a. 공시 유형(pblntf_ty) — 목록 API 의 기본값은 "한 종류만"이다
`list.json` 은 `pblntf_ty` 로 공시 종류를 고른다. 수집기가 한 값으로 고정하면 **행수·신선도는 전부 초록인데
값의 종류가 한 클래스뿐**인 상태가 된다(다운스트림 이벤트 피처는 정의상 전부 0).

| 코드 | 내용 | 여기서 나오는 피처 계열 |
|---|---|---|
| **A** 정기공시 | 사업·반기·분기보고서(+정정) | 재무제표 기반 비율, 공시 지연(rcept_dt) |
| **B** 주요사항보고서 | 유상증자·CB/BW·합병·분할·최대주주변경·자기주식·소송·영업양수도 | `event_capital_increase`·`event_cb_bw`·`event_mna`·`event_treasury`·`event_litigation` |
| **D** 지분공시 | 대량보유·지분 변동 | `event_stake_change`, 지분율 대체 소스 |
| **E** 기타공시 | 임원·대표이사 변경 등 | `event_exec_change` |
| **I** 거래소공시 | 수주·공급계약·신제품·잠정실적 | `event_contract`·`event_new_product`·`event_realized` |

- **감사는 행수가 아니라 `COUNT(DISTINCT report_nm)`(또는 유형별 건수)으로 한다.** A 만 돌리면
  유형 수가 십수 개에 머물고 유상증자·계약 공시가 0건이다(i.e. 이벤트 피처 19개가 조용히 상수).
- 유형 추가는 `--types A,B,D,E,I` 처럼 **순회 파라미터**로 만들고 기본값은 기존 동작(A)으로 둔다.
  유형×월 이중 루프가 된다.
- **재개 지점을 (유형, 월) 단위로 저장하라.** 러너가 매번 `--since` 부터 다시 돌면 앞서 끝낸 유형의
  과거 월을 재탐색하며 **콜 예산을 태우고** 정작 미수집 유형에 도달하지 못한다(실측: 재시작마다 D 의
  앞 9 개월을 다시 훑어 1,200콜 소진). 멱등 upsert 라 데이터는 안전하지만 시간이 사라진다.
- **`total_count` 를 넘는 `page_no` 는 마지막 페이지를 반복 반환한다.** 종료 조건을 `len(items) < page_count`
  로만 잡으면 같은 페이지를 영원히 돈다(실측: 214페이지를 돌고 신규 945행). `page_no × page_count >= total_count`
  로 종료하고, 같은 `rcept_no` 가 반복되면 중단하는 **이중 안전장치**를 둔다.

### 10b. 공시 → 이벤트 피처 (희소성부터 측정하라)
이벤트 피처는 `(종목, 날짜)` 격자에 **직전 N거래일 창의 건수**를 쓸어 담는 형태가 된다.

- **as-of: 창을 `D-N .. D-1` 로 잡고 당일(D)을 빼라.** 장 마감 후 접수된 공시가 그날 종가 기준 피처에
  섞이는 누수를 구조적으로 차단한다. 비거래일(주말·휴일) 접수분은 **다음 거래일**에 귀속한다.
- **결측은 0 이다.** "0 인 행은 저장하지 않는" 방식이면 리더는 결측을 0 으로 채워야 하고(그게 곧
  "창 내 이벤트 없음"), 저장한 행만 보면 매칭률이 10% 대로 보인다(정상).
- **피처를 모델에 넣기 전에 유형별 non-zero 행수 비율을 먼저 측정한다.** 원천을 절반만 수집한 상태에서는
  일부 유형이 정확히 0 이고 나머지도 0.x% 다 — 그 상태로 학습에 넣으면 기대 효과가 없고 "왜 AUC 가 그대로인가"
  에 시간을 쓴다. 먼저 수집을 완주하고, 그 다음에도 희소한 유형은 **밀도 높은 묶음**(자금조달/지배구조/영업)으로
  재구성한다.
- **패널 반영은 전체 재빌드가 아니라 컬럼 패치로 한다**: 기존 패널의 `X` 에 새 컬럼을 append 하고
  `feature_names` 를 늘려 저장하면 같은 행·같은 다른 피처 위에서 A/B 가 되므로 델타가 곱 임팩트다.
  append 전에 **컬럼별 non-zero 수와 종목당 유니크값**을 출력해 죽은 컬럼을 넣지 않았는지 확인한다
  (유니크 계산은 numpy 마스크로 — 리스트 비교는 항상 False 라 전 컬럼이 '상수'로 잘못 찍힌다).

## 6. 백필·수집 상태 감사와 보고

"지금 백필 상태 알려줘" 요청은 감사 절차로 받는다 — 감사 없이 러너 로그만 보면 틀린 답이 나온다
(러너는 최근 창만 보고, 공실은 조용히 넘어간다).

1. 기대 거래일(평일 − 휴장) = 실제 `count(DISTINCT trade_date)`인지, 공실·부분 적재일이 0인지 수치로 확인한다.
2. 휴장 파일이 스스로 맞다고 가정하지 않는다 — 결측 평일은 1일 2콜 프로브로 휴장/공실을 분류해 확정한다.
3. 크론은 로그 파일 유무로 판정하지 않는다(로그 없음 = 미실행, 재부팅이 원인인 경우가 많다).
   재부팅·재가동 직후 "확인해줘" 를 받으면 ① `uptime; date` 로 부팅 시각을 먼저 잡는다 — **그 시각보다 이른 크론 회차는 실행되지 않았다**(로그에 그 회차 기록이 있으면 재부팅 전에 돌았으니 재실행하지 않는다) ② `systemctl is-enabled cron docker <수집 서비스>` 로 자동 복귀 보장을 확인 ③ **크론이 가리키는 스크립트 실존을 검사**한다 — 없는 스크립트를 참조하는 항목은 조용히 실패한다: `for f in $(grep -oE '/home/[a-z]+/cron/[a-z_]+\.sh' /etc/cron.d/<name> | sort -u); do [ -x "$f" ] && echo "OK $f" || echo "MISSING $f"; done` ④ DB 최신일이 D-1이면 정상이다(일별매매는 D+1 공표) — 당일 봉 부재를 수집 실패로 오판해 손으로 재실행하지 않는다 ⑤ 수집 자격증명은 1콜 프로브(토큰+대표종목 시세)로 살아있는지 확인한다.
4. 보고는 숫자 → 수집 경로 → 미완 데이터 → 리스크 순서로 분리하고, 말미에 번호 매긴 다음 작업 후보 + 권장 1순위를 붙인다.

- **"무변동/동결" 행은 느슨하게 세면 과대집계된다.** `시가=전일시가 AND 종가=전일종가` 만 보면 정상적인 무변동일까지 잡힌다(실측 3.78%). 진짜 이상치는 `시·고·저·종가 + 거래량` 이 전부 직전 거래일과 같은 행(3.25%)이고, 그중 **거래량>0 인 것만 의심**한다. 상위는 900xxx/950xxx 외국기업 예탁증권처럼 원래 거래가 드문 종목이다 — 이 필터로 다시 세기 전에는 "데이터가 오염됐다"고 보고하지 않는다.
- **커버리지(행수·거래일 수)와 신호 유무는 다른 축이다.** "백필은 다 했다는데 왜 지표가 안 나오나" 질문에는 ① 커버리지 실측 ② 라벨·표본 특성 ③ 과거 기준값의 측정 방식(구간·split·다중비교) 세 축으로 답하고, 데이터 품질을 원인으로 지목하려면 재현 가능한 근거 쿼리와 함께 제시한다.
- 테이블에 **작성자가 둘 이상**이면(정식 수집기 + 스크래핑/Yahoo 수집기) "DB 최신일+1 ~ 어제" 증분이 당일 부분봉 때문에 막힌다 — `max(trade_date)`가 오늘이면 구간이 비어 `수집 구간 없음`으로 조용히 0건이 된다. 감사는 `max(trade_date)`가 오늘인지 먼저 보고, 오늘이면 부분봉 작성자를 찾아 당일 기록을 막는다(또는 증분 기준을 고정 창으로 바꾼다).
- **적재 위생 가드는 저장소 계층에 넣는 것으로 끝나지 않는다 — 같은 테이블의 모든 writer 에 같은 플래그를 건다.**
  감사·가드를 붙일 때 `grep -rn "INSERT INTO <table>" --include=*.py --include=*.sh .` 로 작성자를 **전부 열거**하고,
  저장소/ORM 계층 밖에서 raw SQL 로 쓰는 경로(특히 쉘 러너 안 heredoc 파이썬)를 찾아 동일 정책(기본 `DO NOTHING` + `*_OVERWRITE=1` 예외)을 적용한다.
  계층에만 가드를 넣은 상태에서는 나머지 writer 가 정책 밖에서 공식 수집분을 스크래핑 값으로 되돌려 놓는다.
- **"넣을 게 없었다" 는 no-op 실행을 실패로 읽지 않는다.** 러너가 `완료: 0영업일 적재, 0행 upsert, 호출 0회` 처럼 요약하면 요청 구간이 이미 DB 에 있다는 뜻이다(정상 종료).
  §1의 "0건을 성공으로 읽지 않는다"와 방향이 반대이므로 **처리 건수·호출 수·선택된 경로 줄을 함께 보고** 판단한다 — no-op 을 실패로 오판해 같은 크론을 손으로 재실행하면 수집 창이 넓어져 부분봉 위험만 커진다.
- **쉘 러너에 박힌 heredoc 파이썬을 고치면 문법 오류가 실행 시점(야간 크론)에야 드러난다** — 수정 후 `bash -n <script>` 로 쉘을, heredoc 본문을 정규식으로 뽑아 `python3 -m py_compile` 로 파이썬을 **둘 다** 검증한다. 새 분기(플래그 등)는 env 를 바꿔가며 한 줄 실측으로 확인한다.
- 장시간 잡은 background로 띄우고 **진행파일 줄 수 = 완료 일수**로 진행률을 읽는다(완료 판정은 프로세스 종료 + 진행파일 개수 둘 다). 진행 중에는 사용자에게 완료/전체·ETA·다음 단계를 짧게 보고한다.
  - **진행파일에는 성공한 항목만 기록한다.** 아무것도 못 받은 항목(행수 0)을 완료로 남기면 이후 실행이 그 항목을 영구히 건너뛰고,
    그 종목은 조용한 0행으로 남는다(진행파일을 지우기 전까지 복구되지 않는다). 중단·실패 분기는 기록하지 말고 재개되게 둔다.
  - **러너의 '성공' 자기보고는 검증 가능해야 한다.** 파서가 0행을 받고도 exit 0 으로 끝나는 유형은 로그로는 안 보이므로,
    러너가 ① 소스에서 받았다고 믿는 행수와 ② 실행 전후 테이블 행수 델타를 원장 테이블에 남기고 모니터링이 대조하게 한다.
    알림은 **명백한 조합**(믿은 값>0 & 델타 0, 주장≠델타)에만 걸고, '0행 수신'은 상장 초기 이력이 소진된 종목만 남은
    실행에서도 정상이므로 알림하지 않는다(대시보드 신호로만).

쿼리·분류 명령·id 시퀀스 판별·크론 미실행 진단: `references/backfill-coverage-audit.md`.

### 6-0. 백필을 크론으로 옮길 때 (인자·이스케이프·검증)

- **필수 인자를 크론에 안 넣으면 매일 조용히 실패해 0행 적재가 된다.** `--from/--to` 를 필수로 받는
  백필러에 인자가 없으면 **매 실행이 에러 한 줄로 끝나고** 적재는 0행이며, 로그는 그럴듯하게 생겼다. 크론에 날짜를
  `--from $(date -d '-7 days' +\%F) --to $(date +\%F)` 로 넣고, **crontab 의 `%` 는 반드시 `\%` 로
  이스케이프**한다(안 하면 명령이 잘리고 개행으로 쪼개진다).
- **판정은 exit code 가 아니라 DB 행 증가로 한다.** 러너가 `claim ... persisted=0` 처럼 0행으로
  정상 종료할 수 있기 때문에, 크론을 새로 깔았거나 인자를 바꿨으면 �� 실행 전후 `count(*)` / `max(trade_date)`
  델타를 보고 근거로 남긴다. 같은 날짜로 다시 돌리면 `--from 은 --to 보다 앞이어야 합니다` 로 죽는 러너는
  크론 창을 열린 구간으로 두고 적재를 UPSERT 로 멱등하게 만든다.
- **append-only 파일을 이어읽을 때 텍스트 모드 `tell()/seek()` 을 쓰지 마라.** 텍스트 모드의 오프셋은
  바이트 값이 아니라 opaque 라서 `tell()-4096` 같은 계산이 `UnicodeDecodeError` 로 수집기를 죽인다
  (실측: 장중 2시간50분 수집 중단·전량 결손). 오프셋을 상태파일에 저장해 재개하려면 **바이너리 모드**로
  열거나 라인 단위로 다시 읽어라.

### 6a. 시세 테이블의 인덱스·자원 위생 ("시스템을 이해하고 최적화해줘" 요청의 첫 단계)

최적화 요청을 받으면 **추측하지 말고 스캔 통계부터 뽑는다** — 인덱스 이름만 보면 중복이 안 보인다.

```sql
select indexname, indexdef from pg_indexes where tablename='market_data';
select relname, seq_scan, coalesce(idx_scan,0), n_live_tup from pg_stat_user_tables order by seq_scan desc limit 6;
select relname, pg_size_pretty(pg_total_relation_size(relid)) from pg_stat_user_tables order by 2 desc limit 6;
```

- **같은 컬럼 조합의 유니크 인덱스가 둘 있으면 하나만 남긴다**: 실측 `market_data` 에
  `(stock_code, trade_date)` 유니크 인덱스가 두 개(각 131MB, 정의까지 같은데 이름만 다름) 있었다 →
  하나 DROP(**−131MB** + 매 INSERT 비용 감소). 이름이 아니라 `indexdef` 로 비교해야 발견된다.
- **날짜 범위 전용 인덱스가 없으면 붙인다**: 야간 잡(신선도·갭·감사·탐색)은 `trade_date > X` / `GROUP BY trade_date`
  형태를 자주 쓰는데, 선두 컬럼이 `stock_code` 인 복합 인덱스만 있으면 플래너가 그걸 못 쓴다 →
  `idx_market_data_trade_date`(21MB) 추가로 626MB 테이블의 **순차 스캔이 Index Only Scan 으로 전환**된다.
  순효과 실측: 인덱스 합계 262MB → 152MB. 살아있는 스택에는 `CREATE INDEX CONCURRENTLY`, 후에 `ANALYZE <table>`.
- **스키마 원본을 같이 고쳐라**: 인덱스를 만드는 파일(예: `init-scripts/postgres/01_schema.sql`)을 함께
  갱신하지 않으면 다음 재초기화에서 중복 인덱스가 되살아난다(같은 줄에 이유를 주석으로).
- 컨테이너 자원도 같이 본다(`docker stats --no-stream`) — 메모리 상위(Neo4j·news-analyzer)와 재시작 0건 여부.
  보고는 항상 **전/후 수치**로 한다("최적화했다"는 문장은 증거가 아니다).

### 6b. 리포 밖에서 시스템을 한 장으로 정리해 두기

최적화·이해 요청이 반복되면 레포에 **실측 지도 문서**(예: `docs/SYSTEM_MAP.md`)를 두고 다음 요청에서 먼저 읽는다:
데이터 흐름(수집→피처→모델→스크리너→주문) · 자원 실측 · 테이블 상위 · **알려진 함정** · 미조치 최적화 후보(비용 추정 포함).
함정은 그 문서에 "추정"이 아니라 "실측"으로만 적는다.
재부팅·재가동 직후 점검 명령 묶음과 로그 오독 방지: `references/restart-verification.md`.
자동 감사 스크립트: `scripts/verify_market_data.py` — 월별 커버리지, 휴장 제외 공실, 부분 적재일, 무거래(가격 0) 행, OHLC 동결 종목, 분봉 요약을 한 번에 출력한다.

- **market_data를 읽는 코드에서 psycopg2 numeric은 `Decimal`로 온다.** `float/int/str`만 처리하는 숫자 변환 헬퍼는 DB에서 온 가격·거래대금을 전부 None으로 만들어 대상을 조용히 전멸시킨다(실측: 후보 20건 전량이 "가격 없음"으로 제외). 변환 헬퍼 마지막에 `float(value)` 폴백을 두거나 `Decimal`을 명시적으로 처리한다 — JSON 파일에서는 float로 오므로 파일 입력만 테스트하면 못 잡는다.
- **psycopg2 의 Python↔SQL 타입 경계에서 조용히 0건이 되는 함정 2개** (둘 다 예외 없이 "아무것도 안 들어감"으로 나타난다):
  - `date` 컬럼은 **`datetime.date`** 로 오는데 payload 는 `'YYYY-MM-DD'` 문자열인 경우가 많다 → `'2026-08-12' in {date(2026,8,12)}` 는 **항상 False**. 집합 비교 전에 `r[0].isoformat()` 로 문자열 통일하거나 컬럼을 `::text` 로 맞춘다.
  - `WHERE trade_date = ANY(%s)` 에 파이썬 문자열 리스트를 넘기면 `text[]` 로 어댑트되어 `operator does not exist: date = text` 다 → `%s::date[]` 로 캐스팅한다.
- **저장 전 필터(패딩·범위 제거)를 새로 넣으면 '살아남은 행수'를 로그와 반환값으로 남겨라.** 필터가 전량을 버리면 러너는 예외 없이 `+0행` 으로 끝나고, 다음 단계는 그 0을 "이미 적재됨"으로 오독한다 — 0 이면 실패로 다룬다(반환값을 호출부에서 검사).

## 7. 종목·점수를 다른 시스템에 넘길 때 (피드 발행)

수집·학습으로 뽑은 종목을 매매 시스템(브로커 자동화 등)에 넘기는 단계는 별도 계약으로 관리한다. 소비 시스템의 계약 문서(필드·필수값·신선도·전략별 청산 규칙)가 있으면 **그것이 단일 진실**이다 — 형식을 만들거나 바꾸기 전에 읽는다. 게이트를 벗어난 후보는 소비 측이 조용히 버리고, 그 사실은 발행 로그에 나타나지 않는다.

- **발행물은 tmp에 쓰고 `os.replace`로 원자적 교체**한다 — 소비자가 폴링 중이면 반쪽 문서를 읽고 전 후보를 버릴 수 있다.
- **소스 산출물의 나이를 발행기에서 막는다.** 계약이 보는 "발행 시각"만 갱신하면 몇 주 전 스크리너 결과도 신선해 보인다 → 오래된 전략은 빈 리스트로 발행한다(기본 3일).
- **점수 분포를 발행 로그에 남긴다**(min/median/max/spread). spread<5면 문턱·상위 N 선별이 무의미해지고, 동일값이 수십 건인 경우(모델 배치 미연결·raw 폴백)는 아예 무작위 선별이다 — 그 전략은 실거래에 쓰지 않는다.
- **필수값은 발행 전에 채운다**: 가격 누락은 시세 테이블 최근 종가로 보정하고(0/누락이면 소비 게이트가 차단), 코드는 6자리 숫자만 통과시키고, 점수 없는 항목은 버린 뒤 점수 내림차순으로 정렬한다.
- **소비자 코드로 검증한다**: 소비 시스템의 파서를 그대로 불러 발행물을 파싱해 건수·가격 누락·점수 분포를 확인하는 점검 도구를 둔다(매매 엔진/브로커 로그인이 없어도 수행 가능).
- 발행 시각·데이터 기준일·전략별 건수를 돌려주는 `/health` 같은 장을 같이 띄워 두면 감사와 장애 판단이 빨라진다.
- **외부 랭킹(상승률·거래량 순위)을 점수 스크리너와 **교집합으로 결합하지 마라 — "압축"이 아니라 "대체"가 된다.**
  실측: 상승률 2~12% 상위 60코드와 칼만·모델 스크리너 상위 20건의 **교집합 0건**, 교집합 유니버스의 최고점 55.1
  vs 전체 65.5. 스크리너 상위는 수일 추세·모델 확률로 뽑혀 당일 등락률과 무관하기 때문이다. 대신
  ① 랭킹 상단(추격 구간)은 **배제 필터** ② 관심 밴드는 **정렬 전용 가점**(공개 `score` 값은 그대로) 으로 쓴다 —
  발행 점수 스케일을 바꾸면 소비자 문턱의 의미가 조용히 달라진다. 교집합을 쓰겠다면 교집합 건수·상위 점수를
  먼저 실측해 보고하고 판단을 받는다.
- **랭킹 조회도 호출 예산과 입력 단위를 지킨다**: 페이지 상한이 무시되고 최대 2페이지(≈60건)만 오는 경로가 있고,
  구간 하한/상한을 **정수**로 요구하는 경로도 있다(문자열 `2.0` → `invalid_input`). 발표된 “상위 200”이 실제로
  60건일 수 있으니 받은 건수를 로그에 남긴다.

## 11. 뉴스 과거 백필 (감정·이벤트 피처 살리기)

시세가 아무리 완벽해도 감정·이벤트 피처가 상수 0 이면 순위 모델은 천장에 막힌다. 뉴스 피처를 채우는 경로는 **RSS 기간 질의 + LLM 배치 분석**이고, 이건 GPU 없이 API 만으로 된다.

- **과거 뉴스는 RSS 기간 질의로 받는다.** Google News RSS 는 `q=<종목명> after:YYYY-MM-DD before:YYYY-MM-DD` 를 지원한다(실측: 질의당 최대 100건, `pubDate` 정상 → 과거 기사 확보 가능).
  - 창당 100건이 꽉 차면 **그 창을 1주 단위로 더 쪼개** 누락을 줄인다(상한에 걸리면 그 기간 기사 일부가 조용히 사라진다).
  - 종목 × 2주 창으로 유니버스를 돌면 무료·수십 분 규모다(50종목 × 6개월 ≈ 650 질의).
  - 중복은 **URL 기준**으로 제거한다(같은 기사가 여러 피드/창에서 반복된다).
  - **호출 간격: 1.2s 는 즉시 429, 6s 는 통과**(실측). 429 가 섞이면 백오프는 되지만 처리량이 무너지므로
    종목별 순회의 기본 간격을 6s 로 잡고, `--sleep` 을 인자로 빼서 상향 조정이 가능하게 한다.
  - **정밀도 가드는 '제목에 종목명 포함'으로 걸어라.** 피드 질의는 관련 없는 기사도 섞어 주므로, 본문이 아니라
    제목에 종목명이 있을 때만 채택한다(실측 통과율 ~70%, 표본 검수에서 오탐 없음). 정규화 이름이 3자 미만인
    종목('남성' 등)은 **독립 토큰**일 때만 통과시킨다 — 일반명사 종목명은 본문 매칭에서 대량 오탐을 낸다.
  - 이 경로의 일은 "커버리지"다: 피드 단위 수집에서 패널 200종목 중 31종목뿐이던 것이 종목별 질의로 **193종목**까지
    올라간다. 다만 **커버리지를 올린 것과 신호가 생긴 것은 별개**이므로(실측: 이 피처의 선행수익 rank-IC ≈ 0),
    수집 후 반드시 IC·분위수 단조성으로 따로 판정한다.
- **LLM 분석은 호출 상한을 코드로 강제한다.** 기사당 1콜(감성·진위·이벤트) 구조에서 6,000건이면 대략 $5~10 규모다 — 실행 전에 예상 비용과 상한을 사용자에게 알리고, 상한 도달 시 중단 + 실제 토큰·추정 비용을 보고한다. 무한 루프 배치에 맡기면 청구서가 결과 보고서보다 먼저 온다.
- **분석 결과를 피처 테이블 모양에 맞춰 다시 집계해야 피처가 살아난다.** `news_analysis` 에 감성 행을 쌓는 것만으로는 부족하고, 피처 빌더가 실제로 읽는 테이블·컬럼(감성 평균·기사 건수, 5d/20d 창)을 **먼저 코드에서 확인**한 뒤 `(stock_code, date)` 단위로 집계해 넣는다.
- **효과는 "피처가 살아났는지"로 먼저 검증하고, 그 다음 모델로 검증한다.** 특정 종목·날짜의 감성·뉴스 건수 피처가 0 이 아닌 값을 내는지 출력하고, 비영(nonzero) 피처 개수의 before/after 를 비교한다. 그 다음 같은 설정을 멀티시드로 재학습해 AUC 변화를 before/after 로 보고한다.
- **데이터를 채우는 것이 하이퍼파라미터 튜닝보다 상위 레버다 — 단, 채우는 것만으로는 AUC 가 오르지 않는다.**
  설정 스윕이 0.51~0.52 에 수렴하면 정보량 한계이므로 튜닝 반복 대신 원천 테이블(news·sns·수급·매크로)을 채우되,
  효과 판정 전에 다음 세 가지를 **먼저** 확인한다(아니면 "데이터를 다 채웠는데 왜 AUC 가 그대로인가"로 몇 시간을 태운다):
  1. **선별 문턱**: 피처를 단변량 edge 상위 K 로 추리는 파이프라인이라면 **K=30 일 때 문턱이 edge ≈0.045~0.05** 다.
     실측: 수급 최고 0.0112 · 공매도 0.0092 · 프로그램/파생 0.0002 → **선별 자체가 불가능**해 AUC 기여가 정확히 0 이었다.
     신규 피처의 edge **순위를 문턱과 비교**한 뒤에 기여 여부를 결론낸다.
  2. **날짜별 횡단면 분산**: 시장 전체 값(그 날 전 종목이 같은 값)은 횡단면 랭킹 모델에서 변별력이 0 이다.
     실측: 파생·프로그램·환율·금리·이벤트 계열 34개가 날짜 내 분산 0 이고 edge 0.0002 였다 — 이런 소스는
     피처가 아니라 **레짐 게이트**로 쓴다(수집 자체가 무의미한 건 아니다).
  3. **종목-상수 여부**: 종목당 값이 1개(패널 전체에서 상수)인 피처는 최신 스냅샷을 과거 날짜에 적용한
     **룩어헤드**일 수 있고, 그런 피처가 edge 상위와 top-K 선별을 독차지한다.
  판정은 **대조군을 같은 런에 포함한 before/after**(같은 패널·폴드·시드) 와 폴드별 짝 델타로 한다.
  커버리지·비영 비율은 `!= 0` 이 아니라 **`notna()`** 로 센다(`NaN != 0` 이 True 라 NaN 이 채워진 것으로 집계된다).
- **피처를 살리는 작업의 첫 단계는 리더(피처 빌더)의 SQL 을 읽는 것이다.** 실제로 조회하는 테이블·컬럼·WHERE 조건을 확인한 뒤
  `information_schema.columns` 로 그 컬럼의 존재를 확인한다. 이 계열 저장소에서는 **테이블은 있는데 리더가 찾는 컬럼이 없거나
  다른 목적의 컬럼만 있거나 writer 자체가 없는** 경우가 흔하다(수급·공매도·프로그램·파생 테이블이 0행인 상태).
  그때 할 일은 수집기 작성만이 아니다 — `ALTER TABLE ... ADD COLUMN` + 마이그레이션 SQL 까지 포함해 리더 계약을 맞춘다.
- **검증은 두 날짜 비교로 한다**: 같은 종목·다른 두 날짜에서 피처값이 0 이 아니고 **서로 다른지** 본다.
  상수(0 또는 동결값)면 as-of 배선이 끊긴 것이므로, 한 날짜만 보고 성공으로 판정하지 않는다.
- **`nonzero_ratio=0` 을 곧바로 '죽은 피처'로 결론내지 마라 — 커버리지 vs 코드를 먼저 가른다.**
  순서: (a) 소스 테이블의 distinct 종목 수·최신일을 센다 → (b) 그 데이터가 있는 **특정 종목**으로
  `build_features(code, date)` 를 직접 돌려 값을 본다 → (c) 그래도 0 이면 코드를 의심한다.
  커버리지 패널은 표본이 작아(예: 15종목×20일) **종목이 희소한 피처가 전부 0 으로 찍힌다.**
  실측 예: 이벤트 `event_*_5d` 18개가 패널에서 전부 0 이었지만 이벤트 보유 종목에서는 정상값이 나왔다 —
  원인은 추출이 **48종목만** 덮은 것이었다. 종목명 부분문자열 매칭(`match_stock`)이 유니버스 목록 밖
  기사를 버리고, 그 목록이 모델 학습 유니버스와 겹치지 않으면 피처가 학습 데이터에서 통째로 0 이 된다.
  처방은 코드가 아니라 **추출 유니버스 확대(종목 수 상한 인자) + 재클러스터**다. 규칙 기반 추출이면 유료 호출이 없다 —
  LLM 비용 승인을 요구하며 막지 말고 먼저 추출 규칙이 룰 기반인지 확인한다.
- 커버리지 측정 도구는 **컨테이너 안에서** 실행한다(호스트 python3 엔 서비스 패키지가 없어
  `ModuleNotFoundError: No module named 'app'`):
  `docker exec <ml-컨테이너> sh -c 'cd /app && python scripts/feature_coverage_report.py --ignore-cache --stocks 15 --days 20'`.

  래퍼에서 **명시적으로** 넘기는 것 — 러너의 기본 경로에 의존하면 다음 사이클에 같은 사고가 재발한다.
