## 2. KIS OpenAPI (한국투자증권 — 일봉/분봉 수집의 주 소스)

- env: `KIS_APP_KEY`, `KIS_APP_SECRET`, `KIS_ACCOUNT_NO`(시세엔 불필요), `KIS_BASE_URL`, `KIS_DAILY_TR_ID`, `KIS_MINUTE_TR_ID`, `KIS_REQUEST_DELAY`(기본 3.0s+jitter), `KIS_RETRY_MAX`, `KIS_TOKEN_PATH`(JWT 24h 캐시 — 발급은 분당 1회 제한), `KIS_DRY_RUN`.
- **1콜 = 최대 100일 범위 조회(기간별시세)** → 구간 백필은 종목당 1콜이면 충분하다. 일자별 반복은 호출을 N배 낭비한다.
- **일일 호출 한도는 코드에 없다 — 스코프를 넓히기 전에 계정 한도를 먼저 확정하라.** 이 레포들이 강제하는 것은
  호출 간 지연(`KIS_REQUEST_DELAY` 3.0s+지터)뿐이고 일일 상한은 `.env`·설정 어디에도 없다. 그래서 대상을 늘리는 변경
  (회전 주기 단축·유니버스 확대·같은 스크립트 이중 실행)은 **초과를 감지할 장치 없이** 핵심 회전과 같은 앱키 쿼터를 나눠 쓴다.
  확대 요청을 받으면 ① 후보 스코프의 호출 예산을 먼저 계산해 수치로 제시한다(예: 4,340종목 × 1콜 ≈ 2,700콜 ≈ 3s 지연에서 2.3시간)
  ② 한도가 확인되기 전에는 **현행 스코프 유지**가 기본값이고, 그 결정을 기록한다 ③ 확대하기로 했으면 env 상한을
  명시적으로 올린다 — 러너의 안전 상한 기본값은 넓은 스캔을 **조용히 토막내고** 로그에는 `완료 0건` 처럼 보인다.
- **분봉은 1회 응답 30행 고정**이다 — `FID_CNT`를 100으로 올려도 30행만 온다(실측). 정규장 391분이면 14페이지가 필요하고, 시간 내림차순 응답을 과거로 페이지네이션한다. `MAX_PAGES` 같은 안전장치의 기본값을 10으로 두면 개장 후 약 91분이 조용히 누락된다 — 페이지 수 상한은 14 이상으로 두거나 env로 조정 가능하게 한다.
- **분봉 페이지네이션 종료 조건을 `len(page) < fid_cnt` 로 쓰지 마라 — 30행 고정이라 항상 참이다.**
  KIS는 `FID_CNT=100` 을 줘도 페이지당 30행만 주므로 그 조건을 종료식에 넣으면 **1페이지만 받고 끝나**
  마감 직전 30분(15:01~15:30)만 쌓인다. 실측: 40여 세션 동안 하루 9,000행(=300종목×30행)으로 고정돼 있었고,
  그 데이터로는 장중 손절/익절 순서를 전혀 알 수 없다. 종료는 ① 빈 페이지 ② `oldest == MARKET_OPEN_TIME`
  ③ 기준시각이 진행하지 않음 으로만 판정하고, 적재 감사에 **종목당 행수가 380~391인지**를 넣는다
  (30행 근처면 페이지네이션이 죽은 것).
- **KIS로 못 채우는 과거 분봉은 Naver `siseJson` 으로 되살린다 — 단 종가만 온다.**
  `https://api.finance.naver.com/siseJson.naver?symbol=005930&requestType=1&startTime=YYYYMMDD&endTime=YYYYMMDD&timeframe=minute`
  → 실측 6거래일 × 정규장 381분/일(행 `["YYYYMMDDHHMM", 시가, 고가, 저가, 종가, 누적거래량, …]`).
  **시/고/저는 null 이고 종가·누적거래량만** 채워져 있으므로, ① 손절/익절 순서 판정은 분 종가 경로로만 하고
  ② 없는 OHLC 를 현재가로 메꿔 저장하지 말며(별도 테이블 + `source` 컬럼으로 분리) ③ 창을 좁혀 과거로 더
  파고들 수 있는지 실호출로 확인한다(KIS는 당일만 주므로 이 경로가 과거 분봉의 유일한 대안이다).
- **분봉은 당일만 제공된다** — 지난 날짜를 요청하면 `no_data`가 온다. 과거 분봉 백필은 불가능하므로 수집 크론이 그날 안에 돌지 않으면 그날 분봉은 영구 결손이다.
- **전 종목 분봉 수집 비용을 먼저 계산한다**: 종목당 ~14콜(30행×14페이지) × 2,700종목 ≈ 3.8만 콜 ≈ 30시간 이상. 야간 크론에 들어가지 않는다 → 우선순위 유니버스(스크리너 후보·보유·관심 종목 100~300종목 = 1~2.7시간)로 제한한다.
- **일봉을 KIS로 전 종목 받으면 1일 2,770콜 ≈ 2.5시간**(3s+지터)이다. 일봉 야간 수집의 기본 경로는 날짜당 2콜인 KRX로 두고 KIS는 폴백·프로브용으로 쓴다. 긴 수집을 다음 단계 시작 시각과 겹치게 돌리면 그 단계(예: 20:00 ML 파이프라인)가 부분 적재분을 학습 입력으로 읽는다.
- HTTP는 `subprocess curl` — 파이썬 `requests`/`urllib`는 WAF 403.
- **유니버스를 `market_data`에서 읽는 구현은 빈 DB에서 아무것도 수집하지 않는다.** 종목 마스터(`stocks`)를 먼저 시딩하고, 백필 러너는 `stocks`(KOSPI/KOSDAQ) 기준으로 돌린다. 이 함정은 KIS에만 있지 않다 — 시세 테이블을 유니버스/스코프 소스로 삼는 러너(재무 백필, 채점기)는 **신규 배포에서 전부 0건**이 되므로 `market_data`가 비면 다른 유니버스로 폴백하는 분기를 넣는다.
- 토큰 발급(`POST {BASE}/oauth2/tokenP`, json `appkey`/`appsecret`)이 **키 유효성을 반증할 수 있는 유일한 1콜 프로브**다. 시세 호출 로그만 보면 원인이 안 갈린다.
  - `403` + `{"error_code":"EGW00103","error_description":"유효하지 않은 AppKey입니다."}` = 앱키 자체를 인식 못 함(오타·폐기·만료). 복사 오류라면 눈에 안 보이는 문자 혼동이 흔하다 — `I`↔`l`, `0`↔`O`, `1`↔`l`, `S`↔`5`. 케이스만 다른 후보 2개를 각각 1콜로 프로브하면 즉시 갈린다.
  - `EGW00102` = AppSecret 불일치. 어느 쪽이든 **두 도메인(실전 `openapi.koreainvestment.com:9443`, 모의 `openapivts.koreainvestment.com:29443`)에서 같은 코드면 도메인 문제가 아니다** — 도메인을 더 바꿔보지 말고 키 재발급을 요청한다.
  - **토큰 발급은 앱키당 분당 1회 — 수동 프로브가 바로 뒤 실행을 깨뜨린다.** 방금 1콜로 토큰을 받아왔는데 이어서 돌린 수집기가 `http=403 EGW-UNKNOWN(rt_cd=1)`으로 죽으면 오타·차단이 아니라 **방금 소진한 발급 쿼터**다. 60초 뒤 같은 명령을 다시 돌려 성공을 확인한다(성공하면 `KIS_TOKEN_PATH` 캐시가 생성된다).
  - **tokenP 실패 본문은 `error_code`/`error_description`으로 온다**(시세 API의 `msg_cd`/`msg1`이 아니다). `msg_cd`만 읽는 클라이언트는 원인을 `EGW-UNKNOWN`으로 뭉개고 레이트리밋 재시도(60s)도 걸지 않아 오타와 쿼터가 로그에서 구분되지 않는다 — 두 키를 모두 읽게 고친다.
- **키를 교체하면 `KIS_TOKEN_PATH` 캐시를 반드시 지운다.** 다른 앱키로 발급된 캐시 JWT를 그대로 쓰면 시세 호출이 `403 EGW-UNKNOWN(rt_cd=1)`으로 즉시 죽어 IP 차단으로 오독된다. 캐시 JWT payload의 `aud`(36자)가 발급 앱키이므로 새 키와 hash를 비교하면 "예전 키와 다른 키"인지 판별할 수 있다(레포에 커밋된 옛 캐시가 남아 있는 경우가 있다).
- **자격증명 점검은 토큰 발급만으로 불충분하다**: 캐시 토큰(`KIS_TOKEN_PATH`)이 남아 있으면 앱키가 틀려도 프로브가 "정상"을 출력한다(실측). 점검 모드는 **대표종목 시세 1콜**까지 해야 하고, 그래야 앱키 불일치가 401 → 재발급 실패 → `EGW00103`으로 드러난다.
- **`EGW00102`/`EGW00103`(자격증명 거부)은 재시도 금지.** KIS가 HTTP 500으로 돌려주기 때문에 일반 일시오류 분기에 걸려 백오프 6회(60초+)를 태우고 실패한다 — 자격증명 오류를 별도 분기로 빼서 즉시 종료하고 EGW코드를 로그에 남긴다.
- **"키가 설정되어 있다"와 "그 키로 된다"는 다르다**: 야간 수집 러너는 경로 선택 전에 프로브를 돌리고, 실패하면 2,700건을 실패로 쓸어버리지 말고 EGW코드와 함께 `exit 3`으로 끝낸다(크론 로그가 수천 건 실패로 채워지지 않게).
- 휴장/공실 판별을 다른 소스로 대체할 때는 러너의 **진행파일을 무시하는 플래그**(`--ignore-progress`)가 필요하다 — 이미 처리한 날짜는 스킵되어 응답 자체를 못 보기 때문이다(실측: 프로브가 계속 판별불가를 반환).
- 상세(tr_id 값·필드 매핑·오류 코드): 레포의 `docs/KIS_컬렉터_PLAN.md`.
- **호스트에서 도는 수집 러너는 `.env` 를 source 한 뒤 DB host/port 를 덮어써야 한다.** `.env` 는
  컨테이너 기준(`POSTGRES_HOST=postgres`, `PORT=5432`)으로 적혀 있어서, 호스트 셸에서는 ① `postgres`
  이름이 해석되지 않고(`could not translate host name` → 후보 0건) ② 노출 포트는 5434 다(컨테이너 5432→호스트 5434).
  `set -a; . .env; set +a` 직후 `export POSTGRES_HOST=127.0.0.1 POSTGRES_PORT=5434` 로 **명시적으로 덮어쓰고**,
  `docker port <pg컨테이너>` 로 실제 노출 포트를 확인한다.

### 2a. 투자자 수급(외국인/기관/개인 순매수) · 지분율 — TR 두 개를 구분하라 (2026-09-24 실측)

수급 데이터는 **TR 에 따라 날짜 파라미터 지원이 정반대**다. 하나만 알면 "최근 30일까지만 된다"고 잘못 결론낸다.

| TR / 경로 | 날짜 파라미터 | 행 수 |
|---|---|---|
| `FHKST01010900` `/uapi/domestic-stock/v1/quotations/inquire-investor` | **완전 무시** — 20250101~20250201 을 요청해도 **최신 30영업일**이 온다 | 1콜 30행 고정 → 페이지네이션 불성립(구간을 바꿔도 같은 행) |
| `FHPTJ04160001` `/uapi/domestic-stock/v1/quotations/investor-trade-by-stock-daily` | `FID_INPUT_DATE_1` = **창의 끝(포함)**, `FID_INPUT_DATE_2 > FID_INPUT_DATE_1` 필수(같으면 **빈 응답**) | d1=20260811 → 20260630~20260811 / d1=20260630 → 20260518~20260630 |

- **과거 백필(60~90영업일)은 두 번째 TR 로만 가능하다**: `d1 = DB 최소일 − 1일`, `d2 = d1 + 1일` 로 한 페이지씩
  과거로 밀면 30영업일씩 파고들 수 있다(진행파일로 재개, 종목당 60영업일 = 2콜).
- 응답 배열 키가 **TR 마다 다르다** — `FHKST01010900` 은 `output`(리스트), `FHPTJ04160001` 은 `output2`
  (리스트; 같은 응답의 `output1` 은 현재가 요약 dict). **한 키만 읽는 파서는 두 번째 TR 에서 조용히 0행**이 되어
  "날짜 앵커가 틀렸다"고 오진하게 된다 → 파서는 두 키를 모두 시도한다. 필드명은 동일:
  `{prsn,frgn,orgn}_ntby_qty`(순매수 수량), `{prsn,frgn,orgn}_ntby_tr_pbmn`(순매수 대금),
  `{prsn,frgn,orgn}_{shnu,seln}_{vol,tr_pbmn}`(매수/매도). 두 TR 의 같은 날짜 값은 서로 일치한다.
  한 응답 안에서도 단위가 섞인다 — `acml_tr_pbmn` 은 **원**, `*_ntby_tr_pbmn` 은 **백만원**.
- 호스트에서 러너를 돌릴 때 `python3` 가 **Hermes 자신의 venv python**(psycopg2 없음)을 가리키는 경우가 있다
  (`ModuleNotFoundError: No module named 'psycopg2'`). 레포 호스트 스크립트는 `/usr/bin/python3` 로 실행한다.
- 레이트리밋: 토큰 발급은 앱키당 분당 1회(`EGW00133`), 시세 호출은 실전 계좌 초당 20건 수준이라
  1.5s+지터면 30종목×~4콜(≈120콜)이 3분 내에 끝난다. 프로브를 먼저 돌려 토큰 쿼터를 소진하면
  직후 본 실행이 `EGW00133` 으로 시작하니, 프로브와 본 실행을 붙여 돌리지 않는다.
- **`*_tr_pbmn` 단위는 백만원이다** — 교차검증: 005930 2026-09-23 `frgn_ntby_qty` 4,513,767 × 종가 286,500
  = 1.293e12원 ≈ API값 1,283,306 × 1e6. 저장 시 단위를 계약으로 못박아라(원으로 환산 권장).
- **지분율은 현재가 TR(`FHKST01010100` `/inquire-price`)에서 온다**: `hts_frgn_ehrt`(외국인 지분율 %)이고
  `frgn_hldn_qty / lstn_stcn × 100` 과 일치한다(005930: 2,726,977,583/5,846,278,608 = 46.64).
  **스냅샷만 제공 — 과거 시점 조회 불가**(종목당 1행). **기관 지분율 필드는 없다**(output 전수 확인) →
  0 을 지어내지 말고 NULL 로 두고 소비 측에 비외국인(개인+기관) 잔여로 해석된다고 보고한다.
  - **스냅샷을 '오늘' 날짜 한 행만 적재하면 과거 패널에서는 전부 0 이 된다** — as-of 리더가
    `trade_date <= 조회일 ORDER BY trade_date DESC LIMIT 1` 로 읽으므로 조회일이 적재일 미만인 행은 못 잡는다.
    과거 날짜에 현재값을 복사해 넣는 것은 룩어헤드다(하지 마라) → **"현재값을 채웠다"와 "과거 시계열 피처가 살아났다"를
    구분해서 보고**하고, 과거 이력은 일별 지분율을 주는 다른 소스를 확인한다.
- **이력 조회 TR 은 상장(거래개시) 전 구간을 all-zero 행으로 패딩해 준다.** 시세 테이블에 시세가 없는 날짜인데
  수급 행만 날짜를 채워 오면 그것이 패딩이다 → 적재 전에 **시세 테이블에 그 `(종목, 날짜)` 가 있는 행만** 남긴다.
  걸러내지 않으면 커버리지(행수·거래일 수)가 부풀고, 상장 직후 5일 평균이 0 으로 희석된다.
- **수급 리더는 `date` 를 안 받으면 테이블 최신 행을 집어간다**(`ORDER BY trade_date DESC LIMIT n`) → 조회일을
  바꿔도 값이 같고 과거 조회일에 미래 수급이 섞인다. as-of 필터(`trade_date <= date`)를 리더에 넣어야
  "날짜별로 값이 달라지는" 피처가 된다. 파이프라인이 `date` 를 안 넘겨도 시세 프레임(이미 `<= date` 로 잘림)의
  최대 거래일을 as-of 로 쓰면 **호출부 수정 없이** 리더 안에서 정합을 맞출 수 있다.

- **공매도 '잔고'(short interest)는 이 스택에서 구할 수 없다 — 그 피처는 폐기하라.** KIS 공매도 TR(`FHPST04830000`)은
  **체결**(일별 거래량·거래대금·거래비중)만 주고, 잔고 계열 후보 6경로(`daily-short-sale-balance`,
  `inquire-short-sale-balance`, `short-sale-balance-trend`, `short-sale`, `ranking/short-sale-balance`,
  `daily-loan-balance`)는 **전부 404** 였다. KRX OpenAPI 주식 카탈로그에도 공매도 서비스가 없다.
  따라서 `short_interest_ratio`(잔고/발행주식)·`days_to_cover`(잔고/평균거래량)는 **데이터 자체가 없고**,
  `krx_short_selling.balance_quantity` 는 전량 0/NULL 이다 — 빌더를 고쳐도 살아나지 않는다.
  살릴 수 있는 것은 체결 기반 `short_selling_ratio`(공매도 거래비중)뿐이고, 그것도 커버리지(패널 26/200)를
  백필로 넓혀야 임계(5%)를 넘는다.

### 2b. 프로그램매매 — 시장 전체 값은 종합조회(일별) TR 하나로 끝난다 (2026-09-24 실측)

"프로그램매매 비중" 피처는 종목별 집계로 풀려 하면 수천 콜이 된다(3콜/초라도 수십 분). 시장 전체 값을
한 구간씩 주는 TR 이 따로 있다 — **먼저 이걸 찾고, 없을 때만 종목별로 내려간다**.

| TR / 경로 | 범위 | 특징 |
|---|---|---|
| `FHPPG04600001` `/uapi/domestic-stock/v1/quotations/comp-program-trade-daily` | **시장 전체·일별(1행/일)** | `FID_COND_MRKT_DIV_CODE=J`, `FID_MRKT_CLS_CODE=K`(KOSPI)/`Q`(KOSDAQ), `FID_INPUT_DATE_1`~`_2` 구간(20일 안전) → `whol_smtn_{seln,shnu,ntby}_tr_pbmn`(전체 프로그램 매도/매수/순매수, **백만원**) + 차익/비차익·위탁/자기 분해. 백필의 기본 경로 |
| `FHPPG04650101` `/quotations/program-trade-by-stock` | 종목별(1콜=최신 30행 고정) | 필드는 `whol_*` 뿐 — **투자자(외국인/기관) 분해 없음**. 시장 전체를 만들려면 전체 종목 집계가 필요해 비경제적 |
| `FHPPG04650201` `/quotations/program-trade-by-stock-daily` | 종목별(위와 동일 응답) | 위 TR 과 경로만 다르고 결과가 같다 — TR_ID 와 경로를 짝지어 확인할 것 |
| `HHPPG046600C1` `/quotations/comp-program-trade-today` | 시장 전체·**장중(당일)** | 외국인 분해가 있는 유일한 프로그램 API 지만 과거 백필 불가 |

- **수급 시장 전체(외국인 매수/매도)는 KIS 에 없다**: `FHPTJ04040000` `/quotations/inquire-investor-daily-by-market`
  은 KOSPI/KOSDAQ 일별을 구간으로 주지만 `{prsn,frgn,orgn}_ntby_tr_pbmn`(**순매수** 백만원)만 있다 — 매수/매도 분해는 종목별 TR 에만 있다.
  그래서 `(foreign_buy + foreign_sell) / total_value` 모양의 리더를 채울 때는 **시장 전체 프로그램 매수/매도 + 시장 전체 거래대금**을 쓰고,
  컬럼명이 `foreign_*` 여도 실제로는 프로그램 전체 값이라는 사실을 마이그레이션 COMMENT 에 남긴다(거짓 라벨링 금지).
- **필수 파라미터는 오류 메시지가 하나씩 가르쳐 준다**: `OPSQ2001 ERROR INPUT FIELD NOT FOUND [FIELD]` 가
  **없는 필드 이름을 그대로** 알려준다 → 한 콜씩 추가하면 3~6콜 안에 요구 파라미터 전부를 확정한다.
  실측: `comp-program-trade-daily` 는 `FID_INPUT_DATE_2`→`FID_INPUT_DATE_1` 순으로, `inquire-investor-daily-by-market`
  은 `FID_INPUT_ISCD`→`_1`→`_2`→`FID_INPUT_DATE_2` 순으로 요구했다(문서 없이도 확정 가능). **`OPSQ2001` 은 권한 문제가 아니다** — 스키마 교정 대상이다.
- **시장 코드로 종목별 엔드포인트를 때리지 마라**: `program-trade-by-stock`·`inquire-investor` 에 `0001`/`1001`/`2001`
  을 넣으면 `rt_cd=0` + **빈 output** 이 온다(성공처럼 보이지만 0행). 시장 집계는 위 표의 시장 전용 TR 로만 된다.
- 경로·TR_ID 카탈로그(문서가 막힐 때): `https://m72x2.com/X2/_PAGE/help/kis_api_list.php` 가
  수백 개 엔드포인트의 `경로 + TR_ID` 쌍을 한 페이지에 준다(예: `comp-program-trade-daily FHPPG04600001`).
  추측 대신 여기서 이름을 확인한 뒤 1콜 프로브한다.
