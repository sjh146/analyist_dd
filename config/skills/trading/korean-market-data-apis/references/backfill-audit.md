## 6. 백필·수집 상태 감사와 보고

"지금 백필 상태 알려줘" 요청은 감사 절차로 받는다 — 감사 없이 러너 로그만 보면 틀린 답이 나온다
(러너는 최근 창만 보고, 공실은 조용히 넘어간다).

1. 기대 거래일(평일 − 휴장) = 실제 `count(DISTINCT trade_date)`인지, 공실·부분 적재일이 0인지 수치로 확인한다.
2. 휴장 파일이 스스로 맞다고 가정하지 않는다 — 결측 평일은 1일 2콜 프로브로 휴장/공실을 분류해 확정한다.
3. 크론은 로그 파일 유무로 판정하지 않는다(로그 없음 = 미실행, 재부팅이 원인인 경우가 많다).
   재부팅·재가동 직후 "확인해줘" 를 받으면 ① `uptime; date` 로 부팅 시각을 먼저 잡는다 — **그 시각보다 이른 크론 회차는 실행되지 않았다**(로그에 그 회차 기록이 있으면 재부팅 전에 돌았으니 재실행하지 않는다) ② `systemctl is-enabled cron docker <수집 서비스>` 로 자동 복귀 보장을 확인 ③ **크론이 가리키는 스크립트 실존을 검사**한다 — 없는 스크립트를 참조하는 항목은 조용히 실패한다: `for f in $(grep -oE '/home/[a-z]+/cron/[a-z_]+\.sh' /etc/cron.d/<name> | sort -u); do [ -x "$f" ] && echo "OK $f" || echo "MISSING $f"; done` ④ DB 최신일이 D-1이면 정상이다(일별매매는 D+1 공표) — 당일 봉 부재를 수집 실패로 오판해 손으로 재실행하지 않는다 ⑤ 수집 자격증명은 1콜 프로브(토큰+대표종목 시세)로 살아있는지 확인한다.
4. 보고는 숫자 → 수집 경로 → 미완 데이터 → 리스크 순서로 분리하고, 말미에 번호 매긴 다음 작업 후보 + 권장 1순위를 붙인다.

- **"무변동/동결" 행은 느슨하게 세면 과대집계된다.** `시가=전일시가 AND 종가=전일종가` 만 보면 정상적인 무변동일까지 잡힌다(실측 3.78%). 진짜 이상치는 `시·고·저·종가 + 거래량` 이 전부 직전 거래일과 같은 행(3.25%)이고, 그중 **거래량>0 인 것만 의심**한다. 상위는 900xxx/950xxx 외국기업 예탁증권처럼 원래 거래가 드문 종목이다 — 이 필터로 다시 세기 전에는 "데이터가 오염됐다"고 보고하지 않는다.
- **커버리지(행수·거래일 수)와 신호 유무는 다른 축이다.** "백필은 다 했다는데 왜 지표가 안 나오나" 질문에는 ① 커버리지 실측 ② 라벨·표본 특성 ③ 과거 기준값의 측정 방식(구간·split·다중비교) 세 축으로 답하고, 데이터 품질을 원인으로 지목하려면 재현 가능한 근거 쿼리와 함께 제시한다.
- 테이블에 **작성자가 둘 이상**이면(정식 수집기 + 스크래핑/Yahoo 수집기) "DB 최신일+1 ~ 어제" 증분이 당일 부분봉 때문에 막힌다 — `max(trade_date)`가 오늘이면 구간이 비어 `수집 구간 없음`으로 조용히 0건이 된다. 감사는 `max(trade_date)`가 오늘인지 먼저 보고, 오늘이면 부분봉 작성자를 찾아 당일 기록을 막는다(또는 증분 기준을 고정 창으로 바꾼다).
- **적재 위생 가드는 저장소 계층에 넣는 것으로 끝나지 않는다 — 같은 테이블의 모든 writer 에 같은 플래그를 건다.**
  감사·가드를 붙일 때 `grep -rn "INSERT INTO <table>" --include=*.py --include=*.sh .` 로 작성자를 **전부 열거**하고,
  저장소/ORM 계층 밖에서 raw SQL 로 쓰는 경로(특히 쉘 러너 안 heredoc 파이썬)를 찾아 동일 정책(기본 `DO NOTHING` + `*_OVERWRITE=1` 예외)을 적용한다.
  계층에만 가드를 넣은 상태에서는 나머지 writer 가 정책 밖에서 공식 수집분을 스크래핑 값으로 되돌려 놓는다.
- **"넣을 게 없었다" 는 no-op 실행을 실패로 읽지 않는다.** 러너가 `완료: 0영업일 적재, 0행 upsert, 호출 0회` 처럼 요약하면 요청 구간이 이미 DB 에 있다는 뜻이다(정상 종료).
  §1의 "0건을 성공으로 읽지 않는다"와 방향이 반대이므로 **처리 건수·호출 수·선택된 경로 줄을 함께 보고** 판단한다 — no-op 을 실패로 오판해 같은 크론을 손으로 재실행하면 수집 창이 넓어져 부분봉 위험만 커진다.
- **쉘 러너에 박힌 heredoc 파이썬을 고치면 문법 오류가 실행 시점(야간 크론)에야 드러난다** — 수정 후 `bash -n <script>` 로 쉘을, heredoc 본문을 정규식으로 뽑아 `python3 -m py_compile` 로 파이썬을 **둘 다** 검증한다. 새 분기(플래그 등)는 env 를 바꿔가며 한 줄 실측으로 확인한다.
- 장시간 잡은 background로 띄우고 **진행파일 줄 수 = 완료 일수**로 진행률을 읽는다(완료 판정은 프로세스 종료 + 진행파일 개수 둘 다). 진행 중에는 사용자에게 완료/전체·ETA·다음 단계를 짧게 보고한다.
  - **진행파일에는 성공한 항목만 기록한다.** 아무것도 못 받은 항목(행수 0)을 완료로 남기면 이후 실행이 그 항목을 영구히 건너뛰고,
    그 종목은 조용한 0행으로 남는다(진행파일을 지우기 전까지 복구되지 않는다). 중단·실패 분기는 기록하지 말고 재개되게 둔다.
  - **러너의 '성공' 자기보고는 검증 가능해야 한다.** 파서가 0행을 받고도 exit 0 으로 끝나는 유형은 로그로는 안 보이므로,
    러너가 ① 소스에서 받았다고 믿는 행수와 ② 실행 전후 테이블 행수 델타를 원장 테이블에 남기고 모니터링이 대조하게 한다.
    알림은 **명백한 조합**(믿은 값>0 & 델타 0, 주장≠델타)에만 걸고, '0행 수신'은 상장 초기 이력이 소진된 종목만 남은
    실행에서도 정상이므로 알림하지 않는다(대시보드 신호로만).

쿼리·분류 명령·id 시퀀스 판별·크론 미실행 진단: `references/backfill-coverage-audit.md`.

### 6-0. 백필을 크론으로 옮길 때 (인자·이스케이프·검증)

- **필수 인자를 크론에 안 넣으면 매일 조용히 실패해 0행 적재가 된다.** `--from/--to` 를 필수로 받는
  백필러에 인자가 없으면 **매 실행이 에러 한 줄로 끝나고** 적재는 0행이며, 로그는 그럴듯하게 생겼다. 크론에 날짜를
  `--from $(date -d '-7 days' +\%F) --to $(date +\%F)` 로 넣고, **crontab 의 `%` 는 반드시 `\%` 로
  이스케이프**한다(안 하면 명령이 잘리고 개행으로 쪼개진다).
- **판정은 exit code 가 아니라 DB 행 증가로 한다.** 러너가 `claim ... persisted=0` 처럼 0행으로
  정상 종료할 수 있기 때문에, 크론을 새로 깔았거나 인자를 바꿨으면 �� 실행 전후 `count(*)` / `max(trade_date)`
  델타를 보고 근거로 남긴다. 같은 날짜로 다시 돌리면 `--from 은 --to 보다 앞이어야 합니다` 로 죽는 러너는
  크론 창을 열린 구간으로 두고 적재를 UPSERT 로 멱등하게 만든다.
- **append-only 파일을 이어읽을 때 텍스트 모드 `tell()/seek()` 을 쓰지 마라.** 텍스트 모드의 오프셋은
  바이트 값이 아니라 opaque 라서 `tell()-4096` 같은 계산이 `UnicodeDecodeError` 로 수집기를 죽인다
  (실측: 장중 2시간50분 수집 중단·전량 결손). 오프셋을 상태파일에 저장해 재개하려면 **바이너리 모드**로
  열거나 라인 단위로 다시 읽어라.

### 6a. 시세 테이블의 인덱스·자원 위생 ("시스템을 이해하고 최적화해줘" 요청의 첫 단계)

최적화 요청을 받으면 **추측하지 말고 스캔 통계부터 뽑는다** — 인덱스 이름만 보면 중복이 안 보인다.

```sql
select indexname, indexdef from pg_indexes where tablename='market_data';
select relname, seq_scan, coalesce(idx_scan,0), n_live_tup from pg_stat_user_tables order by seq_scan desc limit 6;
select relname, pg_size_pretty(pg_total_relation_size(relid)) from pg_stat_user_tables order by 2 desc limit 6;
```

- **같은 컬럼 조합의 유니크 인덱스가 둘 있으면 하나만 남긴다**: 실측 `market_data` 에
  `(stock_code, trade_date)` 유니크 인덱스가 두 개(각 131MB, 정의까지 같은데 이름만 다름) 있었다 →
  하나 DROP(**−131MB** + 매 INSERT 비용 감소). 이름이 아니라 `indexdef` 로 비교해야 발견된다.
- **날짜 범위 전용 인덱스가 없으면 붙인다**: 야간 잡(신선도·갭·감사·탐색)은 `trade_date > X` / `GROUP BY trade_date`
  형태를 자주 쓰는데, 선두 컬럼이 `stock_code` 인 복합 인덱스만 있으면 플래너가 그걸 못 쓴다 →
  `idx_market_data_trade_date`(21MB) 추가로 626MB 테이블의 **순차 스캔이 Index Only Scan 으로 전환**된다.
  순효과 실측: 인덱스 합계 262MB → 152MB. 살아있는 스택에는 `CREATE INDEX CONCURRENTLY`, 후에 `ANALYZE <table>`.
- **스키마 원본을 같이 고쳐라**: 인덱스를 만드는 파일(예: `init-scripts/postgres/01_schema.sql`)을 함께
  갱신하지 않으면 다음 재초기화에서 중복 인덱스가 되살아난다(같은 줄에 이유를 주석으로).
- 컨테이너 자원도 같이 본다(`docker stats --no-stream`) — 메모리 상위(Neo4j·news-analyzer)와 재시작 0건 여부.
  보고는 항상 **전/후 수치**로 한다("최적화했다"는 문장은 증거가 아니다).

### 6b. 리포 밖에서 시스템을 한 장으로 정리해 두기

최적화·이해 요청이 반복되면 레포에 **실측 지도 문서**(예: `docs/SYSTEM_MAP.md`)를 두고 다음 요청에서 먼저 읽는다:
데이터 흐름(수집→피처→모델→스크리너→주문) · 자원 실측 · 테이블 상위 · **알려진 함정** · 미조치 최적화 후보(비용 추정 포함).
함정은 그 문서에 "추정"이 아니라 "실측"으로만 적는다.
재부팅·재가동 직후 점검 명령 묶음과 로그 오독 방지: `references/restart-verification.md`.
자동 감사 스크립트: `scripts/verify_market_data.py` — 월별 커버리지, 휴장 제외 공실, 부분 적재일, 무거래(가격 0) 행, OHLC 동결 종목, 분봉 요약을 한 번에 출력한다.

- **market_data를 읽는 코드에서 psycopg2 numeric은 `Decimal`로 온다.** `float/int/str`만 처리하는 숫자 변환 헬퍼는 DB에서 온 가격·거래대금을 전부 None으로 만들어 대상을 조용히 전멸시킨다(실측: 후보 20건 전량이 "가격 없음"으로 제외). 변환 헬퍼 마지막에 `float(value)` 폴백을 두거나 `Decimal`을 명시적으로 처리한다 — JSON 파일에서는 float로 오므로 파일 입력만 테스트하면 못 잡는다.
- **psycopg2 의 Python↔SQL 타입 경계에서 조용히 0건이 되는 함정 2개** (둘 다 예외 없이 "아무것도 안 들어감"으로 나타난다):
  - `date` 컬럼은 **`datetime.date`** 로 오는데 payload 는 `'YYYY-MM-DD'` 문자열인 경우가 많다 → `'2026-08-12' in {date(2026,8,12)}` 는 **항상 False**. 집합 비교 전에 `r[0].isoformat()` 로 문자열 통일하거나 컬럼을 `::text` 로 맞춘다.
  - `WHERE trade_date = ANY(%s)` 에 파이썬 문자열 리스트를 넘기면 `text[]` 로 어댑트되어 `operator does not exist: date = text` 다 → `%s::date[]` 로 캐스팅한다.
- **저장 전 필터(패딩·범위 제거)를 새로 넣으면 '살아남은 행수'를 로그와 반환값으로 남겨라.** 필터가 전량을 버리면 러너는 예외 없이 `+0행` 으로 끝나고, 다음 단계는 그 0을 "이미 적재됨"으로 오독한다 — 0 이면 실패로 다룬다(반환값을 호출부에서 검사).
