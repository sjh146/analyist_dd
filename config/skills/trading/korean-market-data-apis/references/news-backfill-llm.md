# 뉴스 과거 백필 → LLM 분석 → 피처 살리기

감정·이벤트 피처가 상수 0 인 파이프라인에서 AUC 천장을 올리는 유일한 실질 레버. GPU 불필요(API 만).

## 1. 수집 (무료)

```
q = f'"{종목명}" after:{start} before:{end}'
url = "https://news.google.com/rss/search?q=" + quote(q) + "&hl=ko&gl=KR&ceid=KR:ko"
```

- RSS 1회 응답 상한 ≈ 100건. **상한에 닿은 창은 1주 단위로 재분할**한다(분할 없이 넘기면 그 구간 기사 일부가 조용히 누락).
- 창 설계: 종목 × 2주. 50종목 × 6개월 ≈ 650회 질의(호출 간 최소 지연, 무료).
- 저장: `(source, title, content, url, published_at)` — `published_at` 은 RSS `pubDate` 파싱(GMT → KST 변환 주의).
- **중복 제거 키는 URL**(제목은 매체마다 변형된다). UPSERT 로 재실행 가능하게 만든다.
- 창 단위 진행 로그 + 누적 신규 건수를 찍어 진행률을 읽는다(장시간이면 background + 로그 폴링).

## 2. LLM 분석 (유료 · 상한 필수)

- 대상 축소: 제목에 해당 종목명이 포함된 기사만 분석(무관 기사 제거) → 비용·시간 절감.
- 호출 상한을 **코드 상수/인자로 강제**(예 `--max-articles 6000`). 실행 전 예상 비용을 계산해 사용자에게 알린다.
  - 기사 1건 ≈ 입력 1.5~3k 토큰 + 출력 300~600 토큰. 6,000건 ≈ $5~10 (모델 단가로 계산).
- 동시성 8 이하, 기사당 1콜, 실패는 1회 재시도 후 건너뛰고 실패 수를 집계.
- 결과를 `news_analysis` 행에 반영(감성·진위·신뢰도·raw_response) + 종목 연결.
- 보고에 **호출 수·토큰(또는 문자수 기반 추정)·추정 비용·건너뜀 수**를 반드시 포함한다. 상한 도달 시 "상한에서 중단"을 명시한다.

## 3. 피처 테이블로 집계 (여기서 피처가 살아난다)

1. **피처 빌더 코드를 먼저 읽는다** — 감정/뉴스 피처가 어떤 테이블·컬럼을 어떤 창으로 읽는지 확인한다(예: 감성 평균·기사 건수의 5일/20일 창).
2. `(stock_code, date)` 단위로 upsert: 감성 평균, 기사 건수, (필요하면) 이벤트 유형별 건수.
3. 이벤트 피처까지 살리려면 이벤트 추출 결과도 해당 테이블에 넣는다.

검증 순서(반드시 이 순서):
1. 특정 종목·날짜의 피처 값이 0 이 아닌지 — 피처 빌더를 직접 돌려 출력.
2. 비영 피처 개수(before/after) — 커버리지 지표가 있으면 그 수치로.
3. 같은 설정을 **멀티시드**로 재학습해 AUC before/after 비교(단일 시드 금지).
4. 게이트를 넘으면 후보 저장 + OOS 측정. 넘지 못하면 "데이터를 채웠는데도 AUC 변화 없음/미미"를 그대로 보고한다 — 이것도 유효한 결과다.

## 4. 보고 형식

수집 기사 수(창별) → LLM 호출·토큰·추정 비용·건너뜀 → 집계 건수 → 피처 alive/dead 변화 → AUC before/after(시드별 + 평균±std) → OOS → 남은 한계.
신뢰구간 없이 "개선됐다"고만 쓰지 않는다.
