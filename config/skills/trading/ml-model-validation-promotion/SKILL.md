# ML 모델 재학습·검증·승격 (champion/challenger)

언제: 파이프라인이 주기적으로 모델을 재학습해 서비스에 반영할 때, 또는 "AUC X 이상인 모델을 만들어 달라"는
요청을 받았을 때. 원칙: **측정하지 않은 목표를 약속하지 않고, 단일 측정값을 성능으로 보고하지 않는다.**

## 1. 목표 수치를 받으면 그 수치의 출처를 먼저 캔다

"예전에 0.6 이상이 안정적으로 나왔다" 같은 기준을 재현 목표로 삼기 전에 확인한다:

1. 그 값이 **val / test / OOS** 중 무엇이었나 (`ensemble.train(..., X_val, y_val)` 뒤 `roc_auc_score(y_test, ...)` 인지 확인).
2. 같은 시기의 다른 실행이 얼마나 흔들렸나 — 같은 설정이 0.44↔0.61을 오간 기록이 있으면 "안정적"은 성립하지 않는다.
3. 여러 설정을 **같은 split**에서 스윕해 최고값을 골랐나 — 수십 개 설정이면 최고값은 선택 편향으로 부풀려진다.
4. 표본 크기 — n≈1,200 이면 AUC 표준오차가 대략 ±0.015 이므로 ±0.01 차이는 신호가 아니다.
5. 라벨 정의(예: 다음날 방향은 up_rate ≈ 0.47)로 인한 **구조적 상한**을 먼저 말한다. 데이터 결손과 신호 부족을 구분한다.

## 2. 검증은 3종 세트로 한다

- **멀티시드 ≥5**: 시드별 값을 그대로 나열하고 **평균±std**로 판정한다. 단일 시드·단일 split 최고값은 증거가 아니다.
- **시간순 창(워크포워드)**: 훈련=과거, 평가=미래. 한 구간에 과적합된 값이 일반화로 오독되지 않게 한다.
- **소비자 프로토콜 OOS**: 소비자(스크리너·피드)가 쓰는 것과 **같은 유니버스·같은 기간·같은 스크립트**로 후보와 현 챔피언을 같은 날 측정해 비교한다. val과 OOS는 실제로 엇갈린다(champion val 0.6131 → OOS 0.4924 사례).
- 학습로그의 val 곡선과 최종 test/OOS가 크게 벌어지면(예: 0.67 vs 0.52) "최근 구간 regime shift 또는 라벨 노이즈"를 의심하고 창 민감도 실험을 따로 돌린다.

## 3. 승격은 게이트로만 (직접 덮어쓰기 금지)

- 훈련은 **후보 디렉터리**에만 쓰고(`--out-dir`), 승격은 전용 승격기로만 한다:
  후보 산출물 완전성(모델 파일 + 피처 계약 + `auc.txt`) → 메타와 `auc.txt` 일치 → 절대 하한(min-auc) → 현 챔피언 이상,
  순서로 통과할 때만 복사하고, **직전 챔피언을 `champion_prev_<ts>`로 백업**해 한 줄로 되돌릴 수 있게 한다.
- 스모크·검증 스크립트가 champion 디렉터리에 저장하도록 두지 않는다 — 소량 데이터 스모크 모델이 라이브 모델을 조용히 대체한다(실측).
- 승격 결과(승격/유지/후보 불완전)를 요약 JSON으로 남기고, 파이프라인이 보고하는 AUC는 **라이브 모델의 `auc.txt`**에서 읽는다(폐기된 과거 아티팩트를 읽으면 항상 N/A).
- 승격 게이트가 val만 보면 소비자 기준과 어긋난다 → OOS가 더 좋은 후보를 "val 미달"만으로 버리지 말고, 멀티시드 OOS 분산을 확인한 뒤 사용자에게 승격 여부를 물어 결정한다.

### 재배포 문턱 — 라이브 표본과 OOS 축을 동시에 요구한다

전략·파라미터·모델을 라이브 계좌에 반영하는 결정은 두 축을 **동시에** 만족할 때만 허용한다.

- **A. 라이브 실측**: 현행 규칙 체제에서의 청산 표본이 최소 N(예 20건) 이상이고, 수수료 포함 순손익이 (+).
- **B. OOS**: 세션 단위 순기대가 (+)이고 t ≥ 1.
- 미달이면 **현행 규칙 유지(매매는 계속), 신규 배포만 금지**. 이것을 글로 박아두지 않으면 "오늘 몇 건 벌었다"
  같은 소표본에 반응해 규칙을 또 바꾸고, 바꿀 때마다 표본 카운터가 리셋되어 **영원히 판정 불가** 상태가 된다.
- **OOS 수치를 인용할 때는 in-sample 혼입 여부를 먼저 확인한다.** 같은 챔피언의 세션 기대가 전체표본 −0.286%p /
  in-sample −0.149%p / **OOS-only −0.768%p(t −2.05, 25세션)** 로 갈렸다. 게이트·보고에는 **OOS-only** 를 쓰고,
  학습경계(fit_end/val_start) 이후만 남긴 산출물인지 파일 메타로 확인한다. 혼입값(−0.182%/87세션)을 인용하면
  위험이 4분의 1로 축소되어 보인다.
- **게이트는 기록 장치로 만든다 — 실주문 경로에 자동 잠금을 넣지 않는다**(정상 운영까지 멈출 위험이 더 크다).
  입력은 읽기전용(저널은 사본+`mode=ro`, OOS 파일은 그대로), 출력은 판정 JSON + 종료코드(0 PASS/1 BLOCK/2 입력오류),
  결측은 null+사유로 남기고 **추정으로 통과시키지 않는다**. 배포기록(커밋 메시지·PR)에 판정 JSON을 첨부한다.
- 세션 지표 파일은 스키마가 제각각이라 게이트가 못 읽는 경우가 흔하다 → **게이트가 읽는 평면 키
  (`avg_pct`/`session_expectancy_pct`, `t_stat`, `n_sessions`)를 정본 파일에 같이 넣어** 한 파일로 끝낸다.

### 비교 기준선 설계 — 저장된 운값이 게이트를 잠그지 않게

승격 조건의 '현 챔피언 이상'을 **디스크에 남은 단일 시드 값**(예: `auc.txt`)과 비교하면, 과거의 운 좋은 한 번이
기준선이 되어 그 뒤의 진짜 개선을 영구히 막는다. 실측: 같은 코드·같은 데이터로 학습한 후보가 0.4365 / 0.5790 /
0.6131 로 요동쳤고, 마지막 운값이 기준선이 되자 walk-forward 0.54~0.58 로 개선된 후보가 계속 거부됐다.

- **후보 지표**: 멀티시드 평균(`auc_mean`)이 있으면 그것, 없으면 단일값. 멀티시드 학습을 도입하면 비교가
  자동으로 더 견고해진다.
- **챔피언 기준선**: 승격 시 함께 기록해 둔 **견고 지표 파일**(예: `robust_auc.json`)이 있으면 그 값,
  없으면 레거시 단일값을 **상한(cap)까지만** 인정한다 — 하한과 같은 값으로 캡하면 실질 조건이
  "견고 지표 ≥ 절대 하한"이 되어 운값 잠금이 풀린다.
- **승격 시 견고 지표를 기록**해 다음 비교가 동일 기준이 되게 한다(기준선이 다시 운값으로 오염되지 않음).
- **변동성 게이트**를 함께 건다: 멀티시드 std 가 상한을 넘는 후보는 값이 좋아도 거부한다.
- **절대 하한(min-auc)은 '실측 도달 가능 범위' 안에 둔다** — 하한이 실측 상한보다 높으면 어떤 정직한 후보도
  통과하지 못해 챔피언이 영구 동결되고, 그 사이 학습 데이터가 낡아 train/serve skew 만 커진다(실측: 하한 0.55
  vs 워크포워드 다중 폴드 실측 상한 ≈0.54 → 몇 주간 승격 0건). 하한을 정할 때 기준으로 삼는 것은 실험 최고값이
  아니라 **챔피언 자체를 같은 프로토콜로 재평가한 값**이다.
- **하한은 한 곳에만 있지 않다**: 함수 기본값·CLI 기본값만 바꾸고 끝내면 **오케스트레이터가 플래그를 명시적으로
  넘겨** 무효화된다(실측: 파이프라인 셸이 `--min-auc 0.55 --legacy-baseline-cap 0.55` 를 고정 전달해 기본값 변경이
  아무 효과가 없었다). 변경 전후로 `grep -rn -- "<플래그명>\|<옛 값>"` 을 리포 전체에 돌려 **모든 사본**을 찾고,
  바꾼 뒤에는 실제 사용 경로(파이프라인 스크립트)에서 dry-run 을 돌려 새 값이 적용되는지 확인한다.
- **지표 동형성 — 다른 프로토콜끼리 비교하지 마라, 단 가드는 '그 불일치'에만 건다**: 기준선이 멀티시드
  (`auc_mean`)인데 후보가 단일 분할(`ensemble_auc`)뿐이면 비교가 성립하지 않는다(단일 분할은 낙관적).
  그렇다고 **무조건 막는 가드를 넣으면 새 잠금이 된다** — 생산 학습 경로가 단일 분할만 내보내면 그 경로는 영영
  승격하지 못한다. 가드는 *기준선 지표가 멀티시드일 때만* 발동하게 좁혀라(기준선 JSON 에 `metric` 을 함께
  기록해 두면 판정할 수 있다).
- **기준선 파일은 승격기 단독으로 쓴다**: 별도 견고성 평가가 같은 파일을 덮어쓰면 프로토콜이 섞여 판정이
  느슨해진다(워크포워드 값이 보통 더 낮아 단일 분할 후보가 쉽게 통과). 그런 평가는 다른 이름
  (`robust_walkforward.json` 등)에 쓰게 분리하고, 승격기가 기록한 파일을 건드리지 않게 한다.
- **게이트 변경은 dry-run 으로 실후보 디렉터리에서 검증**한다(라이브·별도 summary 경로 사용). 최소 4케이스:
  ① 하한 미달 → 유지 ② 기존 게이트에서 막혔던 후보 → 통과(잠금 해제 확인) ③ 기준선 파일 있을 때 그 값이
  우선 적용 ④ std 초과 → 거부. "잠금이 풀렸다"는 증거는 옛 게이트에서 거부되던 케이스가 통과하는 것이다.

  ### 승격 지표 자체를 감사하라 — 지표가 OOS 최악을 고를 수 있다

  "비교 가능한 지표끼리 비교"만으로는 부족하다. **그 지표가 OOS 순위를 맞게 매기는지**를 먼저 감사한다:
  기존 모델 풀(챔피언·후보·음성대조군, 8개면 충분)을 **같은 유니버스·같은 피처행렬·추론만**으로
  ①게이트가 쓰는 지표(단일 분할 val AUC) ②정직한 다중 폴드 크로스섹션 AUC 로 동시에 채점하고
  ③두 순위의 스피어만 상관을 계산한다(리포에 기존 도구가 있는지 먼저 찾는다 — 예
  `<repo>/scripts/model_metric_protocol_audit.py`, 없으면 만들어 커밋한다).

  - 실측: 두 지표의 순위 상관이 **−0.81**(거의 반대)이었다. 단일 분할 2위(0.6173) 후보가 다중 폴드
    7위(0.4624), 단일 분할 꼴찌(0.4159)인 대조군이 다중 폴드 1위(0.5199) → 그 지표로 승격하면
    **체계적으로 OOS 최악을 고른다**. "단일 분할은 낙관적이다"로만 넘기면 이 **순위 반전**을 놓친다.
  - 같은 감사에서 **지표 ↔ 돈** 의 상관도 본다: 각 모델의 선택(상위 K, 체결성 필터·비용 반영)의 세션당
    순기대값을 그 모델의 두 AUC 와 상관시킨다. 실측: 단일분할 +0.10 / 다중폴드 −0.24 (n=8) — 어느 AUC 도
    양(+) 기대와 연결되지 않았고 8개 중 양(+) 기대가 0개였다. 이 결론이면 **지표 교체는 과적합 선택을
    막는 안전장치일 뿐 수익 레버가 아니다** → 목표를 AUC 에서 소비자 기대값으로 옮기고 라벨·지평·선택
    규칙(§4 실험 큐)으로 간다. 사용자 보고도 그렇게 한다(지표 개선 ≠ 돈).
  - 후보마다 정직한 지표를 **파일로 남기게** 한다(예 `<candidate>/robust_oos.json` 에 `robust_auc`·
    `metric`·프로토콜 요약·생성시각). 게이트는 그 파일이 있으면 결과에 싣고, **env 하나로만** 그 값 기준
    비교로 전환하게 둔다(파일 없으면 "증거 없는 승격"으로 거부). 기본은 종전 동작(off)이어야 야간
    파이프라인이 그대로 돌고, 켜는 것은 사람의 한 줄 결정이 된다.
  - **전환 전에 기준선을 같은 프로토콜로 다시 재라**: 챔피언의 기록값이 단일 분할이면 정직 지표(예 0.5008)
    보다 0.05 높게 찍혀, 전환하는 순간 어떤 후보도 통과 못 하는 새 잠금이 된다(위 '하한은 실측 도달 가능
    범위 안에'와 같은 함정). 배포 모델 자체를 다중 폴드로 재평가해 기준선 파일에 먼저 반영하고 env 를 켠다.
  - 회귀 테스트 4케이스: 기본 관측(동작 불변) / 정직 지표 열등 → 거부 / 지표 파일 부재 + 정책 켜짐 →
    거부 / 정직 지표 우위 → 승격.

  ### 소비자 문턱 게이트는 공유 초크포인트에 강제한다

  val AUC 는 **순위** 지표라 배포된 스코어 분포가 소비자 문턱을 넘는다는 보장이 없다(실측: val 0.5548 로
  승격한 모델의 라이브 스코어 최대 0.4733 → 소비자 문턱 미달 → 3세션 연속 진입 0건). 검증만 하고 승격을
  막지 않으면 재발한다(실측: 단일분할 0.6173 으로 `would_promote` 판정된 후보가 견고 지표 0.4624 = 무작위 이하).

  - 판정 근거를 **토큰 파일**로 남기고 승격 함수가 그 토큰을 **요구**하게 한다: 후보 일치 + 신선도(TTL, 예 6h)
  + `status=passed`. 파이프라인 안에서만 검사하면 다른 호출자(역할 틱·수동 실행·사후 도구)가 그냥 지나간다 —
  **게이트는 모든 호출자가 지나는 공유 함수에 있어야** 한다(호출자 하나에 배선한 검사는 게이트가 아니다).
  - dry-run 은 거부하지 않고 판정 필드만 보고한다(운영 확인용), 그리고 **env 우회**를 남겨 토큰 만료·검증기
  중단이 승격을 영구 동결시키지 않게 한다.
  - 넣은 뒤 셋을 확인한다: ① 회귀 테스트(토큰 없음·오래됨·다른 후보용·판정≠passed → 거부, 통과 케이스,
  dry-run 미거부, 우회) ② 실 후보 디렉터리 dry-run 으로 판정 필드가 실제로 찍히는지 ③ 단일분할이 좋아도
  견고 지표가 무작위 이하인 후보가 거부되는지.

  ### 기준선은 배포 모델을 직접 재평가해 실측한다

기준선을 정하려고 **새 모델을 학습해 견주지 마라**. 배포된 모델 자체를 여러 시간창에서 평가한다.

- **소비자와 동일한 추론 경로**로 평가한다: 같은 피처 빌더, 같은 피처 계약 파일(모델이 학습된 피처 순서로
  벡터화), 같은 앙상블 predict. 별도 파이프라인으로 재학습·재구성하면 다른 모델을 재는 셈이다.
- **순위 모델에는 날짜별 크로스섹션 AUC 평균**이 맞다(풀링 AUC 는 날짜별 기저율 차이를 섞는다). 창 값을
  창 평균±std 로 제시한다.
- **라벨은 미래수익의 시장상대 이진**(그 날짜 표본 중앙값 기준) + **purge h거래일** — 창 끝 h일은 미래
  가격을 쓰므로 버린다.
- **측정 전에 배포 모델을 스냅샷**하라(`cp -r <champion_dir> /tmp/<snapshot>` 후 `--model-dir <스냅샷>`).
  야간 파이프라인이 측정 중간에 승격하면 비교군이 섞여 "챔피언을 이겼다"가 의미를 잃는다. 승격 여부를
  확인한 뒤에 라이브 디렉터리에 기준선을 반영한다.
- 유니버스·표본 가드: 유동성 유니버스는 **측정 창이 아니라 고정된 최근 N거래일** 기준으로 뽑아라(창 하나만
  보면 최소 거래일 조건을 만족하는 종목이 없어 표본이 비고 '유효 폴드 없음'으로 끝난다). 날짜별 최소
  종목 가드를 표본 크기보다 크게 잡으면 스모크가 항상 건너뛰기만 한다.
- 평가 SQL 을 쓰기 전에 스키마를 확인하라(`information_schema.columns`). 컬럼명 추측 한 번에 실행 한 사이클이 날아간다.
- 무거운 재평가는 **다른 학습·피처 빌드와 동시에 돌리지 마라**(피처 빌드는 CPU·메모리 집약, WSL 메모리
  8GB 급에서는 OOM 이력이 있다). 예약 파이프라인 종료를 기다렸다 시작하는 대기 프로세스로 걸어두되,
  **대기의 완료는 그 대기가 만들 산출물(결과 JSON·로그 최신 시각)로 확인하라** — 세션/게이트웨이가
  재시작되면 이전 세션의 백그라운드 대기 프로세스는 조용히 사라져 아무 일도 일어나지 않는다.
  생존 판정에 `pgrep -f "<패턴>"` 을 쓰면 그 명령줄 자체에 패턴이 들어 있어 자기 자신을 매칭해
  "아직 실행 중"으로 오탐한다 → `ps -eo pid,etime,cmd | grep -v grep` + 산출물 시각으로 판정한다.
  생존 판정 뒤에는 **대기를 다시 걸거나 지금 바로 실행**한다 — 대기가 죽은 상태로 방치하면 측정이 영영 안 돈다.
- **새로 쓰기 전에 기존 도구를 찾아라**: 이 프로토콜을 이미 구현한 스크립트가 리포에 있다
  (예: `<repo>/scripts/champion_robust_eval.py` — 시간창 수·창당 날짜 수·표본 종목 수·호라이즌,
  `--model-dir`/`--write`, 결과 JSON 출력). 없을 때만 새로 만들고, 만들었으면 커밋해 다음 회차가 재사용하게 한다.
- **기준선 파일은 평가가 완주했을 때만 쓴다 — 타임아웃이면 기준선이 옛값으로 남아 게이트가 계속 잠긴다.**
  `--write` 류는 스크립트 **마지막**에 기록하므로 창 수 × 창당 비용이 예산을 넘으면 기록 없이 죽는다(창당 10분+ 소요).
  그러면 새 후보가 견고하게 더 좋아도 비교 기준선은 캡값/옛 운값 그대로라 계속 거부되고, 로그에는 "평가를 돌렸다"는
  흔적만 남아 원인이 보이지 않는다 → 예산을 `창 수 × 창당 비용 + 피처 빌드` 로 계산해 잡고(아니면 창/표본을 줄여 완주),
  **끝난 뒤 기록 파일의 생성·갱신 시각을 반드시 확인**한다. 파일이 없으면 승격 판정 전에 "기준선 미기록"을 먼저 보고한다.
- **기록값과 실측 견고값의 간극을 미리 가늠하라**: `auc.txt` 에 기록된 배포 챔피언을 창별로 재보면
  기록값보다 **0.1 규모 낮게** 나오는 경우가 있다(기록 0.6131 → 창별 0.49~0.52). 그러므로 `auc.txt` 를
  기준선·성능 보고에 쓰기 전에 재평가를 먼저 돌리고, 보고에는 창별 값과 평균±std 를 함께 적는다.

### 승격이 없을 때의 진단 순서 (게이트 거부 vs 후보 미완성)

승격이 안 됐다고 바로 게이트를 의심하면 엉뚱한 곳을 고친다. 로그를 이 순서로 본다.

1. **후보가 완성됐는가** — 학습 프로세스의 종료코드와 진행 카운터. 타임아웃(`exit=124`)이면 후보가 없어
   **승격 심사 자체가 열리지 않았다**. 예산은 `패널쌍수 × 행당 빌드비용` 보다 크게 잡는다(실측: 199피처에서
   행당 약 0.45초 → 200종목×120일 ≈ 2시간인데 30분 예산이라 4,000/16,080쌍에서 중단).
   **피처를 늘리면 이 비용이 같이 는다** — 피처 부활 작업 뒤에는 예산을 재점검하라.
2. **승격 요약 JSON을 읽었는가** — `status`(promoted/kept_incumbent/invalid_candidate)·`reason`·
   `candidate_metric`·`decided_at`. `decided_at` 이 옛 날짜면 이번 회차에 승격 단계가 실행되지 않은 것이다.
3. **파이프라인이 보고한 AUC 를 후보 성능으로 인용하지 마라** — 최종 로그의 "Best AUC" 류 요약줄은 보통
   **라이브 모델의 저장값**이다. 후보 값은 판정 JSON 에서만 읽는다.

## 4. 무인 장시간 실험 루프 (밤샘 등)

- **실험은 직렬화**한다. 피처 빌드/학습 3개 이상 병렬이면 load average가 코어 수의 2배를 넘어 서로를 수 배 느리게 만들고 처리량 측정값까지 오염된다(스레드를 늘릴수록 느려지는 것처럼 보인다). 프로세스당 `OMP_NUM_THREADS=2 MKL_NUM_THREADS=2 OPENBLAS_NUM_THREADS=2`.
- **비싼 중간 산출물은 캐시**한다(패널 행렬 등). 캐시 키에 종목수·기간·마지막 데이터 일자를 포함해 낡은 캐시 재사용을 막는다. 재빌드가 실험 예산을 통째로 태운다.
- 상태 계약을 파일로 남긴다: `heartbeat.txt`(단계·실험ID, 2분 주기), `results.jsonl`(실험 1건 1줄: 설정·시드별 값·평균·std·OOS), `done.flag`/`gate_passed.flag`. 마감이 있으면 "마감 N분 전 이후 새 실험 시작 금지 + 최종 리포트 시각"을 루프 안에 박는다.
- 실험 큐는 우선순위대로: ① 과거 승리 설정 재현 ② 정규화·학습률·깊이·추정기 수 ③ 클래스 가중치 ④ 데이터 위생 필터(거래량 0·완전 동결 행 제외) ⑤ 유니버스 교체(코드순 정렬은 편향) ⑥ 라벨 변형(시장상대·다중일 호라이즌) ⑦ 창 민감도 ⑧ 다중비교 정량화(무작위 N개 분포에서 최고값과 평균의 격차).
- **피처 축이 연속으로 델타 0을 내면 레버를 바꿔라.** 살아있는 피처 수를 늘려도(alive 117→127) 같은
  프로토콜의 폴드평균 AUC 가 그대로면, 그 상한은 피처 부족이 아니라 **신호 부족**이다. 판정은
  `backtest-measurement-validity` §4c 절차(선별 폭만 바꿈 A/B → K 고정 귀속)로 하고, 세 번 연속 0이면
  피처 사냥을 **종결**하고 문제 정의로 넘어간다: 지평·라벨(h5→h1/h3, 변동성·꼬리), 유니버스 축소, 비용·체결,
  룰 기반 단독 검증. 이때도 "부활 실패"와 "부활했으나 무용"을 구분해 쓴다 — 후자는 지표가 아니라 원천·커버리지의
  문제가 아니므로 재시도 가치가 없다.
- **표본 규모가 병목일 수 있다 — 실험 큐보다 먼저 점검하라.** `ORDER BY <코드> LIMIT N` + 단일 시장
  조건은 학습 표본을 임의로 자른다(실측: 한 시장·코드 앞 50개 → 49종목 × 281일 = 13.6k행인데, 같은 DB 에
  3,934종목 × 15개월 = 1.08M행이 있었다). 종목 수를 3배로 늘린 실험군이 **+0.03** 높았고 그 폭은 같은
  기간의 어떤 피처 작업보다 컸다 → 학습 행·종목·거래일 수와 유니버스 선택 조건을 먼저 실측하고 보고한다.
  유니버스 확대는 되돌리기 쉬우므로 **저비용 검증(수백 종목) → 본확장** 순서로 간다. 피처 전량 non-null
  요구도 교집합을 수십 종목으로 붕괴시키니 결측 마스킹을 먼저 검토한다.
- **라벨 호라이즌을 보유기간과 맞춰라**: 라벨이 1일 선행 방향인데 전략이 5일 보유면 검증과 실전이 다른
  문제를 푼다. 중간 구간을 NaN 으로 버리는 **분위 라벨**(상·하위만 학습)과 시장상대(횡단면 중앙값)
  라벨을 함께 스윕하고, 실험에서 이긴 호라이즌이 **스윕 구성 목록에 실제로 들어 있는지** 확인하라
  (구성 id 누락이면 같은 프로토콜 비교가 불가능하다). 누수 차단(purge/embargo)이 없다고 단정하기 전에
  학습·검증 코드를 grep 한다 — 이미 구현돼 있는 경우가 많다.
- **라벨을 바꿀 때는 AUC 옆에 항상 '상위 10% 순수수익/거래'를 같이 잰다.** AUC 는 순위 지표라
  비용을 넘는지 말해주지 않는다. 실측(같은 패널·같은 폴드·왕복비용 0.21% 차감): 1일 라벨
  (다음날 시가→종가) AUC **0.5448±0.0098** 인데 상위 10% 순수익 **−0.36%/거래**·적중 42%,
  5일 상대수익 라벨 AUC 0.5659±0.0617 에 상위 10% **+1.45%/5일**·적중 56%. 폴드 std 가 6배 작은
  쪽이 더 안정적으로 보이나 돈은 반대 — **AUC 안정성 ≠ 수익성**이므로 두 값을 항상 나란히 보고한다.
- **죽은 피처 제거를 AUC 로 정당화하지 마라 — 제거가 AUC 를 올려도 돈은 나빠질 수 있다.** 실측(같은 패널·같은 폴드·
  같은 top-k): 죽은 21개를 빼면 fold_mean AUC **0.5639**(원본 0.5606)로 올랐지만, 비용 반영 순기대는 5일 보유
  **−2.27%/거래(t −2.85)** vs 원본 −0.90%(t −0.82)로 더 나빴다. 제거는 위생(노이즈·연산) 결정으로만 하고
  승격은 순기대값 게이트로만 판정한다. 세 변형의 AUC 차이(±0.003)가 폴드 std(0.067)보다 작으면 그것도 개선으로 보고하지 않는다.
- **승격 판정 도구는 '상위 K 선별 → 실현 수익 − 비용'으로 만들고, 전략 보유기간과 같은 지평에서 잰다.**
  폴드마다 확장창 학습 → 그날 예측 → 상위 K → h일 실현수익에서 왕복비용을 뺀 **일별 순기대의 평균·t·적중률**을 낸다
  (실측 도구: `scripts/promotion_check.py`, `--topk`=하루 진입 건수, `--horizon`=보유일, `--cost-pct` 0.21).
  같은 모델이 5일 −0.90% / 1일 −0.14% 로 10배 차이 나므로 한 지평만 보고하면 전략과 무관한 결론이 나온다.
  AUC 0.578 인 모델이 −2.27%/거래를 낸 사례처럼 **둘을 항상 나란히** 보고하고, 하나라도 음수면 승격하지 않는다.
- **모델을 어느 경로에 얼마나 실었는지 피드 필드로 확인하라.** 같은 리포에서 `close` 는
  `score_kind=screener`(모델 미사용), `swing` 은 `calibrated_prob`(모델 사용), `daytrading` 은
  `composite` + `model_prob` 가중 25% 로 쓰이고 있었다 — 라벨 호라이즌이 1일인데 5일 라벨 모델을
  단타에 25% 싣는 구조였다. 라벨·용도 불일치가 발견되면 모델을 개선하는 대신 **가중을 0 으로 빼고**
  그 몲을 실제로 돈이 나는 축(변동성·테마·수급)으로 재배분하는 것이 먼저다. 판단 근거는 피드
  JSON 의 `score_kind`/`model_prob`/`ml_auc` 를 직접 열어 확인한 값이어야 한다(문서·기억 아님).
- **측정 통계를 소비자에게 넘길 때는 소비자 코드로 단위 계약을 확인하라**: 퍼센트/비율, 정규화 여부,
  가드(0·음수·1 이상)를 실제 소비 모듈에서 읽어 확인한다. 추정 엣지가 **비양수면 다운스트림에 쓰지
  않는다** — 0/음수 사전확률은 진입을 전면 차단하므로, 근거는 소비자가 읽지 않는 경로에 별도 파일로
  남기고 "측정했더니 음수라 쓰지 않았다"를 그대로 보고한다(추정값으로 채우지 않는다). 소비자가 쓰는
  경로에 썼는지 여부는 **파일 존재 여부**로 검증한다.
- 조기 종료 조건을 명시한다(예: 평균 ≥ 목표 AND std ≤ 허용치 → 최종 후보 저장·OOS 측정 후 종료).
- **파이프라인의 하드코딩된 설정만 바꿔 A/B 하려면 파이프라인을 편집하지 말고 얇은 래퍼로 import 한다.**
  `import <pipeline> as p; p.CONFIGS = [...]` 뒤 `p.main()` 을 부르면 같은 코드·같은 폴드로 설정만 바뀐 통제
  실험이 되고, 편집·리버트 리스크와 예약 크론 충돌이 없다. 단 **`main()` 의 시그니처를 먼저 확인**한다 —
  인자를 받지 않고 `sys.argv` 를 직접 읽는 스크립트가 흔해 `main(argv)` 로 부르면 `TypeError` 로 죽는다.
  실험 ID 와 설정 목록을 환경변수로 받게 해두면 한 스크립트로 대조군·처리군을 연속 실행할 수 있다.
- 마감 시각 이후에는 새 실험을 시작하지 않게 하고, 마감 전에 최종 리포트 파일을 반드시 쓴다(무인 실행의 신뢰는 리포트에서 나온다).

## 5. 데이터를 탓하기 전에 (품질 판정 규칙)

- **완전성(행수·거래일 수·일자별 커버리지)과 신호 유무는 다른 축이다.** "백필은 다 했는데 왜 지표가 안 나오냐"에는 ① 커버리지 실측 ② 라벨·표본 특성 ③ 과거 수치의 측정 방식 세 축으로 답한다.
- **"동결/무변동" 행을 느슨하게 세면 과대집계된다**: `시가=전일시가 AND 종가=전일종가`만 보면 정상 무변동일까지 포함된다(실측 3.78%). `시·고·저·종가 + 거래량`이 전부 직전일과 같은 행(3.25%)이고 그중 거래량>0인 것만 진짜 이상치다. 상위는 거래가 드문 종목(예탁증권 등)이다.
- 데이터 품질을 원인으로 지목하기 전에 **재현 가능한 쿼리와 수치**를 준비하고, 앞서 한 진단이 틀렸으면 먼저 정정한다.
- **피처가 '죽었다'고 판정하기 전에 그 피처 테이블의 최신 일자와 writer 의 실행 여부를 보라.** 낡은 패널은
  살아 있는 피처를 0으로 보이게 한다(실측: nonzero=0 인 97개 중 65개는 패널 낡음 때문이었고 현행 코드로 값이
  나왔다 — 실제로 죽은 것은 32개). 그래서 부활 작업의 첫 단계는 피처 재작성이 아니라 **리더·writer 배선 확인**이다:
  ① 리더가 어느 테이블을 보는가(실측: 커버리지 9/200종목인 테이블을 보고 있었고, 정본은 197종목) ② 그 테이블을
  채우는 빌더가 크론·파이프라인에 걸려 있는가(실측: 아무도 돌리지 않아 6거래일 낡아 있었다 → 리더만 고쳐도
  프로덕션에서는 아무 값도 안 변한다). 수리 = writer 손실행으로 최신화 → 상류 데이터 도착(공시·시세 크론)과
  학습 시작 사이에 크론 예약 → **최신 날짜로 종단 확인**(리더를 실제로 호출해 나온 값을 DB 원본과 대조).
- 스모크 판정은 문서의 수치가 아니라 **직접 측정**으로 한다: 문서가 'N개 죽음'이라 해도 그중 몇 개는 낡은
  스냅샷 아티팩트일 수 있으니, 그 문서를 그대로 작업 목록으로 쓰면 없는 문제를 고치느라 시간을 태운다.
- **재빌드 전에 패널의 계열별 비영비를 10초로 세라 — 원천이 0이면 재빌드해도 0이다.** 저장된 패널
  행렬과 피처 이름을 그대로 열어 접두어 계열별 `(X[:, idx] != 0).mean(axis=0)` 을 계산한다. 실측
  (22,382×217 패널): event 20열 평균 0.081 · sentiment 7열 **0.0007** · news 2열 0.001 · sns 22열 0.827 ·
  theme 3열 0.474 — 감성·뉴스 계열은 원천 커버리지가 33~49종목/일에 그쳤기 때문에 재빌드해도 새 값이
  생기지 않는다. **순서는 원천(수집·종목 귀속·보존기간) → 커버리지 상승 확인 → 재빌드**다.
  반대로 비영비가 이미 높은 계열(event·sns)의 저성능은 파이프라인 고장이 아니라 유형별 희소성일 수 있으니
  계열 단위로 나눠 판단하라.
- **기준선은 패널(유니버스)에 종속된다 — 다른 패널에서 잰 AUC를 기준선으로 인용하지 마라.** 같은
  라벨·같은 설정(분위0.30·h5·top30)이 **49종목 패널 0.5405** vs **200종목 유동성 패널 0.5107 ± 0.1059**
  (5폴드×3시드)로 갈렸다. 폴드 std(0.106)가 사전 문턱(+0.02)의 5배이므로 작은 델타는 보고하지 말고
  폴드 목록과 std를 함께 적는다. 기준선 재측정은 재빌드 없이 몇 분이면 된다(기존 패널 + 기준 config 1개만
  지정하는 스윕). 넓은 패널 수치를 판정 기준으로 삼고, 좁은 패널의 개선을 그대로 승격 근거로 쓰지 마라.
- **재빌드 자체가 유니버스를 바꾼다 — 선정 규칙이 '최근 데이터순'이면 서로 다른 시점 패널은 다른 표본이다.**
  같은 스크립트·같은 파라미터로 두 달 뒤 재빌드한 패널의 종목 교집합이 **23/200**까지 떨어졌다. 그래서
  "재빌드 후 생존/성능이 어떻게 변했나"를 횡단 비교하면 개선과 표본 교체가 섞인다 → 같게 만들려면 **명시 코드
  목록**으로 새 파일에 빌드하고(기준선 npz 덮어쓰기 금지) sidecar 의 `codes_sha1` 로 동일성부터 확인한다.
  소요는 실측 **2~4 페어/초**(200종목×314일 = 61,640 페어 ≈ 5~7시간)이므로 밤 1회 예산으로 잡고 500행
  체크포인트 저장 여부로 진도를 판단한다.
- **재판정에서 클래스가 '상수0 → 희박'으로만 움직이면 nnz 를 보라.** 12개가 이동했어도 nnz 가 0.02%
  (nnz≥1% 는 0개)면 실질 부활이 아니다 — 이때 원인은 피처 코드가 아니라 **원천 커버리지·개체 연결**이다.

## 6. 보고 규칙

- val과 OOS를 **분리해서** 제시하고 n을 함께 적는다. "구조적 사실"과 "하루/한 시드 표본의 방향성"을 구분한다.
- 목표 미달이면 미달이라고 쓴다: 최고 달성치, 실험별 시드 값, 실패 원인, 그리고 목표를 위해 무엇이 더 필요한지(데이터·라벨 재정의 등).
- 승격/미승격은 실제 명령과 백업 경로까지 적어 사용자가 한 줄로 되돌릴 수 있게 한다.
- **사용자 몫 블로커(자격증명 발급·서비스 승인 등)는 '사용자가 할 것 / 내가 할 것'으로 분리해 제시**한다.
  사용자 항목에는 정확한 사이트·메뉴 경로와 어느 값을 어디에 넣는지, 그리고 **그 항목이 회수하는
  피처·지표 수**를 붙인다. 사용자는 이 체크리스트 형식을 선호하고, 코드로 못 푸는 항목만 남겨 받는다.
- 산출물이 낡았을 수 있는 지표(캐시된 진단 스냅샷 등)를 인용할 때는 **스냅샷 시각과 계약 수를 함께 밝히고**
  "최신 재측정 진행 중"인지 구분해 말한다 — 낡은 수치를 현재값으로 보고하면 다음 판단이 틀어진다.
- 예약 실행(크론·야간 파이프라인) 직전에 그 스크립트를 편집하지 마라 — 셸은 실행 중인 스크립트를
  바이트 오프셋으로 재읽기 하므로 오작동을 만들 수 있다. 편집은 실행 전 여유 시간에 끝내고 시작 여부를
  확인하거나, 종료 후 반영한다.
