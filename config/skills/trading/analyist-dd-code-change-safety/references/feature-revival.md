# 죽은 피처 진단·부활 (패널 재빌드 → 커버리지 → 성능 게이트)

대상: 학습 패널(`services/xgboost-ml/app/models/wf/panel_*.npz`)의 피처가 상수 0/희소로 죽어
"부활" 작업을 할 때. 순서를 지키지 않으면 3시간짜리 재빌드를 여러 번 돌리고도 아무것도 못 얻는다.

## 0. 진단 순서 (비싼 것부터 하지 말 것)

1. **패널이 언제·어떤 소스로 만들어졌는지 먼저 본다** — npz mtime vs 소스 테이블의 `min/max(날짜)`.
   패널이 소스보다 앞서 만들어졌으면 그 구간은 "피처가 죽은" 게 아니라 **원천이 없었다**.
2. **유니버스 드리프트를 확인한다.** `--universe prod` 는 "최근 데이터순 상위 N종목"이라 몇 주 뒤
   재빌드하면 **다른 종목 집합**이 나온다(실측: 교집합 23/200). 이 상태로 v1 vs v2 델타를 내면
   "개선"이 아니라 "다른 표본"이다 → A/B 가 필요하면 빌드에 **명시적 코드 목록**을 넘겨라.
   비교 스크립트를 쓸 때는 교집합 수를 리포트 헤더에 찍고 "같은 종목 개선이 아니다"를 명시한다.
3. **커버리지를 종목 단위로 센다** — 소스 테이블 전체 건수가 아니라
   `select count(distinct stock_code) from <src> where stock_code = ANY(<패널 코드>)`.
   소스에 수만 행이 있어도 패널 종목엔 없을 수 있다.
4. 상수 0의 정체를 가른다: `null_ratio 0 + std 0` 은 **결측을 0으로 덮은 것**이고,
   `nnz < 5%` 는 **희소**(이벤트·뉴스)다. 둘의 처방이 다르다(전자=리더/조인, 후자=정의).

## 1. 재빌드 비용과 쓰기 경로

- 처리량은 실측 기준 **약 4 페어/초**(페어 = 종목×날짜 1건의 피처 계산). 200종목×314일=61,640페어 ≈ **4시간**.
  `wf_wave.build_panel` 은 500행마다 체크포인트를 남기므로 중단해도 이어서 재개된다 → 반드시 `--panel-out`
  **새 경로**로 돌리고 기존 패널은 건드리지 않는다(대조군 보존).
- **패널 디렉터리는 컨테이너가 root 로 쓰는 경우가 많다**(`drwxr-xr-x root root`).
  호스트에서 그 디렉터리에 새 npz 를 쓰면 `PermissionError: [Errno 13]`. 사용자 소유 경로
  (예: `data/panels/…npz`)에 쓰고, 모델이 그 파일을 직접 읽어야 하면 컨테이너 쪽에 두는 별도 경로를 쓴다.
- 빌드 로그는 Neo4j 경고(`Neo.ClientNotification ... FOLLOWS_CYCLE`)로 가득 찬다 — 무해하니
  `grep -v Neo.ClientNotification` 으로 진행률/체크포인트 줄만 본다.

## 2. 재빌드만으로는 안 살아난다

실측: 재빌드로 상수0 24개 중 12개가 "희소"로 이동했지만 **nnz 0.02%** 수준이라 여전히 무용.
죽음의 주된 원인은 경과 시간이 아니라 **소스 커버리지·종목 연결**이다.
따라서 재빌드 뒤에도 dead 가 남으면 다음은 커버리지 수리(§3) 순서다.

## 3. 종목 연결(링크) 수리

- **이름 매칭이 정확 일치뿐이면 조용히 NULL 이 된다.** 정규화(공백·`(주)`·`㈜`·`주식회사` 제거,
  대문자화) → 별칭 테이블 → **정규화 부분일치가 정확히 1건일 때만** 성공. 2건 이상은 실패로 남긴다
  (오매핑은 누수·오염이다). 실패는 **원장 테이블에 upsert**해 관측 가능하게 해라 — `None` 으로 두고
  로그도 안 남기면 "왜 피처가 0인가"를 영원히 못 푼다.
- **이벤트 텍스트에서 종목명을 찾아 NULL 을 채우는 방식은 쓰지 마라.** 짧은·일반명사 종목명
  (예: '남성', '대양')이 무관한 기사 본문에 걸려 오탐이 대량 발생한다(실측: "가해 남성으로부터…" →
  종목 '남성'). 재연결은 파서·LLM 이 **명시한 종목명**에 대해서만 한다.
- 뉴스 커버리지가 낮은 진짜 이유가 "피드 단위 수집"인지 확인: RSS 수집기가 일반 피드만 받으면
  기사에 등장한 소수 종목만 잡힌다(실측: 패널 200종목 중 31종목).

## 4. 종목별 뉴스 수집(무료 경로)의 실무 파라미터

- Google News RSS 기간 질의: `https://news.google.com/rss/search?q=<종목명> after:YYYY-MM-DD before:YYYY-MM-DD&hl=ko&gl=KR&ceid=KR:ko`
  (창당 최대 100건 → 2주 창으로 쪼갠다).
- **호출 간격 1.2초는 HTTP 429 로 막힌다. 6초에서 안정적으로 통과**했다(800질의 ≈ 80분).
  429 는 재시도로 뚫지 말고 간격을 올려라.
- **정밀도 가드: 제목(title)에 종목명이 포함될 때만 저장.** 본문 매칭은 위 §3 의 오탐 문제를 그대로 만난다.
  종목명 정규화 길이가 3자 미만이면 제목에서 **독립 토큰**으로만 인정한다.
- 실측 산출: 800질의 → 기사 11,990 → 가드 통과 8,369 → 삽입 7,180(rejected 30%), 커버리지 31 → **193종목**.

## 5. 살아난 피처를 모델에 넣기 전 성능 게이트

"alive ≠ 유용" — nnz·분산이 살아났다는 것과 예측력은 별개다. 투입 전에 **일별 횡단면 rank-IC** 를 잰다:

```sql
-- 예: mention_7d vs 5일 선행수익
with px as (
  select stock_code, trade_date, close_price::float8 px,
         lead(close_price::float8,5) over (partition by stock_code order by trade_date) fwd5
  from market_data where trade_date between :d0 and :d1)
select f.stock_code,f.trade_date,f.mention_7d,px.px,px.fwd5
from news_mention_features f join px using (stock_code,trade_date)
where px.fwd5 is not null and px.px > 0
```
→ 날짜별로 `spearman(feature, fwd_ret)` 를 구해 **평균·중앙·양수일 비율**과 5분위 수익률 단조성을 본다.

- 실측 예: `mention_7d` 평균 IC −0.010 · 중앙 +0.015 · 양수일 56%(25일) · 5분위 단조 없음 → **투입 보류**.
  변환(log, surprise=`(7d+1)/(30d/30*7+1)`)도 +0.0023 수준.
- 표본이 30거래일 미만이면 "신호 없음"도 "있음"도 단정하지 말고 **보류 + 재측정 계획**으로 보고한다.
- 이 게이트를 통과하기 전에는 학습·승격 파이프라인에 컬럼을 붙이지 않는다(재학습 비용만 쓰고 AUC 는 그대로다).
