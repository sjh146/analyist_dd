# 역할 협력 설계 — 6개 페르소나를 '한 팀'으로 묶는 계약·버스·조정 (2026-11-16)

작성: 엔지니어 세션(사용자 요청 "페르소나들이 더 유기적으로 협력하는 방법")
대상: 리서처 · 엔지니어 · 트레이더 · 감사(auditor) · CEO · 리뷰보드(council)

---

## 1. 지금 실제로 어떻게 돌고 있나 (실측)

| 구성요소 | 크기 | 역할 |
|---|---|---|
| `docs/QUANT_BOARD.md` | **547KB** | 모든 역할이 절을 append 하는 단일 문서 |
| `docs/QUANT_MODEL_BACKLOG.json` | **1.6MB** | 엔지니어 백로그 |
| `docs/QUANT_RESEARCH_BACKLOG.json` | 205KB | 리서처 백로그 |
| `docs/QUANT_TRADER_BACKLOG.json` | 40KB | 트레이더 백로그 |
| `data/reports/model_engineer_ledger.jsonl` | 1.4MB | 엔지니어 원장 |
| `data/reports/researcher_ledger.jsonl` | 132KB | 리서처 원장 |
| `data/reports/trader_ledger.jsonl` | 70KB | 트레이더 원장 |
| 역할별 크론 틱 | 20+ 개 | 각자 상승/판정/보고 |

즉 **협력의 매체가 "사람이 읽는 큰 문서 + 각자 원장"** 이다. 기계가 읽는 계약은 거의 없다.

### 이 구조가 만든 실제 손실 (2026-11-16 한 세션에서 확인된 것)
1. **뉴스 백필이 몇 주간 0건**: `news_event_backfill.py` 의 `WHERE source='google_news'` 가
   수집기가 저장하는 값(매일경제/이데일리/…)과 달라 대상 기사가 **항상 0건**이었다.
   아무 역할도 이걸 검사하지 않았고, 그 결과 감성 7피처 + 이벤트 12피처가 죽은 채 유지됐다.
2. **유니버스 상한 250종목**: 같은 기사에서 종목 귀속이 46종목에 잘려 있었다(전 종목 사전 = 62종목).
   "수집량"을 논의하는 자리에서도 유니버스 상한은 아무도 보지 않았다.
3. **MT116 재발**: 엔지니어는 AUC 게이트로만 승격을 판정하고, 소비자(트레이더)의 확률 문턱(0.55)은
   승격 시점에만 확인된다. 어젯밤 후보 최대 0.5343 → 신호 0건. 생산자·소비자 계약을 **상시** 보는
   주체가 없었다.
4. **중복 진단**: 같은 지표(피처 커버리지·AUC·경로)를 리서처·엔지니어·감사가 각자 다시 계산한다.
   선점(claim) 개념이 없어서다.

> 결론: 역할이 모자라서가 아니라 **경계(boundary)를 아무도 검사하지 않아서** 잃고 있다.

## 2. 설계 원칙 5개

1. **경계를 코드로 검사한다.** 생산자·소비자 계약(피드 스키마, 확률 문턱, 피처 커버리지, 시세 최신성)은
   문서가 아니라 **매일 도는 체크**로 존재해야 한다. → `scripts/contract_check.py` (구현됨)
2. **작업은 선점(claim)하고, 인계는 버스로 흐른다.** "누가 지금 이걸 잡고 있나"를 파일 한 줄로 안다.
   → `scripts/role_bus.py` (구현됨)
3. **하루에 하나의 목표.** 역할 6개가 각자 최적화하면 합이 최적이 아니다. CEO가 매일 아침
   `data/state/one_thing.json` 을 발행하고 모든 틱이 시작 시 그것을 먼저 읽는다.
4. **교차 검증.** 실험 결과는 소유자가 아니라 **다른 역할이 재현**해야 원장에 채택된다
   (`verifier` 필드). 자기신고 채택 금지는 이미 원칙이지만 대상이 '사람 보고'뿐이었다.
5. **조용한 실패를 금지한다.** 계약 위반·인계 지연·틱 실패는 Discord로 **전이 시점에만** 알린다
   (스팸 없이, 놓치지도 않게). 현재 알림 백로그/워치독 구조를 그대로 재사용한다.

## 3. 구현 (이번 세션에서 실제로 만든 것)

### 3.1 `scripts/contract_check.py` — 경계 검사기 (구현·검증 완료)
6개 계약을 PASS/FAIL 로 판정하고 `data/reports/contract_check_latest.json` 에 남긴다.

| ID | 계약 | 소유 역할 | 실측 예(2026-11-17 01:3x) |
|---|---|---|---|
| DATA-1 | 시세 최신성(오늘-4일 이내) | 리서처 | PASS — 최신 2026-11-16 |
| FEAT-1 | 죽은 피처 ≤45 · 측정 7일 이내 | 엔지니어 | PASS — 38/202, 4일 전 |
| NEWS-1 | 최근 7일 뉴스 종목 귀속 ≥30 | 리서처 | PASS — 211종목 |
| NEWS-2 | 백필이 볼 수 있는 기사 > 0 | 리서처 | PASS — 347건 |
| FEED-1 | 피드 신선도·가격누락·신호나이 | 트레이더 | PASS — 0.7일 전, 후보 20건 |
| FEED-2 | 소비자 확률 문턱(MT116) | 엔지니어↔트레이더 | PASS — swing 20/20 |

운영 제안: 크론 `10 8,13,20 * * *`(장전·장중·장후) → 실패 시에만 Discord.
`owner` 필드가 있으므로 FAIL 알림에 **담당 역할**이 자동으로 붙는다.

### 3.2 `scripts/role_bus.py` — 역할 버스 (구현·검증 완료)
`data/reports/role_bus.jsonl` 에 한 줄씩 append. 이벤트: `claim / release / result / handoff / decision / blocked`.
- `claim` 은 TTL(기본 180분)을 가지며, 다른 역할이 잡고 있으면 **exit 3** 으로 거절된다(중복 작업 차단).
- `handoff --to <role>` 은 인계, `open` 은 아직 결과 없는 선점 목록(인계 지연 감시).
- 검증: post → claim → 타 역할 claim(rc=3 거절) → open 표시까지 실측 통과.

틱 스크립트에 3줄만 넣으면 된다(예: 리서처 틱).
```
python3 scripts/role_bus.py claim --role researcher --task "$TASK" || exit 0     # 이미 누가 잡음
trap 'python3 scripts/role_bus.py release --role researcher --task "$TASK"' EXIT
python3 scripts/role_bus.py post --role researcher --kind result --task "$TASK" --note "..."
```

### 3.3 `data/state/one_thing.json` — 하루 한 목표 (설계)
CEO 틱(23:45)이 다음 날 목표를 발행한다. 입력: `contract_check_latest.json` FAIL, `role_bus` 열린 인계,
`quant_scoreboard` 스탠자, 트레이더 순기대. 스키마:
```json
{"date":"2026-11-17","goal":"뉴스 종목 귀속률 30% 달성","owner":"researcher","metric":"NEWS-1",
 "baseline":211,"target":400,"why":"감성 7피처가 죽은 유일한 원인","deadline":"2026-11-17T20:00+09:00"}
```
각 틱은 시작 시 이 파일을 읽고, 자기 백로그에서 이 goal 에 기여하는 항목을 **최우선**으로 올린다.
(구현 비용 작음: 기존 `*_cycle.py` 의 next_item 정렬 키에 `boost = 1 if item.id == goal.id else 0` 추가.)

| 단계 | 내용 | 비용 | 리스크/완화 |
|---|---|---|---|
| **1주** | ① `contract_check.py` 크론 3회/일 + Discord ② `role_bus` 를 리서처·엔지니어 틱에 연결 ③ 인계 SLA(24h) 알림 | 반나절 | 틱 스크립트 수정은 각 역할 소유 → 리뷰보드 승인 후 일괄 적용 |

| **1개월** | ⑥ 역할별 지연/실패/중복 지표를 Grafana 한 화면에 ⑦ 실패 → 원인 → 담당 자동 배정(포스트모템) | 2~3일 | 지표가 목표가 되지 않게 '판정은 돈 지표' 원칙 유지 |

**측정 지표(협력의 성과)**: 중복 작업률(같은 task claim 충돌 수/주) · 인계 중앙 지연(시간) ·
계약 위반 건수(주) · 죽은 피처 수 · 신규 진입일수 · 순기대(원/세션).
"역할이 많이 돌았다"는 지표로 쓰지 않는다.

## 5. 하지 말 것 (안티패턴)

- **역할을 하나로 합치기**: 역할 분리는 '관점 충돌'을 만들기 위한 장치다. 합치면 AUC-편향(엔지니어)과
  돈-편향(트레이더)의 긴장이 사라져 MT116 같은 사고가 오히려 늘어난다.
- **보드를 더 크게 만들기**: 547KB 는 이미 사람이 못 읽는다. 새 협력 정보는 **JSONL(기계) + 요약 1줄(사람)**
  로만 추가한다.
- **알림을 늘리기**: 계약 위반은 '전이'에서만, 실패는 실패일 때만. 상시 알림은 곧 무시된다.
- **AUC 를 공동 목표로 두기**: 협력의 공동 목표는 **순기대(원)** 이고, AUC 는 엔지니어의 수단일 뿐이다.
