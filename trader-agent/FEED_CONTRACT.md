# FEED_CONTRACT.md — analysit_dd → trader-agent 데이터 계약

이 문서는 GPU 머신의 `analysit_dd` 가 **무엇을, 어떤 형식으로, 언제** 보내야 하는지를
정의한다. 소비자는 64비트 코어(`trader_core.feed.ScreenerFeedClient`)이고, 계약을 벗어나면
엔진 게이트가 후보를 조용히 버리거나(신선도·가격·점수) 잘못된 전략으로 매매할 수 있다.

---

## 1. 전달 방식

| 방식 | 사용 | 비고 |
|---|---|---|
| HTTP JSON | `feed_url` (기본 `http://100.127.186.48:8080/screener_latest.json`) | 권장. Tailscale 위에서 폴링 |
| 로컬 파일 | `--feed /path/screener_latest.json` | URL에 `://` 가 없으면 파일로 읽는다 (테스트/오프라인) |

- 인증/암호화는 Tailscale 에 위임한다 (별도 토큰 없음). 접속은 `ssh jhshi@dduckbeagy-wsl` 또는 tailnet IP.
- 한 번에 **한 세대(generation)** 의 스냅샷만 보낸다. 부분 업데이트·증분은 지원하지 않는다.
- 새 스냅샷을 올리면 통째로 교체된다 (같은 URL에 덮어쓰기).

## 2. 최상위 스키마

```json
{
  "generated_at": "2026-09-11T08:40:00+09:00",   // 필수, tz 포함 ISO-8601
  "source": "analysit_dd",                        // 자유 문자열(감사용)
  "candidates": {
    "close":      { "items": [ ... ] },           // 종가 전략 후보
    "swing":      { "items": [ ... ] },           // 스윙 전략 후보
    "daytrading": { "items": [ ... ] }            // (선택) 당일 청산 전략
  },
  "scoring_summary": {
    "screener_stats": {
      "close": { "win_rate": 61.5, "avg_win_pct": 2.4, "avg_loss_pct": 1.3 },
      "swing": { "win_rate": 0.57, "avg_win_pct": 4.1, "avg_loss_pct": 2.2 }
    }
  }
}
```

- `candidates` 안의 키가 **전략 이름**이다. 없는 리스트는 빈 것으로 취급.
- `scoring_summary.screener_stats` 는 **켈리 사이징 사전확률**로 직결된다 (§6).
- `generated_at` 이 오래되면(`feed_max_age`, 기본 24h) 엔진 게이트 1이 **모든 후보를 차단**한다.

## 3. 후보 항목 필드

| 키 | 필수 | 형/비고 |
|---|---|---|
| `stock_code` | **필수** | 6자리 숫자 (`005930`). `A` 접두어는 자동 제거되지만 쓰지 말 것 |
| `close_price` | **필수(사실상)** | 종목 가격. 0/누락이면 게이트 6에서 차단된다. **주문 지정가로 그대로 쓰인다** |
| `score` | **필수(사실상)** | 0~100 권장. `min_score`(기본 0)보다 **커야** 하고, R1 문턱도 이 값으로 판단한다 |
| `score_kind` | 권장 (v1.1) | `"screener"`(기본) 또는 `"calibrated_prob"`(score = 모델 확률 × 100). 소비자가 이 값으로 R1 문턱 스케일을 고른다 |
| `valid_until` | 권장 (v1.1) | ISO-8601(KST). 이 시각이 지나면 소비자가 **그 후보만** 버린다 |
| `signal_date` | 권장 | `YYYY-MM-DD`. v1.1 부터 소비자가 **후보별 신선도 게이트**에 쓴다(오래되면 그 후보만 차단) |
| `ml_prob` | 권장 (v1.1) | 모델 보정 확률(0~1). `score_kind=calibrated_prob`이면 `score/100`과 같아야 한다 |
| `rank_pct` | 선택 (v1.1) | 모델 **분포 내 백분위**(0~100, 100=최상위). 스크리너가 전체 스코어 유니버스를 남기면 발행측이 계산해 보낸다 |
| `universe_size` | 선택 (v1.1) | `rank_pct` 의 표본 수(예: 300). 소비자가 백분위의 무게를 안다 |
| `ml_horizon_days`, `ml_model`, `ml_auc` | 선택 (v1.1) | 모델 라벨 지평/이름/AUC. 저널·감사용이며, **모르면 보내지 말 것**(추정해서 넣지 않는다) |
| `stock_name` | 권장 | 로그/저널 가독성 |
| `rank` | 권장 | 리스트 내 순위 (감사용) |
| `reason` | 권장 | 왜 뽑혔는지 (저널에 남는다) |
| 그 외 전부 | 자유 | `extras` 로 보존되어 저널/플랜에 남는다 (예: `ml_prob`, `sector`, 지표값) |

- **v1.1(2026-09-29) 배경**: (a) swing 점수가 모델 확률(0.50~0.62)인데 소비자의 R1 swing 문턱은
  0~100 점수 스케일 75 였다 → 상위10 평균 55 로 **전략 경로가 조용히 닫혀 있었다**.
  (b) 게이트 1은 `generated_at`(발행 시각)만 봐서, 발행 파일이 새것이어도 **종목별 신호가
  며칠 전**이면 그대로 매수할 수 있었다(close 후보 `signal_date=09-23` 을 09-29 에 매수 가능).
  그래서 발행 측은 `score_kind`·`valid_until`·`ml_*` 를 명시하고, 소비자(루프)는
  **스케일 인지 문턱(`r1_min_avg_prob`) + 후보별 신선도 게이트(`candidate_max_age_days`)** 로
  그 후보만 버린다.

- **모든 값은 문자열로 보내도 된다** (숫자는 자동 변환). 빈 문자열 `""` 은 "값 없음"으로 취급.
- 6자리가 아닌 코드(지수/선물 `Q530031` 등)는 **버려진다**. 주식 코드만 보낼 것.
- `close_price` 는 **진입 지정가**가 된다 → 종가 전략이면 **당일 종가(또는 현재가)** 를, 스윙이면 신호 시점 가격을 넣을 것. 장 시작 전 스냅샷이면 전일 종가를 넣고, 루프의 R3 규칙(계획가 대비 라이브 시세 ±3% 이탈 시 스킵)이 당일 시세와 어긋나면 자동으로 걸러준다.

## 4. 스크리너별 전략 의미 (중요 — 섞으면 안 됨)

| screener | 언제 도착해야 하나 | 진입 시간창(KST) | 청산 방식 | 사이징 |
|---|---|---|---|---|
| `close` (종가) | **당일 15:00 이전** | 14:50–15:25 | **다음 장 시가(09:00–09:10) 매도** | kelly_fraction 0.15 |
| `swing` | 전일 저녁(19:30)~당일 아침 | 09:00–15:20 | 손절 -7% / 익절 +15% (며칠 보유 가능) | 0.25 |
| `daytrading` | 당일 장중 | 09:00–14:50 | **당일 15:00–15:25 청산(오버나이트 금지)** | 0.15 |
| 그 외 새 이름 | — | 09:00–15:20 | 기본은 스윙과 동일(손절/익절) | 0.25 |

- 종가 리스트는 **그날 마감 직전에 사서 다음 날 시가에 판다.** 그래서 15:00 이전에 도착해야 의미가 있다.
- 종가/스윙/당일을 **한 리스트에 섞지 말 것.** 전략이 다르면 키를 나눠야 한다.
- 새 전략 이름을 쓰려면 알려줘 — 프로파일(`screener_profiles`)을 선언해줄게. 선언 전에는 스윙처럼 다뤄진다.

## 5. ML 학습 결과 전달 방법

권장: **확률을 `score` 로 변환해서 보낸다** (엔진·R1 문턱이 이 값으로 동작).

```json
{ "stock_code": "005930", "close_price": "71200", "score": "83.4",
  "reason": "ml_p_up_2pct=0.834",
  "ml_prob": "0.834", "ml_model": "rank_lgbm_v3", "ml_horizon_days": "3",
  "ml_features": "{\"mom5\":0.12,\"vol_z\":1.8}" }
```

- `score` = 보정된 확률 × 100 (0~100). 캘리브레이션(플랫/아이소토닉)해서 보내면 문턱값이 의미를 갖는다.
  **주의: `score` 가 88~99 처럼 좁게 뭉치면 문턱·상위 N 선별이 무의미해진다** (2026-09-10 자체 랭크 피드에서
  실제로 발생 → 백분위 점수로 교체). 분포가 0~100 에 퍼져 있는지 반드시 확인해서 보낼 것.
- **확률 스케일로 보낼 때는 `score_kind: "calibrated_prob"` 를 반드시 함께 보낸다** (v1.1).
  소비자는 이 선언이 있으면 R1 을 확률 문턱(`r1_min_avg_prob`, 기본 swing 0.58 = 상위10 평균 확률 58%)으로
  판단하고, 없으면 0~100 점수 문턱(swing 75)으로 판단한다 — 선언을 빠뜨리면 확률 피드가
  점수 문턱에 걸려 **경로가 조용히 닫힌다**(실측 2026-09-29: 평균 확률 0.55 로 7일간 신규 진입 0).
- **백분위 모드(선택)**: `score_kind: "rank_pct"` 로 보내면 `score` 자체가 모델 분포 내 백분위
  (0~100)이고, 소비자는 R1 을 `r1_min_avg_rank_pct`(설정 시) 또는 기존 0~100 문턱으로 판단한다.
  확률 절대값 문턱은 모델 분포가 이동하면(재학습·레짐 변화) 의미를 잃지만 백분위는 "모델 자체
  순위에서 상위 몇 %"라 강건하다. 전제: 스크리너가 전체 스코어 유니버스를 남겨야 한다
  (`reports/<screener>_universe_<date>.json`, 형식은 `scripts/screener_universe.py`) — 발행측은
  그 파일이 있을 때만 `rank_pct` 를 계산하고, 없으면 그 필드를 **보내지 않는다**(추정 금지).
  발행측 스위치: `feed_export.py --swing-score-mode rank_pct`(기본 native=확률×100).
- `filters` 블록(선택)에 어떤 파이프라인이 후보를 만들었는지 적어주면 그대로 저널에 남는다:
  ```json
  "filters": {"model": "lgbm_v3 + 뉴스게이트", "min_score": 60, "top_n": 6,
              "notes": "당일 등락률 상한 12% 적용"}
  ```
  매매별 알고리즘 귀속은 `trades.algo_json` 에 저장된다 (스크리너·점수 방식·필터·후보 지표·사이징·손절 모델).
- 원시 확률/모델 정보는 `ml_*` 로 함께 보내면 **저널에 그대로 남아** 나중에 모델 성능과 매매 결과를 대조할 수 있다.
- 모델이 여러 개면 스크리너 키를 나눠라 (예: `swing_ml_v3`). 프로파일만 알려주면 그대로 거래한다.
- 모델 전체 성능(승률·평균손익)은 `scoring_summary.screener_stats` 에 넣어라 (§6).

## 6. 켈리 사전확률 — 누가 이기나

`scoring_summary.screener_stats.<screener>` 에 아래 키가 있으면 **그 값을 켈리 계산에 사용**한다:

| 키 | 의미 |
|---|---|
| `win_rate` | 승률. `0.61`(비율) 또는 `61.0`(퍼센트) 둘 다 허용 |
| `avg_win_pct` | 이익 거래 평균 수익률(%) |
| `avg_loss_pct` | 손실 거래 평균 손실률(%) |

- 없으면 코어의 사전확률(0.55 / 1.0 / 1.0)을 쓰고, 거래가 쌓이면 자체 저널 기반 값으로 바뀐다.
- **우선순위: 피드 통계 > 자체 저널(자기수정) > 설정 기본값.**
- 즉 analysit_dd가 모델 통계를 보내면 그쪽 숫자로 사이징한다 → 과신하지 않도록 **보수적으로(축소 추정된)** 값을 보내는 게 좋다.

## 7. 물량·한도 (보내는 쪽이 알아야 할 제약)

- 코어는 한 사이클에 **상위 N(기본 6)개만** 집행한다. 하루 신규 진입 상한은 100건이지만 **같은 종목은 하루 1회**만 산다(반복매수 방지). 실질 상한은 현금과 종목당 집중한도(20%)다.
- 종목당 약 **자산의 2.5%**(켈리) — 5백만원 계좌면 약 12.5만원. 종목당 상한 20%, 주문당 상한 1,000만원.
- **랭킹을 반드시 점수 내림차순으로** 보낼 것. 우리는 `score` 로 정렬해 상위만 쓴다.
- 같은 종목을 여러 리스트에 중복으로 넣지 말 것 (포지션 중복 판정은 종목 기준).

## 8. 안티패턴 (이걸 보내면 조용히 망가진다)

| 안티패턴 | 결과 |
|---|---|
| `generated_at` 재사용/과거 값 | 게이트 1이 전부 차단 (`feed is stale`) |
| `close_price` 누락 또는 `0` | 게이트 6이 차단 (매수 없음) |
| `score` 누락 | R1/게이트 6에서 판단 불가 → 스킵 |
| 종가 리스트를 15:00 이후 전달 | 진입 시간창(14:50–15:25)을 놓침 → 다음 날로 밀림 |
| 오래된 신호를 새 `generated_at` 으로 감싸 보내기 | 게이트 1은 통과하지만 **후보별 신선도 게이트가 그 종목만 차단** → 매매 0건의 원인이 로그에만 남는다. `signal_date`(필수) + `valid_until` 을 정확히 보낼 것 |
| `score_kind` 없이 확률(0~1) 스케일 점수 전송 | 소비자가 0~100 점수 문턱으로 판단 → 그 전략 경로가 조용히 닫힌다 (v1.1) |
| 종가/스윙/당일을 한 키에 혼합 | 한 가지 청산 규칙으로만 관리됨 (전략 붕괴) |
| 지수/선물/ETN 코드 | 코드 검증에서 버려짐 |
| 부분 업데이트(항목 몇 개만) | 전체 리스트가 교체되므로 나머지가 사라짐 |

| 단계 | 도구 | 산출물 |
